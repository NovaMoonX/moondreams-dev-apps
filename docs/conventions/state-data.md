# State, data, and performance

Part of the repo conventions split out of `CLAUDE.md` (see its "Read before you touch" table). Rules here bind exactly as if they were in `CLAUDE.md`; a reference like `CLAUDE.md "X"` in older text means the bullet titled X, now in whichever conventions file holds it.

- **Firestore `onSnapshot` lives in `store/listeners/`** as `startXListener(key, onChange)`, started once from a `useXSync` hook at the app's top-level page (reference: `useNineLivesSync.ts`, `useWaypointSync.ts`). Never inside a leaf/tab/panel component's `useEffect`. The exception is a genuinely modal-local, ephemeral subscription that no other component reads (e.g. a single invite-code lookup); keep it a small hook and mount it via a conditionally-rendered, keyed component so it subscribes once per key. A listener for an optional enhancement (theaters) never feeds the fatal load-error screen: its failure degrades only its own UI, because a rules-deploy lag or one denied collection must not lock features that work. It also logs its error (`console.error`) and clears what it had loaded, so a rules lag or a typo never removes the feature without a trace or leaves stale rows on screen. A count or summary fed by a listener (a nav badge, "Nothing waiting") says loading or couldn't load until it knows, never zero, and counts every kind of item the screen it opens lists.
- **A continuation after the `await` of a write that can sit queued offline never closes or navigates shared screen state unless the screen that started it is still the one showing.** Use a functional setter that checks what is open (`closeSubviewIf`, a token compared inside `setView`) or a mounted check, never a bare `closeSubview()`: offline the write resolves much later, and a bare close shuts whatever is open by then, such as a half-typed form. A save that can sit queued offline closes its sheet once the same pure checks the write makes have passed, without waiting for the server, and marks the row ("Saves when you're back online") after a moment; only an upload holds the sheet, and then Cancel becomes Close. The same goes for a read: a reading that lands after the person left is dropped, and a confirm answered after the screen moved on leaves the new screen alone.
- **A picker never writes.** A search or pick control's "New X" stages a draft that the form saving the record writes in the same batch (see "A record created only because another record names it" below), so an abandoned plan, recipe or list leaves nothing behind. What a person does where the signal drops (ticks, adds, eating, planning) closes its form as soon as Firestore has the write locally and never holds Cancel hostage to the server; a transaction is used only where losing a rare race is worse than failing offline, and TECHNICAL.md states the race.
- **Request/response calls go through TanStack Query** (`queryOptions` factory in `src/lib/<feature>/<feature>Queries.ts` or `src/apps/<app>/queries/<resource>Queries.ts`). Key includes every param that changes the result and nothing that doesn't; `staleTime` fits how often the data changes. Writes and non-idempotent calls stay uncached. A read whose empty answer came only from the device's cache (`metadata.fromCache`) is "couldn't load", never "nothing".
- **Coming back to the tab is `useOnTabReturn` (`@/hooks/useOnTabReturn`), never a hand-rolled `visibilitychange` listener.** It fires when the page turns visible again or the window regains focus after losing it, so a dismissed "ask me later" question, a refresh of time-sensitive data or a re-check after a hand-off to another site can all hang off one place.
- **A countdown runs to a wall-clock deadline and is settled from three places:** the nearest timeout, `useOnTabReturn` and the display's own tick. A timeout that wakes before the deadline (the clock stepped back, or the tab was throttled) re-arms for what is left instead of returning, so a timer never sits at 0:00 without alerting; a deadline passed by a forward step finishes on the next tick.
- **A hook that mirrors a browser handle (a wake-lock sentinel) updates its status only for the handle it currently holds,** and treats a handle the browser already released as absent. A late `release` event from an old handle must not flip a newer one's status, a released handle is requested again instead of trusted, and a rejected release after the person left is logged, never shown as a failure (`useWakeLock`).
- **A toast for a change is keyed on a transition this page watched, not on a state.** A listener's first snapshot arrives after mount, from an empty store, so "is `sent` and wasn't `sent` before" fires for every old record on each reload. Toast only an item first seen in an earlier state and now in the target one; an item that first appears already there never toasts.
- **Screen state a person could share, reload or go back to lives in the URL through `nuqs`, not `useState`.** `NuqsAdapter` (`nuqs/adapters/react-router/v7`) wraps the router's root element. Its writes are shallow: they change the URL without telling react-router, so `useSearchParams`, `useLocation` and `history.state.idx` lag behind; give each param one reader and never use `idx` to decide what Back does. Declare the parsers next to the feature (`parseAsStringLiteral([...] as const)` for a fixed set, `parseAsString` for an id) in one `use<Feature>UrlState` hook that returns named actions (`showApp`, `goBack`), never raw setters. A step deeper (list → detail on a phone) is `history: 'push'`, and the hook marks that entry (`history.replaceState` with its own flag once the push settles) so Back pops it (`navigate(-1)`) and a deep link's Back clears the params with a replace instead. Peers, tabs and an overlay mirrored to the URL (a member sheet) are `replace`, so opening and closing never changes `history.length`. Check with `history.length` and two system Backs, not only the visible screen. Keep drafts out of the URL. nuqs updates React at once but writes the address a tick later, so a sheet that opens from a param pushes its own Back entry before the param lands: a param that opens a form on another screen is written only after that screen's push has settled, on its own kept entry (`keepEntryFor`-style, Runway's `showAddOnTab`), so Back lands on an entry that still holds it and the form's discard guard asks, and the entry steps itself away once the form closes. Offer such a param only where its consumer is drawn (a level or first-run fallback that hides the screen leaves it waiting to open later by surprise). Reference: `src/screens/admin/useDashboardUrlState.ts`.
- **Session-long state that answers for a person is keyed by uid.** A module-level flag (a dismissed offer) outlives a sign-out, since signing out does not reload the page (Runway's `DraftPickUpRow`).
- **Admin and reporting screens read once, with a refresh button; only what the admin edits is live.** Usage, visits and member lists are one-shot TanStack queries (`staleTime` a minute, all under `ADMIN_QUERY_KEY` so one refresh covers them), not listeners, because nobody watches them change. The app catalog stays a listener since its settings are edited there, and so does the Pipeline view (`usePipelineSync`, started once from `AdminDashboard`), because it is watched while sessions change.
- **`meta: { persist: true }` must earn its place.** Remove it from any query whose `queryFn` reads Firestore (Firestore's own cache already persists it) or returns secrets, tokens, or key material. Keep it on safe third-party/worker results so they work offline.
- **Performance is a design check for every app, judged at scale.** Every app keeps an oversized seed fixture (Waypoint's "Big Group Reunion (scale test)" is the reference) and a feature that adds a list or per-row work is opened on it, on a phone-width page, with the dev build throttled to 4× CPU (Playwright + CDP `Emulation.setCPUThrottlingRate`), switching between the app's main tabs. A tab switch that takes over a second at 4× on the fixture, or any "Maximum update depth" or render storm in the console, is a bug. Profile before optimizing (`Profiler.start` through CDP, sort by self time): the hot spot is rarely where it looks. A fixture is evidence only for the data it holds: when a change adds per-row work on a field the scale fixture lacks, extend the fixture before quoting a number.
- **The patterns that fixed Waypoint, to reuse:**
  - *Build once, reuse.* An `Intl.DateTimeFormat`/`NumberFormat` is built once (module-level or a `Map` keyed by its options), never per call or per row. A pure conversion called per row on every render (a time-zone offset, a trip-relative time) is cached by its inputs, or per item in a `WeakMap` when items are replaced rather than mutated (`memoizeByItem`).
  - *One pass, not per row or per pair.* Compute totals, settlements and groupings in a single walk that buckets into a `Map`, then look up; never filter the whole list inside a per-row or per-pair loop. Keep the old and new outputs identical on random data before replacing an algorithm. Text a list derives per row from data that rarely changes (the names behind each shopping row) is worked out once per change of that data, keyed by its inputs, and shared by the row and its height estimate.
  - *Memoize on stable inputs.* Derive heavy values with `useMemo` or a `createSelector` keyed on the data they read; ids derived from an object (`Object.keys(trip.members)`) are memoized on that object so downstream memos hold.
  - *One listener per key, one render per burst.* An external store that many components watch (`useUserInfo`) shares one Firestore listener per key, bumps a per-key revision so only the components showing that key re-render, and batches a burst of snapshots into one notification; `useSyncExternalStore` snapshots are O(1) and cached (`useMediaQuery` stores the breakpoint instead of calling `matchMedia` per read), and any module cache of user data is cleared on sign-out.
  - *Cap what you draw.* A list that can reach 100+ rows caps or collapses (a "Show N more", a search, a Disclosure) rather than rendering all of it. A long list grouped by day or section mounts a group only when it nears the screen (`@/components/LazyMount`, with an estimated height and the first screenful eager) and gives the group's wrapper the `defer-offscreen` utility (`content-visibility: auto`, so the browser skips style, layout and paint offscreen) with `--defer-size` set to the same estimate. `content-visibility` alone is not enough: React still builds every element, and that was the cost. Calibrate the estimate against the real height so the scrollbar barely moves. A section that can hold 60+ rows mounts them in chunks of 12 and puts `defer-offscreen` on the chunk, not the whole section (a monolithic section can't flow across CSS columns).
  - *Don't tear down what the next screen needs.* A tab switch unmounts and remounts a screen's components; a shared store's listener lingers a few minutes after its last watcher leaves (`useUserInfo`), because starting 120 Firestore listeners again cost more than the render. Never start a listener per tab or per row.
  - A listener kept alive after its last watcher leaves is stopped, and its handle cleared, by the same code that clears the cached data on sign-out (and restarted for components still watching), and a failed `onSnapshot` clears its handle, so a later watcher resubscribes. `LazyMount`'s `eager` is read once: content that has mounted stays mounted when the list reorders.
  - *Keep the tap instant.* Render the new tab in a transition (`useTransition`) and move the nav at once, and wrap each big tab in `memo` so the urgent update (the nav moving) does not re-render the tab that is leaving.
  - *Detail sheets mounted by a big list don't live in its parent.* The open state of a sheet that rows open sits in a small child the rows reach through a ref or store, so a tap doesn't re-render every day of the list; measure click-to-visible at 4× for every row type, not only tab switches (a stay row's sheet took 1.2 s while its sibling travel row took 0.1 s).
  - *Closed means unmounted.* A drawer or modal's heavy body (a filter sheet with a pill per member) renders only while open.
- **A PR that touches performance says how in its body**: a `## Performance` section with the fixture, the throttle, before/after numbers for the screens switched, and what changed.
- **`useAppSelector` that builds a new array/object** (`.filter`, `.map`, spread, object literal, `[]` fallback) must pass `shallowEqual` from `react-redux` or use a `createSelector` selector. A selector that returns an existing slice or `.find(...) ?? null` is fine.
- **Pick the atomic write that fits — never write a cached document back whole.** Anything another user can change while a modal is open (`seenBy`/`dismissedBy` maps, vote or history arrays, `members`, a paid-status map, `isArchived`) is a concurrency hazard. Full rule in `docs/conventions/data-contracts.md` ("Atomic writes"); the short form:
  - **A bulk delete or change chosen from a cached flag** (Clear what's ticked, archive all) re-reads the flag inside a `runTransaction` per chunk and touches only the documents that still match, returning the real count; or its TECHNICAL note states the window. A second device may have flipped one a second ago.
  - **A back-link written for another record** (an idea's `recipeId` when a recipe is made from it) never rides in the batch of the record the person cares about: a queued offline batch can be refused whole when the linked document vanished on another device. Commit the record first, write the link as a field-scoped update after it, never throw if the link fails, and report whether it landed (the toast claims no link it didn't make).
  - **Append/remove on an array** (`changeHistory`, `upvotedBy`) → `arrayUnion`/`arrayRemove`. A list the rules cap is merged from the transaction's own read instead: `arrayUnion` can't respect a cap, and the next add would be denied.
  - **One member's own key in a map** → `runTransaction` (read via `transaction.get`) or a dotted-path `updateDoc`.
  - **Derived from the prior value, or must hold across several documents** (role changes, approving a suggestion, a counter) → one `runTransaction` that re-reads everything it depends on and aborts with a readable message if the world changed. Network side effects (reminders, uploads) stay outside it, with cleanup if it fails.
  - **An edit form's save** → `updateDoc` with only the fields the form owns, never `setDoc` of the cached object: that silently overwrites a concurrent vote, seen-mark, or archive. Reference: `updateEvent`, `updateStay`, `markExpensePaid`.
  - **A pointer to another document** (`favoriteTheatreId`) → a transaction that confirms the target still exists, and removing the target re-points it (to another candidate, or none) in the same transaction on every surface that removes it; a dangling pointer reads as none.
  - **A prompt driven by a timestamp field** (`purchase.startedAt`) is cleared in the same write that answers it, and bounded by the item's status, so it can't re-ask after the answer or for something already over.
  - **A side effect keyed by a stored id** (a scheduled push's `trailerReminderId`) is rescheduled only when the field it derives from changed in that edit (compare with the document the transaction read), cancelled only while still ahead, and never awaited after the write: a slow or offline network must not hold the save UI.
  - **A form's save thunk accepts only the fields its form shows.** If the form doesn't show paid state, `updateX` doesn't take it, and passing the cached value back "unchanged" is the same stale overwrite. An action that reverses another (mark unpaid, un-archive) is a transaction that aborts if the state already changed and also resets the per-member flags the forward action's readers use (`paidMemberStatus`). Reference: `updateExpense` vs `markExpensePaid`/`markExpenseUnpaid`.
  - **A record created only because another record names it** (a new source typed in a recipe form, a proposed ingredient) is written in the same `writeBatch` as that record, never as a separate awaited write before it: a failed save leaves no orphan, and an offline save is queued whole instead of hanging on the first write.
  - A `writeBatch` is for independent writes with no reads. Thunks that only assign caller-supplied values to disjoint scalar fields need none of this. Reference: Waypoint `membershipActions.ts`.
- **A delete across records re-reads each record per chunk inside a transaction, removes the parent last, and reports the real count,** so an interrupted run can be rerun and leaves nothing half-removed; it leaves `updatedAt` alone where that versions a cover.
- **A reminder tells the person through one surface.** A reminder the scheduling page rings for itself carries `inAppToast: false`, and a new push path says which one surface tells the person. A saved copy that names something scheduled on a server (a timer's push) carries its id, and every way the copy is dropped cancels it; a guard on "does this exist" that reads a windowed store checks the window first; a first write that creates a shared document is a transaction, never trusting "not in the cache". Finished reminders are pruned by the scheduled sender, and a device token leaves on sign-out and when the push service reports it gone.
- **A client that starts writing a new key on create is run against the base rules first (only a rule that names the key can refuse it; the beta tier names few).** Before it ships, run the client's exact create and edit shapes against the base rules (`git show <base>:firestore.rules`) and put the consequence in the Regression check as evidence (base rules refuse a create carrying the new key). It is never a step for the reviewer: the merge workflow deploys rules, indexes and functions before it deploys the client, so the order is already right (only the preview, which builds against production rules, can't save what the new rules allow until the merge). A number written with `increment` is rounded wherever it is read back into a field or compared, and every `await` before a bounded step (sign-out's presence write) is driven offline.
