# Review agents (technical, product, design)

Spawn all three in parallel with the Agent tool: `model: "sonnet"`, `run_in_background: true`. They are **read-only**: they report findings and the orchestrator fixes. Before spawning the product and design agents, the orchestrator has the emulators, the seeded data (Alex full, Jamie empty, Taylor scale) and a dev server running on a **frozen worktree at the head commit** (fixes made meanwhile must not move what they read; a "before" build on a second port for comparisons). Agents never reset or reseed data and never edit repo files.

## Keeping these sections useful

When the owner says a review agent should have caught something (any wording: "the design agent should've caught this", "this should have been flagged"), the fix is to **that agent's section**, in the same turn as the code fix, and it is an audit of the whole section, not an append:
1. Name the **class** of failure (not the instance) and why the section missed it: no check, a check too vague to act on, a check buried among many, or one that measured the wrong thing.
2. Put it in the group that owns the class and **sharpen that check** (add the measurement that would have caught it); add a group only when none fits.
3. While in the section: merge checks that overlap, replace checks the new one subsumes, delete checks that only restate a `CLAUDE.md` rule (point to the rule instead) or never caught anything, and fix stale wording. `polish-agents.md` and `SKILL.md` point here; they never keep their own copy of a check.
4. Keep each role to about ten groups an agent can run in full, each a test with its measurement and the owner round that taught it. A section that only grows stops being run.
5. Tell the owner in one line what was added, merged, replaced and deleted.

Finish with what you checked and judged fine, what you **could not** check (needs a write, or data the fixtures lack: say so rather than "fine"), and **rule candidates** (a lasting rule in one or two lines and the section it belongs in). Count what the screens you walked volunteer (the insight budget, `CLAUDE.md` "Design & UX") and list the doors to each feature the change touches with the journey each serves: the whole app, not the diff, is what the owner judges. Write your report file if you can; if a tool refuses, return it as your final message. Do not edit any repo file.

## Technical agent

Review only each PR's own changes: `git diff origin/<base>...origin/<head>` (three dots), no checkouts. Every finding names the **production state** that triggers it ("a week of pending reminders exist and the first run sends all of them"). Groups:
1. **Repo rules** (`CLAUDE.md`): functions over loose `let` and accumulator `for`, no IIFEs, `join()` classes, no raw form elements, default-zero comments, `T | null` Firestore fields, `generateUuid`, date-only vs instant, `useAppSelector` that builds a value, listeners in `store/listeners/`, TanStack Query, `persist: true`, option lists in `constants.ts`, never an overlay on an overlay, no `setState` in an effect body.
2. **Data contract:** `firestore.rules`, `storage.rules` and indexes against every field and permission the diff touches, including legacy-shaped documents (`resource.data.get(field, default)`) and whether the PR body's verification claims are plausible. **Indexes (the emulator never enforces them):** list every `where`/`orderBy` the diff adds or changes in `src` and `functions/src`; run `npm run check:indexes`, then read `firestore.indexes.json` yourself (the script can't resolve a variable collection path); a missing index, a wrong field order or `queryScope` is a blocker, an index no query uses is a finding. Functions: secrets, cache and budget for third-party calls, `functions/README.md` rows, errors that leak a key or URL.
3. **Writes and derived state:** the atomic primitive fits (transaction for derived or cross-document, field-scoped `updateDoc`, `arrayUnion`); a picker never writes and a record created only because another names it is staged in the same batch; **a take-back, Undo or subtraction needs the quantity the source *added* stored with its tag, not recomputed from the source as it is now** (what it can't account for is stated in its result, never explained away); a count or toast reports what the screen draws (rows), not stored items; a local list that mirrors a live one is a `Map` by id, never an appended array.
4. **Day-one data:** what is in production when this ships. A fix that unblocks a silent failure (missing index, denied rule, crashed Function) releases its whole backlog: does a sender flush every missed message, a backfill touch every record, a query return thousands? Look for a cutoff and an expiry; check legacy and half-finished records (a `claimedAt` left set, a status that never advanced).
5. **Server write meets client listener, and anything that reaches the person outside the page:** trace a field a Function or another user writes through the page's life: the first snapshot after a reload (arrives from an empty store, so "changed from X to Y" sees every record as new), reload, sign-out and sign-in as another user, a second tab or device, what dismissing really changes in Firestore, and the same event arriving by two paths (a push and a toast). A toast, banner, badge or sound driven by a state rather than a watched transition is a finding. For notifications write the matrix (foreground, background, closed then opened, two devices): one delivery per event, no replay; every scheduling call passes a link; an SDK-shown notification is never shown again by hand; a notification for something already past is dropped.
6. **Silent failure and what the environment can't prove:** for every scheduled, background or best-effort path (cron, trigger, swallowed `catch`), how would anyone know it stopped, and is it logged with enough to act on? Name every claim in the PR body that rests only on the emulator, a typecheck or a read-through (indexes, scheduler timing, FCM, a real device, production-sized data) as unverified.
7. **Scale and cost** (`CLAUDE.md` "Performance"): an `Intl` formatter per call, work per row or pair that one pass would do (text derived per row is computed once per change and reused for height estimates too), a memo keyed on something that changes every render, a store that re-renders every subscriber, an uncapped list, a module cache of user data surviving sign-out. **A fixture is evidence only for the data it holds**: when the change adds per-row work on a field the scale fixture lacks, extend the fixture before quoting a number. A function that parses a person's link or page is benchmarked against a 1.5 MB body of 100,000 repeated tags and of 780 tags padded with long whitespace, and every collection it builds is capped before any quadratic step.
8. **Layers, back and offline:** every new drawer, sheet or swap-in view closes on the back gesture one layer at a time (a history entry, or it says why not) and Escape steps out of a swapped-in view; focus moves in on open and back to the opener on close; a write made where signal drops (ticks, adds, eating, planning) doesn't hold its form for the server, or the PR says why.
9. **Gaps and honesty:** seeds, docs, `SITE_VERSION`, unmet issue checkboxes, a component that exists but is unreachable, **doors and the sitemap** (`UX.md` and `JOURNEYS.md` §4.1 updated, a journey named per new door), a merge or dedupe that drops provenance (sources, tags) from the survivor, a hunk that only reflows untouched files (revert it), and words that promise more than the code does: a comment naming a cap the rules don't enforce, a check title that claims more than its assertion proves, a React key built from a label that two items can share, a `CLAUDE.md` or rules-file rule the change now contradicts (amend it in the same PR).
Also name any feature-specific risk the brief lists (money math, time zones, transitions, a backlog the change releases, a new query and its index, transactions, memoization keyed on `now`, concurrency).

## Product agent

You wear the **product manager** hat and judge the whole app, not the diff. Groups:
1. **Journeys and taps:** walk the three most common journeys and the weekly loop on the seeded plan (plan five dinners and count taps and typed words; put the week on the list and **read every amount aloud**: no "0.13 tsp", no "2.5 lemons"; tick in the order a shop is walked; cook a planned two-recipe dinner end to end; put leftovers away; look back on the calendar). Is every path discoverable from where a person would look? Dead ends, an action offered that can't be completed, a screen that doesn't serve the problem the README states, a number that could mislead. When a control moves behind ⋯ More or another door, list each moment that uses it with its taps before and after: a frequent one-tap action that became two needs a stated reason, and the moment that needs it most keeps it as the primary. Every recorded number (servings cooked, put away, times cooked) matches what happened, and a plan's servings never silently change what is cooked, shopped or boxed.
2. **Every phase and state of a record:** open each drawer for a record that is ahead, today, done and past and list its actions; one the new state made pointless is a finding, and the one primary is the next step of that phase. Then first run, no data, a lot of data, a value in the past or future, a repeat, a deleted dependency, a slow or failed network, data written before the feature.
3. **Buried or promoted:** an optional-looking detail whose answer a core number depends on and the person has in hand is a visible question with a quick default and a later way to fill it in, not "+ Add X"; flag a truly optional extra that was promoted. Data is asked for where it is in view (the till, the open fridge), and a record the person must keep true is checked by its cost: taps for a realistic week, where they stand, and the state a week later when nothing was logged.
4. **Intentional, not additive:** for the feature, list every entry point and the journey that justifies each (one home plus an in-context shortcut for a named moment is fine; three or more, or one with no journey, is a finding; a sentence that sends the person to another tab is a missing door). Count what each changed screen volunteers at 390×844 on the seeded, empty and scale kitchens and classify each item **decision / status / reference / noise**: fail on noise (a standing caveat on every step, a repeat of something on screen, an insight where nothing can be done), on one fact shown twice or with two counts a tap apart, on a first run that isn't silent (a feature or header action before the data that makes it relevant), and on a screen over budget (first run 0; a tab's front 2 plus its badge; a drawer nothing before its subject but its facts line; a row one detail line and one decision flag). **One act, one name, one icon:** count the labels each action has across its doors, and grep for two labels or icons on one handler across surfaces (round 7: "Mark as cooked" vs "I cooked this", Reset vs Dismiss); check new copy against the glossary. Report numbers before and after.
5. **Numbers and copy:** open each cost and nutrition surface on the partly-priced kitchen and ask "would this change a decision, and is it right within 20%?". A partial figure and everything derived from it (an average, a ratio) reads "so far" or "+" in its figure and **says what it averages over when the denominator isn't the count shown beside it**; a caveat shared by most rows is said once; frozen numbers say what they froze; a dismissal that hides something everywhere is its own named action with Undo. Copy is warm, plain and concrete (no jargon, no ad language). Anything that asks for a permission, shares data or leaves the app says why and has a way back.
6. **Scale and the bulk end:** fill every list that splits into groups or states with 30 to 50 rows per group (a throwaway kitchen) and look at the first screen: two groups that can both grow are a switch with counts, one at a time, not stacked sections (check the counts follow a search and an empty group keeps its tab). Every record that piles up (stock, ticked items, finished history, notes, ideas, a day's meals) has a bulk end for the day after a power cut or a holiday: with the list's own header, a confirm saying what it takes and keeps, hidden while a scope or search narrows the list, a transaction that reports the real count, and an Undo that reverses only what is still as it left it.
7. **Docs match the app:** every claim in the README, `UX.md`, `TECHNICAL.md` and the rules files that no longer matches (including a `CLAUDE.md` rule the change contradicts), and anything shipped that they omit.

## Design agent

You wear the **product designer** hat. **Phone first** (390×844, then 320×568, 390×560 and 844×390), then 1280, light and dark. Measure; screenshots alone miss most of this. Groups:
1. **Container, layers and back:** phone: bottom drawers for menus, quick actions and details; modals only for short forms and confirmations (measure each state: over ~70% of the viewport or scrolling is the wrong container); a tall drawer with a pinned footer for forms; a subview only for a search, a sequence or a page-sized task; no drawer left open behind the editor it launched. Web: popovers, dropdowns or a side panel, never a bottom drawer; a drawer form on phones is a modal at desktop; destructive confirms are modals everywhere. **One scroll area per surface**: list every descendant with `overflow-y` auto/scroll and its `scrollHeight`/`clientHeight`, scroll the list and check the header didn't move; a capped list keeps about three rows at 375×667 and 320×568. **Back:** open each overlay over a tab and over a subview, press back once: one layer closes, never a different tab, never out of the app; dialogs (help, confirm) take the press; Escape steps out of a swapped-in view; a tab keeps its scroll and state. Floating UI with the pointer idle (no tooltip showing, no icon holding focus), then hover and touch (arrow under its icon at 1280, 768, 640); count toasts on screen at once (a toast never repeats what the panel says); a help icon sits only beside a number someone acts on, in two sentences; at 320 with the largest fixture, no absolutely positioned icon overlaps its neighbouring text.
2. **Reach:** with every pinned layer showing (a timer strip, the footer, the keyboard, a toast), `document.elementFromPoint` at the centre of each primary control returns that control at 320×568, 390×560, 375×667 and 844×390 (round 7: a strip covered the next step's Start); every target is at least 40×40 counting a pseudo-element hit area; the search is the first control under a list screen's header (print its top at 390×844 and 320×568; anything between them taller than one thin switch row is a finding) and doors to related screens are tiles below it.

The primary is the largest type, **a running figure (a timer) is never larger than the text it accompanies**, reference content is smaller, tinted and at least 24px away, the action the text offers sits on it ready and not started, and anything running shows in exactly one place (round 7: cooking).
   - **No action blocks in reading flow:** write the drawer's sections in order; a block of actions between two content sections is a finding. The footer holds Modify, ⋯ More and the one primary; the rest are More rows, the destructive one last, red, with a visible edge; an action never sits after a list that can grow long.
   - **Roomy where there is room:** for every compact treatment (grouped dense rows, small subtitles, tight padding, chip rows) ask what space forced it. A view or sheet whose whole content is one list (⋯ More, a picker) owns the surface and uses the roomy layout, not the compact variant it inherited from a cramped place (round 7: ⋯ More).
   - **One figure, one anatomy** across sibling views (saved meal, planned meal, day): same place, same wording. A "Show all N" toggle must earn its place (hiding one to three of a handful is a finding); one emphasised surface per screen.
4. **Alike or different:** list every row of controls on each screen and, for each pair near each other that look alike, write the job of each. Two bordered controls within 24px differ in fill, edge or shape by job: a *which-thing* switch is cards that say their state, a *which-view* switch is one labelled button, an answer is a pill, an action is a chip, a disclosure is a plain muted line (rounds 6 and 7: cooking mode). **Siblings side by side:** sibling views and actions (a header add button on each of a screen's pills, the same record opened from two places, the recipe, saved-meal and planned-meal drawers) share one pattern, shape and wording: screenshot them together at 320 and list every difference in label, icon, size, position and order. **A shape the owner asked to unify is counted, not assumed:** census everything that draws it, emoji (✅ ☑️), icons and shared components included, with computed radius; for checkboxes also contrast (≥3:1 fill vs surface and tick vs fill), `:focus-visible`, hit area, checked, unchecked, disabled, light and dark. A done mark has one look and a solid fill never repeats down a list for a status. **Names, not counts:** a line that says what something is for names its sources (1, 3 and 50 at 320: three in full, then two and "and N more"); "for 3 meals" or an "X & N more" inside a list of names is a finding.
5. **Alignment and wrapping, measured at 390 and 1280:** print `getBoundingClientRect()` left, right and top for each part of every new row, card, header and footer (leading chip, title, detail, action under the text, trailing actions): everything under a row's text starts on the text column's edge; the chip and trailing actions sit at the same offset in a one-line, a two-line and a footer row; a tappable row's text and chevron share the section header's edges; report any sibling pair that differs by 2px or more with both numbers. 6. **State and feedback:** a quick action never flashes its surface (`MutationObserver` on `disabled`/`aria-busy`/`aria-disabled`: zero other nodes change while you tick and untick); selected, disabled and loading are distinguishable; counts only above zero; no menu or button that has nothing to offer. **A switch between two big groups** is thin, counts in the unit of the rows beneath (never items minus rows), keeps a stable order, fits one line at 320, shows one group with the bulk action on its header, and has an "All · n" when the person needs both at once (n is the sum under the same search; a search never leaves All). **A door must not look like a filter:** radius under half its height, a chevron, no count or dot, not in the pills' row, label cut not wrapped, 40px or taller, at most one tile row (~110px) added above the first list row; its status counts only what its landing view shows first. A picker starts with the person's own things (recent or saved before they type; near days as a strip of day pills). A centred panel holds one framed form (hairline that survives dark, flat `divide-y` rows, label left control right, its own Undo, never a card in a card); a one-action moment has one filled primary.
7. **Colour and tone:** dark-mode contrast; text and emoji on a filled or selected control (a selected pill with emoji, light and dark); icon, label and border one colour; solid red only for the one action that needs it; text inset from a rounded edge; a plain tone where cute isn't earned; copy that promises more than happens ("Invite" when nothing is sent).
8. **Repo design rules:** `CLAUDE.md` → "Design & UX" and "Designing a mini-app's look" plus the mini-app's rules file (shared components first, pills over radios, one border per card, `SectionHeader` with at most one CTA, toggled icon state shown by fill, footer actions on one row with Cancel left and the primary alone right, section buttons named by context, never an overlay on an overlay).
