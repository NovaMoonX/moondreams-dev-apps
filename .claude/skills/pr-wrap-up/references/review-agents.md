Before spawning the product and design agents, the orchestrator has the emulators, the seeded data and the dev server (http://127.0.0.1:5173) running on the branch under review. ## Technical agent

Review only each PR's own changes: `git diff origin/<base>...origin/<head>` (three dots). Do not check out branches. Check:
- the repo rules in `CLAUDE.md`: functions over loose `let` and accumulator `for` loops, no IIFEs, `join()` for class names, no raw form elements, default-zero comments, Firestore `T | null`, `generateUuid`, date-only vs instant, `useAppSelector` that builds a value, listeners in `store/listeners/`, TanStack Query, `persist: true`, atomic writes, never an overlay on an overlay, option lists in `constants.ts`;
- `firestore.rules`, `storage.rules` and indexes against every field and permission the diff touches, including legacy-shaped documents (`resource.data.get(field, default)`), and whether the PR body's verification claims are plausible;
- Functions: secrets, caching and budget for third-party calls, `functions/README.md` rows, errors that could leak a key or URL;
- **Indexes (the emulator never enforces them):** list every `where`/`orderBy` the diff adds or changes, in `src` and `functions/src`, and for each say whether it needs a composite index (equality plus a range or an `orderBy` on another field, or range/`orderBy` on two or more fields). Run `npm run check:indexes`, then read `firestore.indexes.json` yourself, because the script reads queries statically and cannot resolve a variable collection path. A needed index that is missing is a blocker, and so is one whose field order or `queryScope` doesn't match the query. Also flag an index no query uses any more. A Function that depends on a new index fails until it builds after deploy, so the PR body should say so;
- **What already exists the day this ships (day-one data):** for every change, ask what is in production right now that the new code will meet for the first time, and trace what it does to each kind of record. A fix that unblocks something that was failing silently (a missing index, a denied rule, a crashed Function, a disabled trigger) releases everything that piled up behind it, so check what the unblocked path now does to the backlog: does a scheduled sender flush every missed message at once, does a migration or backfill touch every old record, does a query now return thousands of rows? Look for a cutoff on how overdue something may be and for a way to expire the old items instead of acting on them. Also check legacy-shaped and half-finished records (a `claimedAt` left set by a crashed run, a status that never advanced, a recurring item long overdue) and what each does;
- **Server write meets client listener:** for every field a Function, trigger or another user writes and a client reads through a listener (a `status` that flips, a counter, a flag), trace the page's life, not just the happy path: (1) the first snapshot after a reload, which arrives after mount from an empty store, so any "changed from X to Y" check sees every record as new; (2) reload, sign-out and sign-in as another user, and a second tab or device; (3) what dismissing, swiping away or closing an in-app surface really changes, since it usually changes nothing in Firestore and the item returns on the next load unless the code remembers it; (4) the same event arriving through two paths at once (a push and a toast, a listener and a refetch) so the person gets it twice, or through neither. A toast, banner, badge or sound driven by a state rather than by a transition this page watched is a finding;
- **Notifications and anything that reaches the person outside the page:** write down the behaviour for each of: app in the foreground, app in the background, app closed then opened later, and the same account on two devices. Each must be exactly one delivery per event and no replay on reload, and the PR body should state the matrix. Also check where a tap goes: every call site that schedules one passes a link, a notification already shown by the SDK is never shown again by hand, and a record saved before the link existed still lands somewhere sensible. Check that a notification for something already past is dropped, not delivered late;
- **Silent failure:** for every scheduled, background or best-effort path (a cron Function, a trigger, a swallowed `catch`, a stretch feature that must "never block"), ask how anyone would know it stopped working, and whether the failure is logged with enough to act on. A path that can fail every run without a visible symptom needs an error that reaches the logs and a line in the README's troubleshooting;
- **What the local environment can't prove:** name every claim in the PR body that rests only on the emulator, a typecheck or a read-through (indexes, scheduler timing, FCM delivery, real-device behaviour, production-sized data), and say it is unverified rather than accepting "tested";
- performance at scale (`CLAUDE.md` "Performance is a design check"): an `Intl` formatter built per call, work done per row or per pair that one pass would do, a `useMemo`/selector keyed on something that changes every render, a store or hook that re-renders every subscriber on any change, an uncapped list, a module-level cache of user data that survives sign-out;
- gaps: seeds, docs, `SITE_VERSION`, unmet issue checkboxes, a component that exists but isn't reachable from a screen, a merge or dedupe that drops a line without carrying its provenance (sources, tags) onto the survivor, a check whose title promises more than its assertion proves, and a hunk that only reflows files the change doesn't otherwise touch (revert it).
- **A picker never writes:** grep the diff for a search or pick control whose "New X" awaits a write before the form that names it is saved (`ItemSearch`-style). A record created only because another record names it is staged and written in the same batch; an abandoned form must leave nothing behind.
- **Doors and the sitemap:** for every entry point the diff adds, removes or moves, check `UX.md`'s sitemap and `src/apps/pinch/JOURNEYS.md` §4.1 were updated, and that the PR body names the journey each new door serves. A new door with no named journey is a finding.
- **Back and offline:** every new drawer, sheet or swap-in view closes on the back gesture one layer at a time (it takes a history entry, or says why not); a write the person makes where signal drops (ticks, adds, eating, planning) does not wait for the server to close its form, or the PR body says why it must.
- a function that parses a person's link or a page: benchmark it against a 1.5 MB body of 100,000 repeated tags and of 780 tags padded with long whitespace runs, and check every collection it builds is capped before any quadratic step;
Also name any feature-specific risk: <list the risky logic for this PR: money math, time zones, transitions, first-snapshot and reload behaviour, a backlog the change will release, a new query shape and its index, rules, transactions, memoization keyed on `now`, overlay stacking, concurrency>. For every finding give the concrete production state that triggers it ("a week of pending reminders exist and the first run sends all of them"), not just the code path.

## Product agent

You wear the **product manager** hat. Question the product as a whole:
- **Paths:** is each path discoverable from where a user would look? Count the taps. Any dead end, or an action offered that can't be completed?
- **Journey or buried?** For every optional-looking detail, ask whether a core answer (savings, totals) depends on it and whether the user has it in hand right now. If both, it belongs in the path as a question with a quick default and a later way to fill it in, not behind "+ Add X". Flag buried ones, and flag any truly optional extra that was promoted to a question.
- **Problem fit:** does each screen serve the user's problem as the README states it? Anything core missing, confusing, or answered in a way that could mislead (a wrong total, an ambiguous label, an unexplained number)?
- **Trust and privacy:** anything that asks for a permission, shares data or leaves the app (location, links out) without the person knowing why, or without a clear way back.
- **Copy:** warm, product-forward, concrete. Flag spec-literal or jargon text.
- **Edge cases:** first run, no data, a lot of data, a value in the past or future, a repeat, a deleted dependency, a slow or failed network, data written before the feature existed.
- **README accuracy:** every claim in the mini-app README, `UX.md` or `TECHNICAL.md` that no longer matches, and anything shipped that they omit.
- **Scale of every list that splits into groups or states (places, to buy / got it, in stock / finished, today / later):** fill each group with 30 to 50 rows (a throwaway kitchen, never a seeded one) and look at the first screen. If reaching the second group means scrolling past the first, that is a finding: two groups that can both grow are a switch with counts that shows one at a time, not stacked sections or a disclosure. Check what the switch shows while a search is typed (the counts follow the search, and a pick with no match falls to the other group), and that a group with nothing in it keeps its tab.
- **Every record that piles up has its bulk end:** for each list the person adds to (stock, ticked items, finished history, notes, ideas, a day's meals), ask what happens after a power cut, a clean-out or a holiday, when the honest answer is "finish all of it". Finishing a hundred rows one by one is a finding. The bulk action sits with the list's own header (not under the rows), says exactly what it takes off and what it keeps in its confirm, is hidden while a scope or search narrows the list so "all" is never ambiguous, re-reads each record in a transaction and reports the real count, and has an Undo that only reverses what is still as the action left it.
- **Intentional, not additive (the whole, not the diff):** for the feature under review, count its entry points (every place it can be started or reached: a tab, a header action, a row action, a drawer row, a chip, a toast button, a nudge, an empty-state button) and name the journey that justifies each. One home plus an in-context shortcut for a named moment is fine; three or more, or a shortcut with no journey, is a finding. Then list every insight the change makes the app volunteer (a badge, count, pill, nudge line, tooltip, summary line, toast) and classify it DECISION (changes what the person does next, shown where they act), STATUS (confirms what they just did), REFERENCE (they opened it to see it) or NOISE. Noise, a repeat of something already on screen, or an insight shown where nothing can be done about it is a finding. Count the first view's volunteered items on every tab the change reaches and compare with before.
- **First-run silence and concepts:** with the empty fixture, does the feature appear before the person has any data that makes it relevant (a stock count on an empty kitchen, a nudge about prices with no recipes)? Does it add a noun the person must learn, and is it named the same everywhere (grep the copy)? A feature that only matters after the person has a certain history stays invisible until then.
- **Count what the screen volunteers (the insight budget).** For each screen you touched, at 390×844 and with the seeded (Alex), empty (Jamie) and scale (Taylor) kitchens, list every item the screen volunteers (a tile, count chip, badge, caveat phrase, status line, nudge, help icon, explanatory subtitle, toast) and classify it **decision / status / reference / noise**. Fail on any noise, on a screen over its budget (first run 0; a tab's front at most 2 plus its badge; a drawer at most 4 before its subject; a row at most 1 detail line and 1 decision flag), and on one fact shown twice in one view or with two different counts a tap apart. A header action that needs data the person doesn't have yet (Plan before any recipe) is hidden on a first run, and a sentence that lists names is capped at three and "and N more", checked with 50. Report the numbers before and after.
- **Walk the weekly loop, and read it aloud.** On the seeded plan: plan five dinners (count the taps and the typed words), put the week on the shopping list and read every amount aloud ("would someone pick that up in a shop?": no "0.13 tsp", no "2.5 lemons"), tick in the order a shop is walked, cook a planned two-recipe dinner end to end, put leftovers away, look back on the calendar. Check that every recorded number (servings cooked, servings put away, times cooked) matches what actually happened, and that a plan's servings never silently change what is cooked, shopped or boxed.
- **A record the person must keep true:** count the taps to keep it true for a realistic week and where the person is standing when they do it (the open fridge, the shop, the stove). Then walk the state a week later when nothing was logged (a pile of "Past its date", stale stock): a feature that costs more than it pays will drift.
- **Every phase of a record:** open each drawer for a record that is ahead, today, done and past, and list the actions shown in each; any action the new state made pointless (Start cooking after Cooked ✓, Eat from the fridge for the box this very dinner made, Save to Saved meals on a plate that already is one) is a finding. The one primary is the next step in that phase.
- **One act, one name; copy that says "go to X":** count the labels used for each action across its doors (planning, cooked, shopping: one verb), grep new copy against the Pinch glossary (meal, saved meal, Fridge & freezer, note, Got it), and treat any sentence that sends the person to another tab or screen instead of opening it as a missing door. A number that needs a sentence to explain a mismatch the app itself created means the numbers are wrong.
- **Cost and nutrition surfaces:** open each with the seeded partly-priced kitchen and ask "would this number change a decision, and is it right within 20%?". A partial figure reads "so far" or "+" in its figure, and so does anything derived from it, an average or a ratio ("Avg per meal so far"), wherever it can be read as a total; a caveat shared by most rows is said once; a dismissal that hides something everywhere or permanently is its own named action with Undo and a place to take it back.

## Design agent

You wear the **product designer** hat. **Mobile is the priority.** Judge every flow on the phone first, then check that the web layout uses its extra width well instead of stretching the phone layout.
- **Phone (390px):** one column, thumb-reachable primary actions, bottom drawers for menus, quick actions and details, modals only for short forms and confirmations, a tall drawer (footer pinned) for any form that grows or scrolls, and a full-screen subview only for a search, a sequence or a page-sized task. A takeover that hides all context when a drawer would have kept it is a finding; so is a details drawer left open behind the editor it launched. **Measure every modal and form in each state it can reach:** over ~70% of the viewport (about 590px) or scrolling means it is in the wrong container. A long form in one modal is a finding, whatever the desktop looks like.
- **One scroll area per surface:** in every drawer, sheet or subview that holds a list, the text and search above the list are a fixed header and only the list scrolls beneath it. Flag a list with its own `max-height` + `overflow-y: auto` inside a sheet that also scrolls (two scrollbars), a search or header that scrolls with, or is laid over, the rows (`position: sticky` over the list, rows visible above it), and a drawer body whose `scrollHeight` exceeds its `clientHeight`. Script it: with each such sheet open, list every descendant whose computed `overflow-y` is `auto`/`scroll`, report `scrollHeight`/`clientHeight`, scroll the list and check the header's top didn't move. A capped list keeps a floor of about three rows and its cap counts every line of the header above it: report the list's `clientHeight` at 375×667 and 320×568, where it is never 0.
- **A quick action never flashes the rest of its surface:** in every sheet, drawer or card, perform each quick, reversible action (tick and untick a checkbox, toggle a switch, pick a pill) and watch what else changes. A busy or disabled flag that covers the whole surface for the length of a write fades every other button for a moment, which reads as a flicker; a list that remounts does the same. Script it: with the sheet open, attach a `MutationObserver` (`subtree: true`, `attributeFilter: ['disabled', 'aria-busy', 'aria-disabled']`) and count how many nodes other than the control you acted on change while you tick and untick; anything above zero is a finding. Only a slow, consequential action (add, link, delete) may lock the surface, and a failure toast still shows.
- **Web (1280px):** may differ on purpose: side-by-side content, popovers and dropdowns for small choices, a right-side panel for details. A bottom drawer at desktop width is wrong. A form that is a drawer or subview on phones is a modal at desktop width, and destructive confirms stay modals at every size.
- **Measure alignment, don't eyeball it, at 390px and again at 1280px** (a layout that is right on the phone is often wrong at width, and the other way round). For every new or changed row, list, card, header or footer, write a throwaway script that prints `getBoundingClientRect()` left and right edges (and tops) for each part in a row: the leading chip or icon, the title, the detail line, any action or button under the text, and the trailing actions. Then check: everything under a row's text starts on the **text column's** left edge, not the leading icon's; the chip and trailing actions sit at the same offset from the row's top in a one-line, a two-line and a row with a footer; a tappable row's text and chevron share the section header's left and right edges; and a full-width control on a phone doesn't stay full-width (or misaligned) on desktop. Compare each edge across the sibling rows, and report any pair that differs by 2px or more with both numbers. Screenshots alone are not enough: a button that starts under the icon chip instead of the text looks plausible in a phone-width shot.
- **Look for, at both widths:** alignment (baselines, gutters, icon columns, anything that should be centred), space and balance (cramped or wasted space, inconsistent padding), state clarity (active tab, day or filter obvious; selected, disabled and loading distinguishable; counts only when above zero), buried journey steps (a detail the path depends on behind a "+ Add X" link or chip instead of a visible question), hierarchy (one emphasised surface per screen, clear primary action, labels that don't truncate at 390px, no horizontal page scroll), dark mode contrast, and repeated solid-red controls down a list. Also look for: text or emoji lost on a filled or selected control (check selected pills with emoji in light and dark), a control whose icon, label and border disagree, text pressed against a rounded edge or a label not lined up with its field's text, a separator dangling after a wrap, an action sitting after a list that can grow long, copy that promises more than happens ("Invite" when nothing is sent), a menu or button with nothing to offer, and a tone that is cute where it should be plain.
- **A "Show all N" / "Show more" / "Show fewer" toggle must earn its place.** For every collapse in a changed screen, at 390px and again at 320px, count how many items it hides. Hiding one to three of a handful (five share options on three rows, a short list with a tail) is a finding: the toggle costs a tap and a layout shift to save almost no space, so show everything and drop it. A collapse is right when it hides a meaningful share (more than three items, or most of a long list) and the screen would otherwise grow past a phone's height. Report the count hidden and the total with the screenshot.
- **Floating and layered UI, driven with the pointer idle:** open every container (drawer, modal, subview) without touching the mouse and print the `[role=tooltip]` count and `document.activeElement` after 1.5 s (no tooltip may be showing, no icon may hold focus visibly); then hover, wait 1.5 s, and compare arrow and trigger centers and the tooltip's edges against the viewport at 1280, 768 and 640; tap the trigger with `hasTouch` at 768×1024 and 844×390; press Escape once and `goBack()` once with each drawer open over a subview and list the dialogs left; at 320px with the largest fixture, report any overlap between an absolutely positioned icon and its neighbouring text, and measure each placeholder against its field's content box.
- **Chrome above the search field:** on every list screen (Recipes, Kitchen, Shopping, a subview's list) print the search field's top edge at 390×844 and at 320×568, and list everything between the header and it. Anything taller than one thin switch row (banners, a second header, a block of entry tiles above the search) is a finding: the search is the first control under the header, and doors to related screens are tiles below it (see "A door must not look like a filter").
- **Actions inside reading flow:** in every details drawer or sheet, write down its sections in order. A block of action rows between two content sections (a recipe's Ingredients and Steps, a day's meals and its totals) is a finding, as is a drawer that is taller than its content needs because of rows with subtitles. Actions live in the footer, or in one compact chip row under the front matter; what the app knows about the record (cooked, in stock, a note) is one kitchen block of rows that open what they sum up, not a loose line each. Report the drawer's `scrollHeight` and the heading order.
- **A centered panel holds a framed form, not a left-aligned stack:** open every panel that mixes centered text with fields or steppers (a finish or confirmation panel). Fields floating left under centered lines, loose lines with no frame, or a form that reads differently from the panel around it is a finding. Each stage sits in one framed card (hairline that survives dark mode, flat `divide-y` rows inside, label left and control right, never a card in a card), and the panel confirms itself in place with its own Undo instead of stacking a toast over another.
- **Two toasts at once:** run each multi-step flow with toasts shown (`open({ showToasts: true })`) and count how many are on screen at the same moment and what they cover; a toast that repeats what the panel already says is a finding. Find toasts with `[role="region"] [role="status"]`, never by list items: a wrong selector once reported "no toasts" over a visible one.
- **Review the back gesture as a phone user:** for every new drawer, sheet or swap-in view, open it over a tab and over a subview, press the browser back once, and write down what is open and which tab shows. One back closes one layer; never a different tab, never out of the app while a layer is open. Re-tapping the active tab scrolls it to the top, and a tab opens where the person left it (its own scroll, pill, search and period), never at another tab's scroll. Every dialog that can open on a tab screen (a help note, a confirm) takes the press itself: open each over a tab, press back once, and the tab must stay.
- **One confirmation per act, and help only where it earns it:** a panel that confirms in place raises no toast, a toast never repeats a state already on screen (a timer's own strip), and a help icon sits only beside a number someone acts on, in at most two sentences, never explaining a mismatch the app created or pointing to another tab.
- **A picker starts with the person's own things:** an empty plate, list or search shows their recent or saved items before they type, in one list with one search; a near day is a strip of day pills (today and the next six) with the full date picker behind "Other day".
- **A switch between two big groups:** wherever a screen has two groups that can both grow, check the switch is thin, has counts in the unit of the rows beneath them (never items minus rows), keeps a stable order, fits one line at 320 (or wraps cleanly), shows exactly one group, and that the screen's bulk action sits with the shown group's header. Then ask whether the person ever needs both groups at once (the shopping list: what is left and what is already in the cart). If so it needs an "All · n": n equals the sum of the other counts under the same search, the second group sits under a `SectionDivider` in the same list, the bulk action shows with that divider, a search never switches away from All, and the three thin pills fit one line at 320 with the largest real counts (owner, round 6).
- **A door must not look like a filter:** for every control that opens another screen (an entry to a related list, a "see all"), check at 390 and at 320 with the longest status that it cannot be mistaken for a pill or a filter: its computed `border-radius` is under half its height, it holds a chevron, it carries no count and no dot, and it is not in the same row as a list's scope pills. Every door label's `scrollWidth <= clientWidth` (cut short, never wrapped), doors in one row share one height, each is at least 40px tall, and print the first list row's top with and without the doors (they add at most one tile row, about 110px with a two-line status). A door's status counts only what its landing view shows first, or the landing view opens on what the status names: open each door with something due and read the first thing the landing shows. A row of pills under a search that goes somewhere else is a finding (owner, round 6: Kitchen).
- **Front matter budget:** on every details drawer, count what sits between its title and its subject as visually distinct groups (distinct combinations of font size, text color, emoji column and background): at most three, one style per group, plus one chip row; no fact said twice (a total in a line and again in a tile); a line that isn't a decision is either in the facts line or a row that opens something. Print the subject's top edge (the Ingredients or "On the plate" section) minus the title's bottom for the heaviest seeded record at 390 and at 320 in dark; it is no larger than the previous build's. At 320×568 the first ingredient or plate row starts above the pinned footer and the chips are two to a row at most (print both). A source, a last-changed date, a prep count and a stock line each in their own treatment is a finding (owner, round 6: the recipe drawer).
- **A tick control matches the app's shape language:** in an app whose radii are raised (pills, round chips), print every `[role=checkbox]`'s computed `border-radius` (at least half its width) and, in light and dark, checked, unchecked and disabled, the ticked fill's contrast with the surface and the tick's with the fill (at least 3:1 each), that `:focus-visible` shows an outline, and the hit area with any pseudo-element (at least 40×40). A square tick in a round app, or a theme rule that loses to a component's inline style, is a finding (owner, round 6).
- **Repo design rules:** `CLAUDE.md` → "Design & UX" and "Designing a mini-app's look", plus the mini-app's rules file: shared components first, pills over radios, one border per card, `SectionHeader` with at most one CTA, destructive actions last and red, toggled icon state shown by fill, footer actions on one row, the container fitted to the content (modal / drawer / subview), never an overlay on an overlay, body text in the normal color (blue only for real links and filled buttons), a visible edge on drawer action rows, Cancel on the left and the primary alone on the right, section buttons named by context ("Add").
