# PR wrap-up

Every piece of work in this repo ends with a **draft PR**, opened automatically as soon as the work is pushed (if the branch has none; never ready for review, and without asking), and every PR ends the same way below, and nobody has to ask for it. It runs whenever a push changes behaviour, and only the parts that push needs: the Stop hook (`.claude/hooks/pr-gate.sh`) lists them from the files the push changed and the PR's size, and a follow-up push redoes only the parts whose area it touched (**incremental**: the screenshots of changed screens, the regression rows of touched areas, a review of the delta).

**Skip it** only for a PR that changes no app behaviour or UI (docs, CI config, skills): say so in the PR body in one line. Its draft PR and status comment still happen, as the Stop hook says.

**What triggers each part (decide from the diff, not from cost).** Screenshots: any visible change (a new or changed section, row, control, copy or colour). Review agents: a visible change, a new or changed callable, rule, index, write path or third-party contract, or anything non-obvious in the logic; a pure docs or config diff needs neither. Cost, length of the session and "the change is small" are never reasons to skip a part whose trigger is met; if the diff meets a trigger, do the part, and if you judge it does not, say which trigger you checked in the PR body.

**An environment failure is not a reason to skip.** If the emulators or the app won't start, fall back before reporting anything. In the cloud sandbox the emulators fail with `Unable to parse JSON … "request bl…"` because firebase-tools sends its own calls to `127.0.0.1` through the agent proxy: start them (and run the seed) with the proxy unset, `env -u HTTPS_PROXY -u https_proxy -u GLOBAL_AGENT_HTTPS_PROXY npm run emulators`, and they start. Only when that fails too, fall back: mount the changed component in a throwaway Vite page (`harness.html` plus `src/__harness.tsx` in the repo root, never committed) with the real store, a seeded `QueryClient` (`setQueryData` with the query's key) and fixture data for each state (empty, filled, filtered out, error), serve it with `npx vite`, and drive it with Playwright (`$(npm root -g)/playwright`, Chromium at `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`). Give the design and product agents the harness URLs, and say in the PR body what the harness could not show (the app shell, footers, real data). Only when no fallback exists, put it first in the report to the user ("I could not do X because Y") and ask; never list it as a sandbox limit under "not done" and move on. Delete the harness files before committing.

## The body's shape (the reviewer reads this first)

The person reviewing wants to know what they are looking at, what they must do and how it works before they see any evidence. Write the body in this order:

1. **`## Overview`**: what a person can now do, from the product and user side, one bullet per capability ("Share a recipe by a link anyone can open"). Each bullet has sub-bullets with the technical know-how in a line each (the callable, the collection, the component that changed). Above it: one `Resolves #N` line per issue the PR delivers (search the open issues for its work; a closing keyword is the only thing that closes one, and `close-linked-issues.yml` closes it on a merge into any branch), then what the PR is stacked on in one line, and name anything the owner asked for by quoting it once.
2. **`## What you need to do`**: the reviewer's list and nothing else: decisions that are theirs (each as a question with the option and its cost), only copy that warrants a second look, each with why (owner: approving every string is too much), the few steps only a person can do before the merge (a new production secret, a build variable the workflows don't have, a one-off upload or console setting), steps after (what to open and what it should show); **never a step the workflows already do** (rules, indexes, functions and callable access deploy before Hosting on merge, `npm ci`, the version and tag, the Cloudflare worker): see CLAUDE.md "What you need to do leaves out everything the workflows do", and what could not be checked from here.
3. **`## How it works`**: the architecture in short sections: data and paths, rules (widened, narrowed or unchanged, one line each), Functions, the main flows, and what is deliberately not built.
4. **`## Screenshots`**: before | after for changes, one image for new screens (section 1 below).
5. **Evidence, collapsed:** `## Regression check` (security rules first), `## Performance`, `## Privacy`, `## Reviews`, `## Not checked`, `## Rules written down` and any journey or behaviour tables, each as `<details><summary><b>Regression check</b>: 14 rows, access widened in one</summary>` followed by a blank line and the section's content (tables need that blank line), closed by `</details>`. The summary line carries the verdict, so the reader can decide whether to open it. A block with nothing to say is left out, not filled.

Keep the first three sections short enough to read without scrolling past evidence; link to an evidence block instead of repeating its figures.

## 1. Screenshots in the PR body

The reader should see what changed without checking out the branch.

- **Phone first.** 390×844, `timezoneId: 'America/Los_Angeles'`, signed in as a seeded fixture user. Add a desktop shot (1280×900) only when the experience differs there (a popover instead of a modal, a side panel, a different layout). Never show real data or secrets.
- **Net new behaviour:** one screenshot per distinct screen or state is enough, **plus the door that reaches it**, as a person meets it in the app shell (the tab bar, the pill row, the Home section or the row that opens it). A harness that mounts a screen bare must also mount its door; a brief for a screenshot agent lists the doors beside the screens (owner, Runway cards: the Cards pill was never shown). What an info icon, help tip or popover on a new or changed screen opens gets its own shot (open it, then capture), since that is where a figure's caveats now live (owner, Runway setup polish: no tip was ever shown).
- **Never publish an image older than its screen.** An image taken on an earlier commit than the last change to what it shows is retaken or dropped, never republished because "the layout didn't change" (owner, Runway cards: a stale title still stranded a word).
- **Changed behaviour:** a **before** and an **after** of each changed screen. Take "before" from the PR's base branch: `git worktree add /tmp/before origin/<base>`, symlink `node_modules`, run a second dev server on another port (`npx vite --port 5174 --host 127.0.0.1`, same `VITE_*` env), and remove the worktree afterwards.
- **Nothing may cover the content the shot is for.** Seeded reminders pop an in-app toast a few seconds after load (it sits across the top of the screen and hides the title and context), and dev banners, the emulator warning, an open keyboard or a half-finished animation can do the same. `pw.mjs` `open()` hides toasts and the emulator warning by default (`open({ showToasts: true })` only when the toast itself is the subject); for any other overlay, dismiss it or wait it out before capturing. Take the shot only after the screen has settled (`waitForTimeout` after the last navigation or click), and re-take any image where something sits on top of the thing it should show. A check script finds toasts with `[role="region"] [role="status"]`, never by list items: a wrong selector once reported "no toasts" over a visible one.
- **Look before you publish.** `node .claude/skills/pr-wrap-up/scripts/contact-sheet.mjs <out.png> 560 <dir> <name> <name> …` lays several shots side by side so one look covers a before/after set.
- **Capture** with a throwaway Playwright script (`.claude/skills/build-app-mvp/scripts/pw.mjs` has `open` and `signIn`). Name files `<screen>-<mobile|desktop>-<before|after>.png` in one folder, and look at every image before publishing it, specifically for anything covering the screen's content.
- **Publish** with `bash .claude/skills/pr-wrap-up/scripts/publish-screenshots.sh <pr> <folder>`. It commits the PNGs to the `pr-screenshots` branch under `pr-<n>/` (never to the PR's branch, so the diff stays clean) and prints Markdown image links pinned to that commit, so they never go stale or cache. Put the same URLs on the status comment's **New screenshots** line (replacing the last push's), so the owner inbox shows them.
- **PR body:** a `## Screenshots` section: a before | after table for changes, and a single image for new screens, each with a one-line caption. **Every shot of a change says whether it is before or after**: in a column headed Before or After, or, for a shot outside such a table, a file name ending `-before` or `-after` (the gallery labels and orders them Before then After from either, and a shot that says neither reads as new). A label may carry a longer note after `<br>`, or after an em dash that follows a bold label (`**History** — opens from any card`; a dash after a plain label is punctuation): the dashboard shows the label on up to two lines and the note over the picture, where it can be dismissed. **The admin dashboard's gallery is built from this section, every row and every image, in the order written** (not from the status comment's "New screenshots" line, which only holds the latest push), so every screen belongs here, and a flow is rows numbered in the order a person meets them (`1 · Open a card`, `2 · History opens`): numbered rows show as a walkthrough with step numbers, and a Before and After column pair shows as one tile. Keep the section's heading exactly `## Screenshots` and put the table or image lines right under it.
- **Keep them current.** Whenever a push changes how something looks, re-take only the affected screens, re-publish, and update the links. The Stop hook reminds you on every new HEAD; treat out-of-date screenshots as an unfinished PR.

## 2. Regression check

A `## Regression check` section in the PR body shows that what the PR adds does not break what already worked, **technical regressions first, security rules above all**. Build it from the diff against the base, not from memory.

1. **Map the blast radius.** `git diff --stat origin/<base>...HEAD`, then for each changed file that something else depends on, grep its consumers: a shared component, hook or util (`src/components`, `src/hooks`, `src/utils`), a global stylesheet or token (`src/dreamer-ui.css` reaches every app), a constant, a type, a selector, a rule, an index, a Function. A change that reaches other apps is a regression risk for each of them.
2. **Security rules, always first.** If the diff touches `firestore.rules`, `storage.rules`, an index, a field's type or who may write it, a path, or a Function, say for each change whether access is **widened, narrowed or unchanged**, and who gains or loses what. Then prove it against the emulator, signed in through the Auth emulator as the owner, another signed-in user and a signed-out client: one allowed and one denied write per role-sensitive rule (including the "non-member must be denied" side), reads of a **legacy-shaped document** (new keys removed), and the PR's existing rules on the same collection. Run the same script against the **base** rules too (hot-swap with `PUT http://127.0.0.1:8080/emulator/v1/projects/<project>:securityRules`, then restore the branch's rules): the only outcomes that differ must be the ones the PR intends. If the PR touches no rules, say so only after grepping the diff for each touched field and permission. Run `npm run check:indexes` and state in the PR body which indexes the diff adds (or that no query needs one): the emulator can't catch a missing index.
3. **Data compatibility.** Existing documents lack any new field: readers default it, edits backfill it, rules accept the old shape, and a legacy-shaped document was driven through every read and edit path. Name any value that is computed rather than stored and now changes for existing users (a week boundary, a total), and call it an intended change.
4. **Shared surfaces, visually.** For every changed shared component or token, take **before and after** of each screen that uses it (from the base branch in a second worktree, as in step 1), phone first, light and dark, and look at them. Include other apps' screens when the change is global. Anything that moved without being meant to is a regression to fix, not to explain.
5. **Behaviour that existing users already rely on.** Gestures, shortcuts, defaults, copy and keyboard paths the PR replaces or removes: list each as "was / now", and why.
6. **Write it as a table:** `Area | What could regress | How it was checked | Result`, one row per risk, with the security-rules row first. Then one line each for anything found and fixed, and anything not checked and why.

**Performance section.** When the PR changes rendering, selectors, listeners, shared hooks or per-row computation, the body also has a `## Performance` section: the app's scale fixture, the throttle used (dev build, 4× CPU), before/after timings for each screen switched, what changed (formatter caches, one-pass math, shared stores, memoization, caps) and anything still slow. A PR that adds a list to an app says how it behaves on that app's fixture.

**Keep it current.** Whenever a push touches an area a row covers, re-run that row and update the result. A stale row, or a rules change with no matching row, is an unfinished PR. The Stop hook asks for this on every new HEAD, like the screenshots.

## 3. Ask Copilot first (20-minute window)

1. Request a review (MCP `request_copilot_review`), then verify it registered: `gh api repos/NovaMoonX/moondreams-dev-apps/pulls/<n>/requested_reviewers` and `…/reviews`. A request can "succeed" without registering. **If Copilot isn't listed, treat it as failed and go to step 4 immediately.** (It has not registered on draft PRs.)
2. If it registered, wait up to **20 minutes**: `.claude/skills/build-app-mvp/scripts/waitreview.sh <pr> 20 <request-time-iso>` in the background. Use the wait for the screenshots, not for idling.
3. **Copilot reviewed:** fix every real finding, reply on each thread in one line, resolve it. A finding that is wrong or out of scope gets a reply saying why, and stays open.
4. **No review in 20 minutes:** step 4.

## 4. Our own review: sized to the PR

Size the PR (S, M or L) and run the review that size gets, as `orchestrate` "Sizing the review" defines it; record the size and why in the Review block. The agents are `.claude/agents/`: `validator` (haiku) first, then `technical-reviewer`, `product-reviewer` and `design-reviewer` (sonnet), and for an L PR one reviewer per shard plus `lead-reviewer` (opus), which verifies the findings and does the cross-shard pass. Spawn them by name with `run_in_background: true`; they are **read-only**, report, and you make every fix. The size in the hook's message is a floor: raise it when the diff is riskier than its line count (a money or date calculation, a transaction).

- **The checklists live only in the agent files** (`docs/conventions/agents.md` lists them): do not copy a check into this file, a prompt or a conventions file. Give each agent a brief: the PR, base and head, the shard if any, the worktree or port, and what the owner asked for, in their words, with any concern they voiced. **A brief states the goal and the concern, never a list of what to verify** (an agent handed the design it should confirm confirms it: the receipt editor's ⋯ menu passed a review whose brief listed it as a thing to measure), and a redesign is reviewed as a whole surface, not as the delta.
- **A stack of PRs:** one `technical-reviewer` per PR (it only needs `git diff`), and one product and one design reviewer on the **top** branch, each tagging findings with the PR the flow belongs to. Before spawning them, have the emulators, the seed and the dev server running on the top branch.
- **While read-only agents are running, don't change the checkout they read.** Make fixes in separate worktrees (`git worktree add /tmp/fix-<n> <branch>`, with `node_modules` symlinked), start from the lowest PR that needs one, merge it up through each branch above in order, and push only once every agent has reported.

**Journeys, doors and insight counts in the PR body.** A PR that adds or changes a tab, drawer, row type, entry point or anything a screen volunteers also carries a `## Journeys` section: for each feature it touches, its doors with the journey each serves (an extra door with no named journey goes), the first-view insight count at 390×844 for Alex and Jamie before and after, classified decision / status / reference / noise (a noise item is a finding), and the taps of the journeys it shortens or lengthens. It updates `src/apps/pinch/JOURNEYS.md` §4.1 and §4.2 and the sitemap in `UX.md` in the same PR. The product and design reviewers' checks read it.

## 5. Triage, fix, re-validate

- Merge duplicates. Fix every real, in-scope finding. **A reviewer's severity is a claim: before fixing, say from the person's side what they are doing at that moment and whether the fix helps them then.** A fix that makes the app reach further (over a sheet, into a task, one more control) needs a journey that asks for it; without one, the finding is answered and dropped (owner, PR 559: an update strip was lifted over open sheets because a review called it unreachable mid-form). Put anything bigger in the PR body under "Follow-ups" rather than widening the PR.
- Fix on the PR the finding belongs to, then merge that branch up through every branch above it (merge, never rebase or force-push), re-running `npm run typecheck` and `npx eslint .` on each.
- Re-validate what you changed in the browser, and refresh the affected screenshots (step 1) and the regression check (step 2).
- **The last fresh design pass runs on the head that ships.** A fix round that changes `src` after the last fresh design pass is re-checked by a fresh design agent on those screens, and on every screen that draws a shared part they changed, before the PR body says "reviewed": a fix measured only by its author does not close a finding, and "left" is not an outcome (the owner's goal check, round 8: three rounds ended with the fixes unreviewed).
- **Check third-party contract claims before building on them.** A reviewer's "AMC's date format is different" is cheap to check and expensive to ship wrong; search for the real contract, and say in the PR body what is still unverified.

## 6. Write down what the review taught, automatically

Don't ask first. When a finding reflects a **lasting** design or product rule rather than a one-off bug, add it in the same PR. The same goes for a **pattern** the PR establishes or reuses (a component, a layout, a copy convention): add its line to the "Pattern index" in `CLAUDE.md`, and its rules to the app's rules file when it belongs to one app and tell the user afterwards (the PR body's "Rules added" line and the final report).

- **Where:** Conventions edits from a stack of PRs go into the one PR that owns the section (usually the procedure/rules PR) so the stack doesn't conflict, and the final report says which. Design rules go in `docs/conventions/design-ux.md` (or `app-look.md`); product rules go in `docs/conventions/product.md`; a rule for another topic goes in that topic's conventions file; a rule that only applies to one app goes in its rules file (`.claude/rules/<app>.md`) and its `UX.md`.
- **How:** fold, don't append. Tighten the nearest existing bullet instead of adding a near-duplicate, reword or remove a bullet the finding proves wrong, keep the section's voice (one or two lines, bold lead-in), and re-read the section afterwards.
- **"X agent should have caught this" is an instruction to fix that agent.** When the owner says a review agent should have caught something (or words to that effect), amend that agent's file in `.claude/agents/` in the same turn as the code fix, as an audit of the whole section, not an append, by the procedure in `docs/conventions/agents.md` (it ends with the one line to the owner).
- **This applies outside the review too.** Any time during a session, while iterating on a PR or on the user's requests, you decide something is worth noting in the product or design guidance, add it in that PR and tell the user afterwards.

## 7. Finish

Rewrite the PR's status comment (`orchestrate` "The PR status comment") last, after every push of the pass, so the owner sees where the PR stands.

The PR body ends with: Screenshots, Regression check, Performance (when it applies), Review (who reviewed, what was found and fixed, what is a follow-up), Rules added (or "none"), and what is unverified. Then the final report to the user: the same, short, with links.
