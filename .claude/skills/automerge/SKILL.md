# Automerge

"automerge" (or `/automerge`) is the owner saying, once: "if there's nothing that needs my attention, input or knowing, merge this when you're done." It covers every PR this session opens or drives from the moment it is given until the session ends, and nothing it didn't touch. It is a go to join the merge line, not to merge at once: another session's merge or deploy always finishes first.

**A small, clear-cut change needs no "automerge" at all.** When the request leaves nothing open (the owner said what to change and how), the PR is size S, and none of the holds below applies, merge it by this skill without waiting to be told, in every session (owner: "for changes like these, which are … pretty clear up front … I'd leave it to you to … auto-merge"). Anything that needs the owner's attention, a heavy decision, a risk or an irreversible step still holds it as below, and a PR you are unsure is clear-cut waits for the go.

Finish the PR the usual way first (`pr-wrap-up`, the review its size gets, fixes, status comment). Then merge it by `orchestrate` "Merging a run's PRs" (every gate there holds on the current head, the merge lock and the line, ready for review, squash, wait for the deploy), only if, in addition:

- **No heavy decision is open on it.** A heavy decision is one a follow-up PR can't cheaply undo or that could hurt the person if wrong: a figure about money the code computes wrong (not a model's answer the sandbox can't run, below), a data shape, a rule or who can see what, removing a behaviour people rely on, a secret or console step, a cost. It holds the PR as a `(who: owner)` line and a 🚩. A **light decision** (copy, a default, a threshold, how an AI is told to classify, which of two reasonable layouts) never holds it: make the call, merge, and list it under "Decisions I made for you" in the PR's status comment (a bullet each; the Pipeline view lists them with a box to change any) and any work it would suggest next under "Possible follow-ups" (the same, a box to do any; a changed call or a chosen follow-up on a merged PR arrives as a GitHub issue, which is new work), the PR body and the round's card, each with what you chose and the other option, so the owner can ask for the change after the fact (owner, Runway budget reading: "these are light decisions … you could have just merged"). A session only makes a call for the owner when a follow-up can undo it (owner: "decisions it makes should be reversible or relatively easily reversible. We should not make irreversible decisions on behalf of the user"), so anything irreversible is always asked first and holds the PR as a `(who: owner)` 🚩: deleting or rewriting stored data, a migration, publishing or sending something outside the repo, spending money, closing off an option. A reviewer finding you chose not to fix is light when it is one of these, and a question about later work goes to an issue first.
- **Nothing the owner should know is new with it.** A risk it brings (a rule widened, data rewritten, a behaviour people rely on removed, a secret or console step, a break only a device would show) holds it. **What an AI model answers is not one of these:** a prompt change that the sandbox can't run against the real model ships, and its check ("re-read the CSVs after the deploy") is a **Should** in the status comment and a ⚠️ in the card, never a 🚩 or a hold, since a wrong answer is fixed by the next PR in minutes and the code around it (normalising, forms, checks) is still verified. A known limit that was already true before the PR, written in the PR body, does not hold it either.
- **Its reviews came back clean, or every confirmed finding is fixed** and the fixes were looked at on the head that ships.

When any of these holds a PR, leave it as a draft, say which one in a 🚩 line, and carry on with the rest. While it waits its turn, say what it waits behind (the PR, its session, since when) in its status comment and in your reply. After a merge, say in one line what shipped and link the merged PR; the owner reads it after the fact.
