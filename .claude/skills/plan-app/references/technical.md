## Phase 3: Technical Design Document (TDD)

When turning PRODUCT.md into a TDD, omit boilerplate system architecture diagrams. Focus strictly on data, state, and security boundaries — plus the Backend Surface section below, which lists any new APIs, Cloud Functions, indexes, or integrations worth knowing about up front.

### Data Schema

**Firestore cannot store `undefined` — model schemas as nullable, never optional.** A write containing an `undefined` value throws at the SDK level; `null` is a normal, storable value. So every field whose value can legitimately be absent is typed `field: Type | null` — a required key with a nullable value — and **never** `field?: Type`. Every code path that assembles an object bound for Firestore (a create payload, an optimistic update, a default) must give that field an explicit value: `null` when there's nothing to write yet, never left `undefined` and never quietly omitted on the assumption "it'll just be undefined." The one deliberate exception is an array with nothing in it yet: default that to `[]`, not `null` — an empty array is already a normal, non-`undefined` Firestore value, and it avoids null-checking before every `.map()`/`.filter()` call site. Apply this to every field in every entity below, not just the ones that read as obviously optional — this is exactly the kind of thing that's easy to typo as `?:` out of habit and only fails at runtime, on a real write.

- Root all data paths under an app-specific namespace (e.g., `apps/[app-name]/...`), with two categories of exception that are deliberately **not** app-scoped: the shared user profile (`users/{uid}`) and any cross-app infrastructure collection (e.g. a central `reminders/{id}` collection — see "Central vs. app-scoped infrastructure" below). Call these exceptions out explicitly in the TDD; don't let them blend in silently with the app-scoped paths.
- Use exact field names and types. Use Enums instead of booleans for status/methods where appropriate.
- **All dates and times are millisecond Unix timestamps (`number`), never ISO strings** — this is an existing repo convention (see `docs/conventions/data-contracts.md`), not a new one, so there's no excuse for a TDD to introduce a `string` date field. This includes calendar-only values with no meaningful time-of-day (like a birthdate) — those still store as a `number` (e.g. midnight UTC of that date), not a `"YYYY-MM-DD"` string, purely for consistency of type across the schema.
- Include standard timestamps: `createdAt`, `lastEditedAt`, and action-specific timestamps (e.g., `revealedAt`) — typed `number | null` wherever the event hasn't happened yet (no edit made, nothing revealed), per the nullable-not-optional rule above, not left as `field?: number`.

**Shared container pattern**: if the app involves a space shared between multiple users (even if only one user uses it at first), model it with a container document holding `members: string[]` and `inviteCode: string | null` — structured for multi-member from day one even if the MVP only ever populates it with the creator. Nine Lives generalized this as `Household`; name it appropriately for the domain.

**Pending requests are a flat, app-scoped collection — never nested under the container, and never queried via `collectionGroup()`.** Path: `apps/{appId}/pendingRequests/{docId}`, sibling to the resource collection, not `<container>/{id}/pendingRequests/{uid}`. This isn't a style preference: `collectionGroup()` matches a collection *name* across the entire database regardless of parent path, so if two apps both nest a same-named `pendingRequests` subcollection, a `collectionGroup('pendingRequests')` query — and the `{path=**}` wildcard security rule required to make it work at all — can return or authorize documents from a completely different app. The rule itself must not be *capable* of returning cross-app data, not just filtered client-side after the fact. A flat, app-scoped collection makes every query on it an ordinary `COLLECTION`-scope query against one specific path, with no wildcard rule and no possibility of cross-app leakage.

**Doc ID scheme** — pick per-app based on whether one user can hold more than one open request at a time:
- **Single-request apps** (a hard cap on the resource, e.g. a two-person space): doc ID is just `{uid}`. A user can only ever have one pending request app-wide, so `apps/<app-name>/pendingRequests/{uid}` is trivially unique, and "my request" is a single `getDoc`/`onSnapshot(doc)` — not even a query.
- **Multi-request apps** (a user can request to join several resources concurrently, e.g. several households): doc ID is `{uid}_{resourceId}` — a composite key, not a random ID, so uniqueness (no double-request to the same resource) is enforced by the ID itself rather than a query-then-write race.

**Rules shape** — one `match` block per app, no wildcard, no nesting. The three-way `allow read` OR is the crux: each branch exists for a specific reason, not redundantly.

```
match /apps/{appId}/pendingRequests/{requestId} {
  function requestUid() { return requestId.split('_')[0]; } // composite-ID scheme only; for single-ID it's just requestId

  allow read: if request.auth != null && (
    request.auth.uid == requestUid() ||                              // path-based: makes get() work on a not-yet-existing doc
    (resource != null && resource.data.uid == request.auth.uid) ||   // proves the "my requests" list query is safe
    (resource != null && isMemberOf(resource.data.resourceId))       // proves the "requests for my resource" list query is safe
  );
  allow create: if request.auth.uid == request.resource.data.uid
    && exists(/databases/$(database)/documents/apps/{appId}/{resourceCollection}/$(request.resource.data.resourceId))
    && !isMemberOf(request.resource.data.resourceId);
  allow delete: if request.auth.uid == requestUid() || (resource != null && isMemberOf(resource.data.resourceId));
  allow update: if false; // created, read, deleted — never patched
}
```

Branch 1 (path-based) is what lets the client check "have I already requested?" via `get()` before ever writing, when the doc doesn't exist yet — `resource.data` is `null` on a nonexistent doc, so this branch can't rely on it. Branches 2 and 3 aren't for that check at all; Firestore's list-safety checker requires a rule branch that references the exact field a list query filters on, so each direction below needs its own branch to be provably safe as a *query*, not just as a single-doc read.

Both directions are now plain, single-collection queries — no `collectionGroup`, no manual index: a requester's own pending requests, across every resource they've asked to join, via `where('uid', '==', myUid)`; an owner/member's incoming requests for their own resource via `where('resourceId', '==', id)`. Both are `COLLECTION`-scope single-field queries, auto-indexed for free. If `firestore.indexes.json` ever gains a manual entry for this collection, treat that as a signal a `collectionGroup` scope crept back in — it shouldn't need one.

**Approving is one atomic `writeBatch`, never two separate writes**: add the uid to `members`, and delete the pending-request doc, in the same `batch.commit()`. Two separate writes risk a partial failure leaving the resource updated but the request undeleted (or the reverse) — a state neither side's UI accounts for. Declining just deletes the request doc.

**If the resource being joined carries anything sensitive** (an encryption key, private content), see Security Rules Design Criteria #8 above — pending state must never touch that resource document or grant a pending requester any access to it beyond their own request doc.

**Both sides of this need real, reachable UI** — a requester-facing surface (their own outgoing pending requests, with a way to cancel) and an owner/member-facing surface (incoming requests for their own resource, with approve/decline) are two distinct pieces of UI, not one. This is Flow Completeness and the reachability rule from Phase 4 applied to this specific pattern: an issue that implements sending a request but not either viewing surface is an incomplete flow by that rule, not a smaller-but-valid slice of it. One practical wrinkle worth planning for up front: a `pendingRequests` doc only stores `uid`, `resourceId`, and `requestedAt` — no resource name — so rendering the requester's own list meaningfully (e.g. "Pending: join *The Smiths' Household*") needs a follow-up fetch per result to resolve each `resourceId` to something displayable.

Worth the Wait is the reference for the single-request/uid-only scheme (a two-person space with a hard member cap); Nine Lives is the reference for the composite-ID/multi-request scheme (a user can request to join several households at once).

A quick audit list for whether an existing or new app's request/invite flow actually holds to this: the collection is flat and sibling to the resource, never nested; no `collectionGroup()` and no `{path=**}` wildcard rule anywhere in the flow; the doc ID scheme matches whether the app allows concurrent multi-resource requests; `firestore.indexes.json` has no manual entry for this collection; the resource's own read rule has no pending-related exception and no `pendingMember`-style field was added to it; both the requester-facing and owner-facing UI actually exist, not just one side.

**Two-party relationship pattern**: when two specific users need a mutual, symmetric relationship rather than an open-ended shared space (e.g. "buddies," contacts, a 1:1 connection), don't reach for the Shared container pattern above — there's no need for a `members` array, `inviteCode`, or a `pendingRequests` collection when membership is always exactly two people. Instead, key a single doc by both uids sorted and joined (`${uidA}_${uidB}`), with a `status: 'pending' | 'accepted'` enum and a `requestedBy` field. Support two distinct paths to `accepted`: instantly, when someone redeems the other user's personal, permanent invite link (redemption is implicit mutual consent — no separate accept step); or via an explicit request-then-accept flow when the initiator doesn't hold that link (only the member who isn't `requestedBy` may accept). Watch Buddies' `buddyLinks` is the worked example.

**Relationship cardinality**: when one entity references another, decide up front whether it's a single-occurrence relationship or one that can recur over time, and model accordingly:
- A **discrete, one-time event** (a dose administered, a measurement taken, a file uploaded) only ever needs a singular back-pointer (`linkedVisitId: string | null`) — the "history" is just every document of that type, sorted.
- Something that can **legitimately be referenced across multiple related events over time** (a chronic condition discussed at several visits, a symptom monitored across follow-ups) needs an array (`linkedVisitIds: string[]`, defaulting to `[]`), not a singular field, or history gets silently overwritten.
- When the "many" side is itself a multi-entity hub (e.g. a visit can involve several cats and several kinds of records), give the hub forward arrays (`linkedConditionIds`, `linkedVaccinationIds`, etc.) so it stays a complete record of everything tied to it, and keep both sides in sync via a single batched write when a link is created — never two separate writes that could drift.

**Before fixing a field as a closed enum, ask whether its set of values might ever expand — and if so, who's expected to add to it.** Two different situations, two different answers:
- **Developer-driven growth** (the app might gain a new status/type later, but only ever via a code change): a closed TypeScript union is still right. Just make sure whatever consumes it doesn't assume today's cases are exhaustive forever — a `default`/fallback branch in a switch, not a bare exhaustiveness check that would silently mishandle a value added later without every call site being updated.
- **User-driven growth** (an end user should be able to add their own value, not just pick from a fixed list): the field isn't a closed enum at all — it's a plain string, and the actual value needs somewhere to persist. Follow Reusable entities via upsert-on-first-mention below if it's the kind of value users invent as they go (a custom category, a custom label), or Reference & preset data below if it's closer to admin-curated reference data end users pick from but don't add to themselves.

This is a UX decision as much as a schema one: whether a Select/Combobox actually offers an "Other — add your own" option is what determines which of these applies, so Phase 2's form field organization section should note it per field — don't leave Phase 3 to guess from the schema alone whether a field was meant to be closed or extensible.

**A closed enum's type and its option list are two different files, not one.** `types.ts` declares the union itself (`type MealType = 'breakfast' | 'lunch' | 'dinner' | 'snack'`) — that's all it should hold. The list of selectable options a `Select`/`RadioGroup` actually renders — each value paired with its display label, and any per-value metadata like icon or sort order — belongs in `constants.ts`, as a single exported array/const (e.g. `MEAL_TYPE_OPTIONS: { value: MealType; label: string }[]`), built once and imported everywhere that enum needs to render as choices. Two things this prevents: a label re-derived inline at each call site (`type.charAt(0).toUpperCase() + type.slice(1)` scattered across three components, silently drifting once one of them special-cases a label the others don't), and a new enum case landing in `types.ts` without anyone remembering to add its option to every place that renders the list, since there's now exactly one place that needs the addition. Name the TDD's Data Schema entry for that field, and its Component & File Architecture entry, so `constants.ts` shows up in the tree the same way `types.ts` already does — it's app-scoped, alongside `types.ts`, not central to `src/lib/`, since these option lists are meaningful only within their own app.

**Reference & preset data — Firestore vs. client constants**: don't reflexively put every list into Firestore. Ask whether the data is shared, admin-curated, and likely to grow or need seeding (e.g. a condition library, a glossary) — that belongs in a seeded Firestore collection, read-only to end users. A simple, fixed pick-list for a form combobox (breed options, category presets) is a static client-side constant, not a collection — it doesn't need admin editing, live sync, or a security rule.

**Reusable entities via upsert-on-first-mention**: when a user-invented label or value will recur (a doctor's name at a given clinic, a custom document type), give it its own small entity scoped to the right level (household, clinic, etc.) rather than a free-text field copied onto every record. Create it inline the first time it's typed if it doesn't already match an existing one, and offer it as a select from then on. This avoids both retyping and the data drift that comes from two records meaning the same thing with slightly different spelling.

### State Machines & Logic

- Map out core state changes (e.g., `locked -> pending -> complete`).
- Define locking mechanisms for synchronous actions to prevent race conditions.
- If realtime presence is needed, specify how it's consumed from the global app state (e.g., reading a global RTDB path).
- **Separate "visibility" from "proactive notification."** A dashboard or timeline showing what's due/upcoming should be a plain selector over data that's already loaded (visits, due dates, etc.) — it does not need any notification infrastructure and should ship as part of core functionality. A **push notification** that fires ahead of time is a materially bigger, cross-app piece of infrastructure (device tokens, a central reminders collection, a scheduled Cloud Function) and belongs in Next Steps/Stretch, sequenced after the UI already works — don't let "show upcoming things" and "proactively notify about upcoming things" become the same TDD section or the same issue tier.

### Security Rules Design Criteria

Security rules must be secure and comprehensive without becoming so field-specific that they break every time a feature evolves slightly. Apply these criteria to every collection in the TDD, and check every Phase 4 issue that touches `firestore.rules` against them:

1. **Default to relationship-based checks, not field-diffing.** For most collections, "is this UID a member of the owning space/household" (or "is this UID the author") is sufficient. Reach for exhaustive `diff().affectedKeys().hasOnly([...])` validation only when a collection has a genuine security-critical invariant to protect — not as the default posture for every write path.
2. **Identify the small set of fields that are actually security-critical, and validate only those explicitly.** An owning-container ID can't change after creation; `createdBy` can't be spoofed; a join request's UID must match the requester. Everything else — names, notes, dates, categories — just needs a type/shape check, not a value check.
3. **Prefer type and shape checks over exact-value checks** where the specific value doesn't affect access control.
4. **Adding a new nullable field to a schema should not require a rules change.** An exhaustive per-write field allowlist makes every new nullable field a rules change and a silent trap for whoever forgets it. Reserve that pattern for collections with a genuinely locked-down, multi-step lifecycle (a two-person space-locking flow is the one clear example of this being warranted) rather than applying it by default.
5. **Give security-critical transitions their own narrow, explicit rule; let a general membership rule cover everything else.** Approving a join request is a distinct, tightly-scoped rule. Editing a notes field is just covered by "any member can write to this space's data."
6. **Every Phase 4 issue that adds or changes a Firestore-backed collection or field must treat `firestore.rules` (and `storage.rules`, if files are involved) as an explicit success criterion** — not an implied side effect someone remembers later. Seed data needs the same discipline; see Phase 4's Seed Data Stays Current rule.
7. **A visibility/privacy field is often a query filter, not an access boundary.** If everyone in the underlying relationship (buddy, space, household) can already read a document by relationship alone, a "private vs. public" style field on that document doesn't need duplicating into the read rule — write the read rule once, off the relationship, and let the field govern only which documents a *listing* query surfaces (e.g. "browse my buddy's public lists"). A direct fetch of a specific document — via a share link, say — bypasses that query filter and is still gated purely by the relationship check. Watch Buddies' private-vs-public lists are the worked example: private only means "not auto-browsable," not "unreadable by a buddy who has the link." State this distinction explicitly in the TDD so it doesn't get "corrected" into a field-level check later.
8. **A pending — not yet approved — requester's read access is exactly their own request document, never any part of the resource they're requesting to join.** Don't add a `pendingMember`-style field to the resource document and loosen its read rule to match, even partially — that grants a not-yet-approved requester read access to whatever else the resource carries. This has teeth well beyond names and dates: a resource carrying anything sensitive (an encryption key, private content) turns this from a scoping nicety into an actual data exposure if skipped. See the Shared container pattern's pending-requests writeup above for the full pattern this protects.

### Client State Management (Redux Toolkit)

This is now the standard state-management pattern for apps in this repo — write this section even if a given app's needs are simple, so the TDD says explicitly which pieces of this it uses.

- **Central vs. app-scoped infrastructure**: mirrors the Firestore split above. `src/store/` holds cross-app pieces any app can use: `configureStore`/`RootState`/typed hooks, a central `user` slice mirroring `AuthContext`, the `resetAllState` global action, a generic reusable `createFirestoreCollectionListener` utility, and a generic reusable `createOptimisticCollectionSlice` factory (apply-optimistically → write → roll back on failure). Build these once, in the first app that needs them, not per-app. Each app then gets its own `src/apps/<name>/store/` with slices/actions/listeners built on top of those central utilities.
- **Typed per-app state**: each app exports its own named state interface (`NineLivesState`, not an inline shape) and a base selector (`selectNineLives(state)`) so every other selector in that app is typed against it without casting. `RootState` composes these named per-app types.
- **`resetAllState`**: dispatched whenever the authenticated UID changes — including via any dev tooling that can swap the signed-in user without a full page reload (this repo has `DevAccountSwitcher`, which is exactly the case that makes this necessary, not just a hypothetical).
- **Snapshot listener tiering**: subscribe eagerly (on mount) to whatever a dashboard/overview needs to show without drilling into a specific record, and lazily (only while a detail view is open) to everything else. If something needs to be visible household/space-wide without opening an individual item (e.g. "what's due across every cat"), that's a sign it belongs in the eager tier even if it's normally a per-item subcollection — a `collectionGroup` query scoped by a denormalized owning-container ID is the standard way to do this (see Nine Lives' vaccinations for the worked example), and needs that denormalized ID field called out explicitly in the Data Schema section. Any `collectionGroup` query's security rule must validate that the container it's scoped to actually belongs to this app's own namespace, not just check the field value in isolation — the same cross-app leakage risk the Data Schema section's pending-requests rule avoids by staying flat applies here too, just via a same-named subcollection instead of a same-named top-level collection.
- **Context/Provider is a different tool from the Redux pattern above, not a substitute for it — but it's still the right one for a narrower job.** The test is scope: if every component within one section of a feature (e.g. every tab of one entity's detail view) needs the same running ID or the same handler, and the components in between don't otherwise use that value themselves, that's real prop-drilling and a section-scoped Context is the fix — not lifting the value into Redux, and not threading it through every intermediate component's props either. Components still read app-wide state via `useAppSelector` and dispatch via `useAppDispatch` directly — that's what removes prop-drilling for anything genuinely cross-cutting, not adding a Context next to Redux for the same data. Purely ephemeral view state nothing else needs (e.g. "which item's detail view is open") stays as local component state. Whenever the TDD identifies a section that needs a Context like this, name it explicitly up front in the Component & File Architecture section below — which context, what it provides, which components consume it — the same way the TDD names collections and selectors, not left implicit until an issue happens to need one. Create it in the same issue as the first component that actually needs it, per No Isolated Setup — a Context is exactly the kind of helper that rule already covers, not an exception to it.

### Utility Reuse — Check `src/utils/` Before Building

This generalizes Client State Management's central-vs-app-scoped split above to utility functions generally, not just store infrastructure. Before the TDD specifies a new helper for anything reasonably generic — date/timestamp formatting, string manipulation, clipboard access, validation, id generation — check central `src/utils/` first (`accountUtils.ts`, `clipboardUtils.ts`, `formatUtils.ts`, and by now `createDateInputField`/`toDateInputValue`/`fromDateInputValue` — see UI Component Conventions below) to see whether it already exists. Name the specific existing utility being reused in the TDD, the same way a reused DreamerUI component gets named — don't silently re-derive the same logic locally because checking felt like more overhead than writing five lines.

When no existing utility covers the need, decide where the new one goes by asking one question: **is this logic specific to this app's own domain, or would it make just as much sense in a app that has nothing to do with this one?**
- **App-specific** (formatting a cat's age from its birthdate field, computing a household's due-dates timeline): scope it to `src/apps/<name>/utils/`. It's meaningless outside this app's own entities.
- **Domain-agnostic and plausibly reusable** (a generic currency formatter, a debounce helper, a generic id-slugify function): build it in central `src/utils/` — even if this is the first app that happens to need it, per the same "build once in the first app that needs it, reuse after" rule already established for `FormSection.tsx` and `createDateInputField`. Don't wait for a second app to actually need it before centralizing something that obviously isn't app-specific; that just guarantees the first version gets built twice.

State this placement decision explicitly for any new utility named in Component & File Architecture below — which existing central utility (if any) it reuses, or why it's new and why it's scoped where it's scoped — the same way Context/Provider decisions above get named rather than left implicit.

### Known Footguns (Firestore Listeners & React Effects)

Generic mistakes that surfaced while building and validating the invite/pending-request pattern above — none of them specific to that feature, all of them likely to recur in any app with per-element listeners or effects gated on auth/async state.

- **An effect's dependency array must be keyed on content, not on array identity.** A hook that takes `ids: string[]` and sets up one listener per id, with the effect depending on `ids` itself, will tear down and resubscribe *every* listener on every unrelated re-render if the caller passes a freshly-derived array (e.g. `items.map(i => i.uid)`) — `.map()`/`.filter()` produce a new reference every render, even a `useMemo` recomputes to a new reference whenever its own inputs are new references. In production this looks like continuous, unthrottled reads hammering the same documents with no user interaction driving it, and it can degrade unrelated listeners as a side effect of resource contention. Fix: derive a stable key from the content (`ids.join(',')`) and depend on that instead of the array.
- **A hook that creates one listener per array element must handle the zero-element case explicitly.** If "loading" only ever resolves to `false` inside a listener's callback, and the array is empty, zero listeners get created and loading is stuck `true` forever — visible as a screen stuck loading after creating something that starts with no children (e.g. a freshly-created household with no cats yet). Fix: loading must be derived from "is there anything to wait for," not "did a listener fire" — an empty source array means there's trivially nothing to load, so resolve loading immediately rather than waiting on a listener that will never exist.
- **Don't let a "pending" value silently satisfy an "active" check via a fallback chain.** A pattern like `getPartnerUid()` returning the active member's uid, falling back to a pending requester's uid if there's no active member yet, makes any `!partnerUid`-style check for "is anyone pending" false the moment *any* request exists — because the fallback already made the value truthy. The visible symptom is a pending-approval UI that never renders, and a pending requester's live status shown as if they were already an accepted member. Fix: compute the pending-display value and the active-member value as two separate things; never derive a "nothing pending" check from a value that already has pending state baked into its own fallback.
- **An effect that silently no-ops when auth isn't ready yet needs auth as an explicit dependency, not just as a guard inside the effect.** If an effect keys off something like route changes and separately checks `auth.currentUser` internally before doing its write, it's possible for auth to still be resolving on a hard refresh or deep link — the write gets silently skipped, and since the effect's only *trigger* was the route (which isn't changing, because the user isn't navigating anywhere), it never retries. This is a race, not deterministic, so it won't reproduce on every attempt. Fix: add the auth value itself to the effect's dependency array, so it re-fires once auth actually resolves even if nothing else has changed since the skipped attempt.

### Component Encapsulation

Exactly one component per app owns cross-cutting concerns, and it's the app's own top-level component, `<AppName>.tsx` — directly, not via a thin entry file that delegates to a separate `<AppName>Home.tsx` orchestrator wrapper. Splitting "auth/loading gate" from "orchestration" into two files just to keep the entry file short adds a layer with no independent responsibility of its own; keep them together in the one top-level component, which acts as the orchestrator.

That top-level component owns only what genuinely spans the whole page:
- The auth/loading gate (redirect to sign-in, loading spinner) before anything else renders.
- Which shared container (household/space) is currently selected, and the modal state for switching to or adding one.
- The layout/composition of section components — the order they render in, nothing about how any one of them works internally.

Everything else belongs inside that section's own component (`CatsSection.tsx`, `ClinicsSection.tsx`, etc.), not lifted into the orchestrator: the section's own data selectors, its own "is the create form open" state and `isSubmitting` flag, and the create/update/delete dispatches for that section's data. A useful test while planning issues or reviewing a Possible Approach: if a feature needs the orchestrator to gain a new selector, a new boolean, or a new dispatch call that only that one feature touches, that's a sign the feature needs its own section component instead of growing the orchestrator. Watch for this specifically once an app has three or more largely-independent sections (cats, clinics, doctors, etc.) — that's exactly the shape that tends to accrete state in the wrong place if issues aren't scoped carefully.

Extract selector logic that's repeated per collection (`state.<app>.<collection>.items.filter((x) => x.<parentId> === parentId)`) into named, reusable selectors in `store/selectors.ts` (e.g. `selectCatsByHousehold(householdId)`) as soon as it's used from more than one place, rather than letting each section reimplement the same filter inline.

### UI Component Conventions (DreamerUI)

- **Any data-entry form** (create/edit screens, modals with fields, settings panels) uses DreamerUI's `Form` component and its factory functions (`FormFactories` — `input`, `textarea`, `select`, `checkbox`, `radio`, all from `@moondreamsdev/dreamer-ui/components`) rather than hand-rolled `<input>`/`useState` wiring. It already covers validation and field state, which would otherwise be re-built per app. Note this explicitly in the TDD's Component & File Architecture section wherever a form-bearing component appears, and treat it as a default — call out the specific exception in the TDD if a screen's input genuinely doesn't fit the Form/factory shape (e.g. a bespoke drag-and-drop control), rather than silently doing something else.
- **Forms render inside a modal** — a create/edit form opens over the current screen rather than as an inline expanding section or its own full-page route. This is a standing default across every app, same as the Form-component rule above; if Phase 2's UX.md flagged a genuine exception for this app, follow that instead and say so in the TDD. One standing exception applies everywhere, not just per-app: editing a list item from inside a detail view that's *already* a modal swaps that tab's content in place rather than opening a second modal — see Entity Detail View Conventions below.
- **Disclosure/Accordion for a long in-modal form**: per Phase 2's guidance on organizing a form with a lot of fields, prefer `Disclosure` — stacked, one per field group — over `Accordion`; reach for `Accordion` only when the form specifically needs its exclusive-open behavior. Both are from `@moondreamsdev/dreamer-ui/components`. There's no dedicated DreamerUI stepper for the multi-step option Phase 2 also allows for; that's local step-index state plus per-step field groups, not a library component.

  Every grouped `Disclosure` section uses this same shell, so every app's grouped forms look and behave consistently:

  ```tsx
  <div className='overflow-hidden rounded-lg border-2 border-border'>
    <Disclosure
      label={<span className='font-medium'>{label}</span>}
      buttonClassName='px-3 py-2.5 hover:bg-muted/40'
    >
      <div className='border-t-2 border-border bg-muted/20 p-3'>{children}</div>
    </Disclosure>
  </div>
  ```

  Don't inline this shell at each call site — it's exactly the kind of cross-app UI wrapper the Client State Management section's "build once, reuse" rule already applies to. Extract it as a small shared component (e.g. `FormSection.tsx`, taking `label` and `children`) in central `src/ui/`, built by the first app that needs a grouped Disclosure form, and reused by every app after that rather than re-created.

- **Inline reveal, for Phase 2's inline-reveal later-set entry point**: a `Button` with `variant='link'` (e.g. `<Button variant='link' className='text-sm' onClick={...}>+ Add engine details</Button>`), positioned at the bottom-right of the input or group it extends, that toggles local component state to render the extra input(s) in place — no modal, no step change, no network round-trip just to reveal a field. Label it with what it adds ("+ Add \<thing>"), not a generic "More options." Once revealed, leave it revealed for the rest of that form session — don't build a "show less" affordance to re-hide it, that's solving a problem the user didn't ask for.
- **Contextual entry-point modals, for Phase 2's contextual later-set entry point**: a small modal scoped to just that field or cluster — built the same way as any other form (DreamerUI `Form`/`FormFactories`), just limited to that subset of fields — triggered from wherever in the UI the field is contextually relevant, that writes a partial update to the existing entity document. This is the Update counterpart to the "quick add" pattern below: quick add handles *creating* an entity from a location other than its parent's own screen; this handles *editing one specific part* of an already-created entity from a location other than its own edit flow. Don't route this through the entity's full edit form just because the form already exists — a focused modal with only the relevant field(s) is the point.

**Entity Detail View Conventions** — the default for any screen showing one entity's full detail, not just where they were first established:

- **Open with an identity header, not a form**: avatar/icon (`shape='circle'`, `size='2xl'`) plus the entity's name, before any editable field. This reads correctly today with an initials-only avatar and needs no rework once a photo-upload feature ships — the image field just starts resolving.
- **Tabs for a detail view with more than one logical section** (core fields plus one or more related sub-entity lists, e.g. a cat's own fields plus its vaccination history) — `Tabs`/`TabsList`/`TabsTrigger`/`TabsContent` (`variant='pills'`, `tabsWidth='full'`), one tab per section. This is a level above Disclosure/Accordion, not a replacement for it: Tabs organizes between whole *sections*, Disclosure/Accordion above still organizes optional fields *within* one section's own form. Keep a field visible outside any Disclosure if a user is likely to want it at a glance every time they open the view (e.g. free-text notes) — don't bury something people check often just because it's "extra."
- **Editing a list item inside an already-open detail-view modal swaps that tab's content in place, never stacks a second modal on top** — this is the standing exception to "forms render inside a modal" above. A "← Back to \<list>" link returns to the list; saving or deleting also returns to it. Extract the form's actual fields (inputs, validation, submit/cancel/delete) into their own component with no `Modal` wrapper, so the identical fields render both inside the "Add" modal and inline in the "Edit" tab view — don't duplicate the form for the two contexts. When editing, set each field's `placeholder` to its original value (not just its `value`) — if the user clears a field to retype it, the placeholder still shows what it used to be.
- **Group closely-related quick-action buttons into one `DropdownMenu`** rather than a row of small buttons next to a primary action (e.g. "Log vaccination" + "Log weight" next to "Add cat"). Size the trigger to match the primary button beside it, not `size='sm'`.
- **Real date inputs, never freeform text.** A date field is never a plain text input with manual "YYYY-MM-DD" parsing — that's exactly the local reinvention the millisecond-timestamp rule in Data Schema exists to prevent. Build (or reuse, once it exists) a shared `createDateInputField` helper wrapping `FormFactories.input` with a native `type: 'date'`, paired with `toDateInputValue`/`fromDateInputValue` for the timestamp↔input-value conversion, as central utilities in `@/utils` — same "build once in the first app that needs it, reuse after" rule as `FormSection.tsx` above.
- **A "quick add" flow reuses the existing form, not a second one.** If an entity needs to be creatable without first navigating into its parent (e.g. logging a vaccination without opening a specific cat first), add an optional parent-selector prop to the existing form component that renders a required "which parent" field only when that prop is passed — the per-parent usage, where the parent is already known, simply never passes it.
- More generally, check the DreamerUI component catalog (`https://ui.moondreams.dev/components`) before specifying a new bespoke component for anything that looks like a standard UI pattern (modals, toasts, tabs, calendars, tables, etc.) — reach for the shared library first, and only design something custom when DreamerUI genuinely doesn't cover it.
