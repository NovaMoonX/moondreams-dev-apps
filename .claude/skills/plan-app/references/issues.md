## Phase 4: Issue Roadmap

When breaking the TDD down into actionable tasks, adhere strictly to a Vertical-Slice Development approach.

**No Isolated Setup**: Never create issues just for "setting up types", "creating utilities", or "building hooks". Types, helpers, and hooks MUST be created in the exact same PR as the UI component that first consumes them. The one standing exception is genuinely cross-app infrastructure (see "Tiering" below) — a central Redux store foundation or a central notification system earns its own issue because multiple future features depend on it, not because it's "just setup."

This rule applies at the field level too, not just the whole-type level, and to security rules the same way it applies to types/helpers/hooks: **don't add a field to an entity's interface, or a rules clause for it, until the issue that actually uses that field is being implemented** — even when the TDD's Data Schema already documents where that field will eventually go. An MVP-tier issue only puts MVP-tier fields into the actual `types.ts` interface and the actual `firestore.rules`; a Next Steps or Stretch field gets added by *that* tier's own issue, when it's genuinely being built, not pre-added "for completeness" by an earlier one. This is exactly what Security Rules Design Criteria #4 sets up: rules built on relationship-based checks rather than exhaustive field allowlists mean adding a field later is normally a schema-only change, so there's no cost to waiting for the field's own tier. The TDD can and should still document the full shape across every tier up front — that's what keeps an MVP-tier schema decision (like a shared container's `members` array) from forcing a breaking migration once Next Steps or Stretch actually arrives — but documenting a shape and adding it to the codebase are different things, and this rule governs the second one. It should all be iterative: MVP issues build MVP, Next Steps issues build Next Steps, and neither reaches ahead to do the other's work early.

**Sealed fields follow the same rule, and need it more.** A sealed field is one stored as an encrypted payload (an envelope of ciphertext plus its nonce, algorithm and key metadata) rather than as plain values. The plaintext shape inside the envelope is part of the schema even though nothing outside can see it: **a sealed payload gains a field in the issue that uses it, never early.** Adding an inner field means, in that same issue, the payload's inner type, the code that seals it, the code that opens and renders it, and any seed entry that carries it. Never widen the payload "for completeness" ahead of its consumer. This needs stating separately because the safety nets that catch an early plain field don't see inside a sealed one: `firestore.rules` can only validate the envelope, so no rules clause will ever flag an unused inner field, and the issue's Success Criteria are the only place it gets caught. Because payloads sealed by earlier issues won't have the new field, readers default it (`?? null`) and nothing re-seals old data to backfill it; say so in the issue. The envelope's own fields (ciphertext, nonce, algorithm, key id and version) land once, in the first issue that seals anything, not piecemeal.

Same pairing discipline applies to a closed enum and its option list (see Data Schema's note on `types.ts` vs. `constants.ts`): an issue that adds a new enum case to `types.ts` adds that case's entry to `constants.ts` in the same PR, and both files belong in that issue's **Files** list explicitly — not just `types.ts`, with the option-list update left as an assumed side effect the way seed data used to be before Seed Data Stays Current made it explicit.

This rule's "no isolated setup" framing is about not front-loading a helper before anything consumes it — it isn't permission to write a new one without first checking whether it already exists. Before an issue's Possible Approach specifies writing any reasonably generic helper, check central `src/utils/` per Client State Management's Utility Reuse note above; if it's already there, the issue's Possible Approach names the existing utility being reused, not a new one being written. When an issue does introduce a genuinely new utility, its Possible Approach states the app-scoped-vs-central placement call from that same note, briefly, rather than leaving the reader to infer why it landed in one `utils/` folder and not the other.

**Section Ownership**: per Component Encapsulation in Phase 3, feature-specific state, selectors, and dispatches belong in that feature's own section component, not in the app's top-level orchestrator. When writing an issue's Possible Approach, if a step would add a selector, a boolean, or a dispatch call to `<AppName>.tsx` for something only the issue's own feature needs, route it into that feature's section component instead (creating one now if it doesn't exist yet) — don't let successive issues each add "just one more thing" to the entry file until it's carrying every feature's state.

**Create+Read Pairing**: Most entities in this repo end up needing full CRUD; plan for that explicitly in Phase 4 rather than treating "it can be created" as the finish line. When scoping the issues for a given entity, Create and Read must ship in the same issue — never an issue that writes data with nothing yet rendering it back. This is what makes the reachability rule above actually checkable end-to-end: the developer needs to both trigger the create flow *and* see the result land in the UI, in one PR, not take it on faith that the write succeeded. Update and Delete are not part of this pairing: if a full-CRUD scope for an entity would blow past the PR size budget below, that's the signal to peel Update/Delete off into a follow-up issue (sequenced right after, same tier) — never to peel off Read instead.

**Flow Completeness**: some entities aren't a standalone record — they're one step in a flow involving more than one action or more than one viewer. A pending request/invite is the clearest example: sending it is a create, but the flow isn't done until there's a way to see it as the sender, a way to see it as the recipient, and a way to resolve it (approve/decline, accept/reject) — see the Shared container pattern's own note on this in Phase 3. It's easy to plan an issue for "send a request" and stop, because the write is what's visible in the schema — the viewing and resolving steps are just as much part of the flow and are just as subject to Create+Read Pairing and the reachability rule above, not a lesser, optional add-on. Before writing issues for any entity like this, write out the whole flow first — every action, every side that needs to see something, every way it resolves — and check off that each step has a real issue behind it, not just the step that creates the record. This isn't limited to invites: check any entity in the TDD whose creation isn't the whole story for who else needs to see or act on it.

**Docs Stay Current**: if an issue changes something PRODUCT.md (and the README's summary), UX.md, or TECHNICAL.md already states as fact — a screen that no longer works the way its board or `UX.md` row shows it, a flow that gained a step, a schema decision that changed — updating that doc is part of the issue's own scope, not a separately-remembered chore. Name the specific doc and section in the issue's Files/Possible Approach the same way the Context field already points *into* these docs (see the Issue Template below) — this is the same pointer, just written when an issue is closing a doc's gap rather than opening one.

**Keep `.github/copilot-instructions.md` current**: per the note on this near the top of this skill, a convention doesn't have to be discovered during planning to belong there — plenty surface mid-implementation instead (a footgun worth naming, a pattern that turned out to need a hard rule, exactly like the invite/pending-request architecture and the Known Footguns above did in practice). When an issue's own work establishes or corrects a repo-wide convention like that, updating copilot-instructions.md is part of that issue's scope, named explicitly in its Success Criteria — not left as a mental note that only exists in the PR description.

**Seed Data Stays Current**: seed data goes stale the same way rules do, from the same cause — a schema change that isn't propagated everywhere it needs to be. Any issue that changes what a seeded document of some type should look like (a new required-shape expectation, a field renamed, a nullable field's default) updates `scripts/seeds/<app-name>.ts` in the same PR. This is the same discipline as Security Rules Design Criteria #6's seed-data line — stated here as its own rule because it's easy to remember for the "adds a Firestore collection" case that criterion names and forget for a same-app schema *change* that doesn't add anything new.

**PR Sizing**: Scope issues to roughly 200–400 lines of code. Create+Read together are sized as one unit against this budget; when full CRUD doesn't fit, trim by deferring Update/Delete (see Create+Read Pairing), not by shrinking scope in a way that leaves Create without Read.

**Tiering**: Group and sequence issues into MVP / Next Steps / Beyond tiers mirroring the PRODUCT.md's Core MVP / Next Steps / Stretch Goals split. Within a tier, order strictly by prerequisite. Across tiers:
- MVP-tier issues come first, including any infrastructure they genuinely require.
- Push notifications, and any comparably heavy infrastructure that's a real stretch goal rather than a blocker, belong in a Beyond tier sequenced near the end — the core UI should ship and work end-to-end without them. Don't let "this would be good shared infrastructure" pull a stretch-goal feature earlier than its tier warrants.
- The same discipline runs the other direction too, per No Isolated Setup above: an MVP-tier issue doesn't reach ahead and add a field, a type, or a rules clause that only a Next Steps or Stretch issue will actually use. Each tier's issues build exactly that tier's functionality — no more, no less — even where the TDD's schema already shows the fuller picture.
- **Cross-app alignment**: if this app introduces new shared infrastructure (a new state-management pattern, a new central service), add one final issue — its own tier, sequenced last — to migrate other *existing* apps onto it. It depends only on the foundational infrastructure issue, not on anything else in this roadmap, and doesn't block this app's own launch.
- **Tier headings in the roadmap file**: group the roadmap's issues under literal `## MVP`, `## Next Steps`, and `## Beyond` level-2 headings, in that order, one per tier actually used. This isn't just organizational — `npm run issues:create` (`scripts/createGithubIssues.ts`) reads each heading's text verbatim as that tier's GitHub label, applied to every issue under it (see "Creating the issues" below), so the heading text must be the plain tier name and nothing else (not `## Tier: MVP`, not `## MVP Tier` — either becomes the literal label text).

**Issue Template Structure** — every issue gets:

```
**Prerequisites:** (Previous issues that must be completed)
**Target PR Size:** (e.g., ~300 lines)
**Files:** (List of files to touch)
**Context:** (Which specific section(s) of PRODUCT.md/TECHNICAL.md this issue depends on — see below)
### Description
### Possible Approach (Step-by-step technical implementation guide)
### CRUD & Entry-Point Requirements (checklist — see below; omit only if this issue genuinely touches no entity)
### Success Criteria (Checklist of agent-ready, testable requirements)
```

**Context field**: name the specific PRODUCT.md/UX.md/TECHNICAL.md section(s) relevant to that issue (e.g. `` Read `src/apps/nine-lives/TECHNICAL.md`'s "8. Visit" section and the "Visit Outcome Flow" subsection before starting ``), not just "read the docs." Whoever picks up the issue won't have this planning conversation's context — only the issue text and whatever's already committed to the repo — so point them at the exact place the reasoning lives instead of restating it. This matters most for issues with non-obvious design decisions behind them (why a field is an array vs. singular, why a listener is eager vs. lazy, why a create form only asks for its initial-set fields per UX.md's progressive disclosure); a purely mechanical issue can have a lighter Context note.

**CRUD & Entry-Point Requirements**: real markdown checkboxes (`- [ ]`), not prose — one line per operation, naming what it concretely means for *this* entity, not just checking the box abstractly. This is the actual, per-entity form of Create+Read Pairing and the reachability rule below, written out instead of left as something to keep in mind while scoping. Worked example, from a real issue attaching a condition to a cat:

```
### CRUD & Entry-Point Requirements
- [ ] **Create:** attach a condition to a cat, from the library or as a fully custom entry (already covered above).
- [ ] **Read:** a cat's attached conditions are visible in a dedicated "Conditions" tab on that cat's details view, following the same tabbed pattern established for Vaccinations/Weight history in Issue 6 (`src/apps/nine-lives/components/CatDetailsModal.tsx`) — not a component that exists but is never rendered anywhere reachable.
- [ ] **Update:** an attached `CatCondition` can be edited after creation (e.g. updating notes, marking it resolved, correcting a mis-picked library entry) without deleting and recreating it.
- [ ] **Delete:** an attached `CatCondition` can be removed, with a guarded confirmation (mirror the delete-confirmation pattern already used for cats/vaccinations elsewhere in Nine Lives), and this is verified to not affect `conditionLibrary` itself.
```

Notice what each line is doing: **Read** is where reachability actually gets verified — it names the exact reachable surface (a specific tab on a specific component), not just "displays it," per the reachability rule below. **Update** and **Delete** point at an existing pattern elsewhere in the app to copy rather than inventing a new one. When Update or Delete is genuinely deferred to a later issue per Create+Read Pairing below, say so on that line (e.g. `- [ ] **Update:** deferred to Issue #14`) rather than leaving it unchecked with no explanation. For a flow that isn't clean single-entity CRUD (an approve/decline action that batches a write across two collections, say), Flow Completeness below is the right tool instead of forcing it into this shape.

**Success Criteria must include, wherever the issue touches a Firestore-backed collection or field**: an explicit line confirming `firestore.rules` (and `storage.rules` if files are involved) were updated per the Security Rules Design Criteria, and another confirming seed data was updated if the schema change affects what a seeded document looks like. Don't leave these as assumed side effects.

**Success Criteria must include, wherever an issue introduces a new entity's Create flow**: this is exactly what the CRUD & Entry-Point Requirements checklist above is for — Read must be checked (with the concrete reachable surface named) in the same issue as Create, and Update/Delete either checked or marked with the specific follow-up issue that carries them, never left unchecked with no explanation.

**Success Criteria must include, wherever an issue is one step in a multi-step flow** (per Flow Completeness above): a line naming every other step in that flow — the other sides that need to see it, and however it resolves — and stating whether this issue covers each one or defers it to a named follow-up issue. An issue that sends a request with no stated plan for how it gets seen or resolved has an incomplete Success Criteria, even if the write itself is fully correct.

**Success Criteria must include, wherever an issue changes something a committed doc already states, or establishes/corrects a repo-wide convention, or changes what a seeded document should look like**: one line per Docs Stay Current, Keep `.github/copilot-instructions.md` current, and Seed Data Stays Current above, confirming each was updated — or, if genuinely none of the three apply to this issue, that's fine, but the check should still have been made rather than skipped by default.

**Success Criteria must include, for every field, type, and rules clause the issue adds**: a check that each one is used by *this* issue's own functionality — not sitting there unused because it was pre-added for a Next Steps or Stretch feature this issue doesn't actually implement. Per No Isolated Setup above, a field with no consumer in the current issue doesn't belong in this PR yet, however clearly the TDD anticipates it. For a sealed payload this is a separate line of its own: each inner field the issue adds to a sealed payload is sealed, opened and shown by this issue's own code, and readers default it for payloads sealed before it existed (see "Sealed fields follow the same rule" above).

**Success Criteria must include, wherever the issue adds or changes a UI surface the user can open** (a screen, modal, drawer, panel, or form): an explicit line confirming it has a reachable entry point in the running app — a nav item, button, menu item, or route already wired up — so the developer can open it and visually check the work without wiring anything else together first. For anything tied to a specific entity, this is verified by the CRUD & Entry-Point Requirements checklist's Read/Update/Delete lines above naming their reachable surface; this broader rule is what still applies to UI that isn't entity-shaped (a new screen unlocked by navigation, a settings panel). This generalizes the "route before any other UI work" rule in Important Notes below to *every* issue that adds UI, not just the app's very first screen: a modal or form that only exists behind a `// TODO: hook this up` isn't done. If the natural trigger genuinely belongs to a later issue (e.g. a detail modal that a not-yet-built list row will eventually open), this issue should still add a minimal stand-in trigger (a temporary button is fine) so it's independently verifiable now, and Success Criteria should say so explicitly rather than leaving verification deferred to some future issue.

**Formatting**: write the roadmap as plain `### Issue N: Title` sections (not individually fenced in code blocks), grouped under the `## MVP` / `## Next Steps` / `## Beyond` tier headings above, in their own file, `<app-name>-ISSUES.md`, separate from the TDD. This is deliberate, not just a style choice: `npm run issues:create` (`scripts/createGithubIssues.ts`) parses exactly this format — both the issue headings and the tier headings — to bulk-create the issues on GitHub.

**Roadmap preamble**: the roadmap file opens, above the first `## ` tier heading, with a short preamble: how the tiers map to PRODUCT.md's Build Plan, that each issue adds only the fields, types and rules clauses it uses, and the two closing checks every issue ends with. The checks are written once in the preamble and then repeated verbatim as the last two Success Criteria lines of every issue, because each issue is filed on its own and its body has to stand without the preamble:

1. **Release and validation**: the repo's release-label rule is followed, `npx tsc -b --force` and `npx eslint .` pass, and the feature was driven in a real browser at phone width in light and dark.
2. **Docs current**: the PRODUCT.md Build Plan lines the issue delivers are checked off (and the README's Status list), and `UX.md`, `TECHNICAL.md` and the app's rules files still match what shipped.

**Use the label rule, not a hard-coded version bump.** Never write "bump `SITE_VERSION`" (or any other specific version-bump instruction) into the preamble or an issue. Read how the repo handles releases in its `CLAUDE.md` and `.github/copilot-instructions.md` at planning time, and write check 1 as that rule: the issue's PR carries the release label the repo's rule calls for, at the size that issue warrants (a feature versus a fix). Name the label in the check only if the repo's docs name it; otherwise say "the repo's release-label rule" and leave the lookup to the implementer. If those docs describe a manual version bump rather than a label, flag that mismatch to the user instead of silently choosing one. An issue that changes no app code or behavior (a docs-only issue) says so in check 1 rather than inheriting a label it doesn't need.

### Creating the issues

Once the roadmap is approved and committed as `src/apps/<id>/ISSUES.md`, run the repo's own script from the repo root (it needs `gh` signed in with `project` and `read:project` scopes, so it runs on the owner's machine):

```bash
npm run issues:create:dry-run -- <app-id>   # parse and preview; needs no gh
npm run issues:create -- <app-id> --app-name "<App name>"   # before the app is in APP_REGISTRY
npm run issues:create -- <app-id> --file <draft>.md   # a planning draft not yet in src/apps
```

For each `### Issue N: Title` it:
- titles the GitHub issue **`<App name> N: Title`** (the app's `name` in `APP_REGISTRY`, or `--app-name "<App name>"` while the app isn't registered yet, which is every new app's first run), e.g. `Runway 3: Income sources`, so the roadmap number stays visible and never clashes across apps;
- labels it with its tier (the `## MVP` / `## Next Steps` / `## Beyond` heading it sits under, verbatim), creating the label the first time;
- adds it to project board 3 with the board's **Apps** field set to the app's name and, for a new issue, **Status = Ready** (the board's Apps field needs an option of that exact name; add it once in the board's field settings, and the script stops and says so when it is missing);
- once every issue exists, replaces every `Issue N` still in a body (as it stands on GitHub) with the real `#123`, so later docs, PRs and status comments use the real numbers.

It is safe to re-run: an issue found by its prefixed or its bare title is not created again; it keeps its board Status and any edits to its body, and only gets its tier label, Apps field and links. In a cloud session without `gh`, create the issues with the GitHub MCP `issue_write` using the same title format, then ask the owner to run `npm run issues:create -- <app-id>` (with `--app-name` if the app isn't registered yet) once locally, which attaches them to the board.

‼️ Important Notes:
- **App registration, branding, usage tracking and the app's route are all one first issue** (alongside the store foundation, if this is the first app needing it) — nothing else depends on any of it, it can be built in parallel with everything else, and there's no dependency reason to split "register the app" from "make it reachable" into two issues when the second is a natural, small follow-on to the first. Scope its **Files** exactly — this issue has a recurring tendency to over-scope if left implicit:
  - **Net-new files**: `public/banners/by-app/banner-<app-name>.png`, `public/logos/by-app/logo-<app-name>.svg`, `functions/src/apps/<app-name>/findFirstActivityAt.ts` (with its `FIRST_ACTIVITY_FINDERS` entry and the `useTrackAppUsage` call in the app's top-level page), and the route itself. The site installs as one app, so there is no per-app manifest. Walk the "New app checklist" in `.github/copilot-instructions.md` for the rest (e.g. an entry in `src/routes/AppRoutes.tsx`, even if it only renders a placeholder screen at first). The route must be listed explicitly in Files, not just mentioned in prose, so it's not accidentally deferred to a later issue.
  - **Two existing files to register the app, each with a single small addition**: `src/lib/app/app.registry.ts` (add the app's entry) and `src/lib/types/appCatalog.ts` (add the app's catalog entry).
  - **`cloudflare-worker.js` gets exactly one new entry in its own app registry** — nothing else in that file changes. Over-touching this file is the single most common way this issue goes wrong and has to be partly reverted.
  - **`src/lib/app/app.constants.ts` is not part of this issue and should never appear in its Files list.** It holds parent-app-wide detail (app description, admin email) — nothing per-app — so registering a new app never touches it, no matter how adjacent it looks to `app.registry.ts` in the same folder.

  The point of folding the route into this issue rather than a separate one is the same reason the route needs to exist this early at all: every subsequent issue's UI work can be opened and visually checked in a running app as it lands, rather than only becoming reachable once everything is wired together at the end.
- **That "reachable and checkable" bar doesn't stop at the app's first route.** It's a standing rule for every later issue too: any screen, modal, drawer, or form an issue adds needs its own working entry point in the UI by the time that issue is done (see Phase 4's Success Criteria rule on this) — a stubbed trigger if the "real" one belongs to a later issue, never a component that only exists in code with nothing yet pointing at it.
- **Forms default to DreamerUI's `Form` component** (factory pattern, see Phase 3's UI Component Conventions) rather than a hand-rolled set of inputs — call out the exception explicitly in the TDD on the rare occasion a form's inputs genuinely don't fit that shape.
