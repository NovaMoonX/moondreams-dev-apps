# CLAUDE.md

Coding practices, styles, and norms for this repo. Every rule here applies to new code and to any PR you review or finish.

The shared rules (imports/aliases, Firestore data contracts, listeners, TanStack Query, invite/join pattern, React state, class names, Dreamer UI usage) live in `.github/copilot-instructions.md` and apply in full:

@.github/copilot-instructions.md

Per-mini-app rules live in `.github/instructions/<app>.instructions.md` (Copilot, `applyTo`) with an identical `.claude/rules/<app>.md` (Claude, `paths`); read the one for the app you are touching. This file adds the norms specific to how Claude works in this repo, plus the review checklist that `.claude/skills/finish-feature-pr` runs. When a rule appears in both places, `copilot-instructions.md` is the source of truth and this file only points at it.

## Code style

- **Functions over loose variables.** No `let` assigned across `if`/`else` branches — wrap the branching in a small function with early returns and use its result. Build values with `.reduce`/`.map`/`.filter`/`Object.fromEntries` instead of `for` loops and manual `push`/insertion. Default to `const`. Keep code compact and colocated: a helper lives next to its use, not in a new file. Don't extract a small snippet just because two or three places repeat it — keep a copy where each is used, so changing one never means untangling shared callers, and so a one-off helper doesn't become the precedent. Share only what is genuinely general and stable (a real `src/utils` function, a component with its own reason to exist).
- **Comments: default zero.** Only write one when the process doesn't make sense on its own — a hidden constraint, a workaround for a specific bug, a non-obvious invariant, or why the obvious approach isn't used. Never describe what code does, restate a name in prose, or reference a task/PR/caller. Max 3 lines, no app/file/function names. One exception: a one-line `/** */` on an exported helper that says what it provides and its hard scope limit (reference: `grantEmulatorDevAccess` in `src/lib/dev/devAccess.ts`, "…Emulators only.") is welcome. Re-audit every touched file before wrapping up.
- **No IIFEs.** Arrow callbacks passed to `.map()`, `onClick=`, `setState()` are fine.
- **Never `setState` synchronously in a `useEffect` body** (or during render to mirror props). Derive during render, or set state only inside async/subscription callbacks.
- **Generate ids with `generateUuid` (`@/utils`), never `crypto.randomUUID()` directly:** it doesn't exist on the plain-HTTP LAN and share links, so a bare call crashes there.
- **Firestore fields are `T | null`**, required keys, explicit `null` — never optional `?:` or `undefined`.
- **Date-only vs. instant.** A date picked with no time (`fromDateInputValue`) is UTC midnight: display it with `formatDateUTC`/`getDayLabel`, never `formatDate`/`formatDateTime`/local getters, and treat a date-only end date as covering its whole day (`endDate + 1 day`) when comparing an instant against it. An instant (`startAt`, `createdAt`) displays in local time. Full rule in `copilot-instructions.md` ("Know which of the two kinds of time value a field is").
- **Trip-relative time** (Waypoint events and stays: a day offset + floating `"HH:mm"`, zone = the item's override or the trip's default) is a third kind of time value: never store it as a timestamp, and convert it to an instant only through `zonedDateTimeToEpoch` for reminders and "now" checks. Full rule in `copilot-instructions.md`.
- **A range input preserves its range:** moving a start moves an already-chosen end by the same amount (`DateRangeField`, `shiftRangeEnd`).
- **Deprecate, don't delete, superseded Firestore fields** — keep them in the type with `@deprecated` and write `null` going forward.
- **Shared utils are general** (name and parameters free of app entities, in `src/utils`); app-specific ones live in that mini-app's `utils/`. A component or hook a second mini-app needs moves to central `src/components`/`src/ui`/`src/hooks` in that PR; never import across `src/apps/*`.
- **Money is integer minor units** (`priceCents`), formatted at the edge. Per-member private data nests under `apps/{appId}/<root>/{uid}/…` with a one-line uid rule (full rules in `copilot-instructions.md`).
- **Copy is product-forward**: warm, friendly user-facing text (subtext, empty states, descriptions), not spec-literal. A label written for the default stays true in every state it can reach (a split among some people is not "the whole group"), and an example uses a real day from this trip.
- **Labeled hairline dividers use `@/components/SectionDivider`** (label centered, optional `trailing`), never a hand-rolled `flex-1 border-t` pair. A list that splits into named groups (Waypoint's timeline days, A-List's "Opening this week" / "Everything else") separates them with it.
- **Hover and floating UI uses Dreamer UI's `Popover`/`DropdownMenu`/`Drawer`, not a hand-rolled `group-hover` panel.** Check the library before building a floating surface; if a quirk of the component truly blocks it, say why in the PR (A-List's day peek is a `hoverable` `Popover` whose inline-block wrapper is stretched over the calendar cell).
- **A UI primitive with no app entities in its props lives in `src/components` from the first use, not only once a second app wants it** (`SearchInput`, `SectionDivider`, `Subview`, `MoneyInput`). Before writing a component, ask whether its props mention a movie, trip, cat or household; if not, it is shared. Keep only entity-aware pieces (a `ViewingRow`, a `PriorityBadge`) in the app.
- **Shared components first, then Dreamer UI.** Before hand-building any UI behavior, check `src/components`/`src/ui` and then Dreamer UI's components for one that already does it (copy-with-feedback is `CopyButton`, not a `Button` + state + timeout). No raw `<button>`/`<input>`/`<select>`/`<textarea>`. Use `AppToggle` (`@/components/AppToggle`), never Dreamer UI's raw `Toggle`. Use a toggle for anything that takes effect immediately (live filter, "show archived"); use `Checkbox` only for form-staged values and to-do-style completion marks.
- **A control never flashes a border when focus or selection leaves it.** Two causes, both fixed centrally: a pointer-focused control keeps its focus outline/ring and fades it out when focus moves on (a pill you tapped, a card the drawer handed focus back to on close), and a deselected pill fades its old selected fill and border while the next one fades in. `src/index.css` removes the outline/ring for `:focus:not(:focus-visible)` at every width (keyboard focus keeps its cue), and `Pill` carries `!transition-none`. Never reintroduce a focus cue that shows for the pointer, never re-enable the transition in a theme, and give any hand-styled toggled chip or `Button` used as an option `transition-none`. It bit Waypoint, then A-List's filters and watchlist cards.
- **A toggled icon-button state (liked, upvoted, saved, bookmarked) is shown by filling the icon, not by switching the button's `variant`.** Keep the button on one neutral `variant` (usually `tertiary`) and conditionally add `fill-current` plus a matching `text-*` color class to the icon itself, e.g. `className={join('h-3.5 w-3.5', isUpvoted && 'fill-current text-primary')}`. Reference: the upvote button in `EventSuggestionsList.tsx`.

## Forms and CRUD conventions

- **Form and section titles are plain nouns**, whatever the container (modal, drawer or subview): "Expense", "Visit", "New cat", never CRUD verbs ("Add Expense", "Edit Visit"). The same title serves create and edit. The verb belongs on the primary action button and on a destructive confirm dialog's title.
- **Submit buttons disable until required fields are valid** (`onDataChange` + `isValid`); no required-field asterisks.
- **Truly optional extras use a "+ Add X" reveal link** (or a chip, see `AddFieldChips`), not "(optional)" in the label. Keep the "+" for short labels (a verb and a noun or two); a sentence-like label ("Can't find it? Add it by title") gets no plus. A detail the user's path depends on is not an optional extra: it is asked ("A journey detail is asked, not tucked away", under Design & UX). An action beside a section title is vertically centered on the title line (`SectionHeader` does this).
- **An always-mounted form container (a modal, drawer or subview shown via `isOpen`) needs `key={editingX?.id ?? 'new'}`** at its call site, or its internal state goes stale across edit targets. One that's conditionally rendered should be keyed on whatever identity it depends on.
- **Deletes go through `useActionModal().confirm(...)` with `destructive: true`** — never a bare `window.confirm` or no confirmation.
- **A form's delete is an icon-only trash button, bottom-left of the footer**, in a modal or in a subview's pinned footer alike. Use the shared `DeleteIconButton` as `leftActions` of `ModalFooterActions` (`rightActions` holds Cancel then the primary submit). Never a "Delete" text button in the Cancel/Save row. References: `ChecklistItemFormModal.tsx`, `ExpenseFormModal.tsx`.
- **Dreamer UI's `Form` reads `initialData` once.** To change its values from code, remount it with a key that changes on every change (a counter, so re-picking the same item still remounts).
- **An add step confirms itself and never loses typing.** A form clears its field only after the write succeeds (a failed save keeps what was typed), and a successful add either returns to the list, where the new row is the confirmation, or says what was added; never clear the field and stay silent. A cap or uniqueness check that lives only in the UI is stated as such in `TECHNICAL.md`.
- **A form's footer must be able to pin.** `ModalFooterActions` is a direct child of the form grid (a wrapper around it is `contents`), or its `sticky` has no room to move; check that Cancel and the primary action are on screen the moment a sheet opens at 390×844. A Dreamer UI `Select` filters its own list: never mirror its search into state to filter or cap the options yourself (`onSearch` doesn't fire when it resets).
- **Fields inside a `Modal` use `variant='outline'`:** `solid` is the card's own color in dark mode and the field disappears. A modal step whose list grows puts its input above the list and caps the list's height, so the field and footer never fall below the fold at 390×844.
- **Pending-request/invite features ship both sides together**: owner approve/decline *and* requester cancel/withdraw (delete their own doc, destructive confirm).
- **Static option lists** (dropdown options, role/status allowlists) are declared once in the mini-app's `constants.ts` (never `types.ts`, which is types only) and imported everywhere. Reference: `src/apps/waypoint/constants.ts`.

## Design & UX

How Waypoint's phone-first redesign works; new features follow it. Design the phone screen first, then widen.

- **A private surface and its shared look-alike point at each other.** A shared control whose name resembles a private one (a split pill "Just me" against a private "Just for me" list) says in one line that everyone still sees it and where the private version lives, and a private section sits where it is found without scrolling past a long shared one (above the dues, not below).
- **Extra lines on a repeated card are checked for height, width and zero.** A chip or line added to every totals card is looked at for the height jump when the first one appears, at 320px and with five-figure amounts, and renders only where its amount is above zero; prefer one compact line over a chip plus two more. A section header with an action reuses `SectionHeader`'s layout (title row `h-10`, action centered on it) with a 40px hit area, and a "Show all" link under a list is `px-0!` with a 40px hit area so it sits on the rows' left edge.
- **A search field looks like one:** filled (`variant='solid'`), roomy (`h-12`), rounded, with a leading magnifier (A-List's `SearchInput`); an outline-only input with just a placeholder is too subtle. A search screen shows results or exactly one empty state, never both: decide from the typed text, not the debounced value (so clearing the field hides stale results at once), and show "Searching…" while the debounce or request lags behind the text.
- **Design for 5 and for 50.** Every list a person can grow (members, days, categories, groups, stacks, items) is checked at both sizes before a screen is done. Pick-one and pick-several rows are `PillGroup`/`MultiPillGroup`, which already scale: on a phone they show two rows with "Show all N" (and the count selected), and past 12 options they add a search. Never hand-roll a pill row over data that can grow. A name that can be picked or created ("New group", a stack, a category) is `PickOrCreate` (`@/components/forms/PickOrCreate`): a dashed "New" pill first, existing names after, nothing preselected so the person has to act, never a `Select` with a hidden "Add new…" entry. The same goes for tables, strips and menus: ask what the phone screen looks like with 30 of everything, and cap or collapse it rather than letting the sheet grow. A collapsed pill group unfolds only for keyboard focus, never on a tap, so choosing an option never moves the fields below it.
- **Playful by default.** Rounded shapes, pills over radios and tab strips, an emoji where it carries meaning, warm copy. Pick-one and pick-several rows of a few options are `PillGroup`/`MultiPillGroup` (`@/components/PillGroup`), never a `Select` of three to six items; a `Select` stays for long lists. A mini-app can round everything at once by raising `--radius-md` and up in its theme class (Waypoint) instead of setting `rounded` on each control. A mini-app may theme itself further (A-List's AMC red lives in its own `a-list.css`).
- **No "Back home" in a mini-app's page.** Home is the header's home icon (sm and up) or the avatar menu's "Home" (phones), shown whenever the route isn't `/`. Only a mini-app's landing page (`AppEntryFallback`) says "Back home".
- **An image from a URL that can stop working (a cover, a hotlinked photo) is `@/components/FallbackImage`, never a bare `<img>`.** On a load error it renders its `fallback` prop, or nothing, so the page never shows a broken-image icon or alt text; give it a themed `fallback` where a hole would look wrong. Keep the failed-state look in that one component so every app changes together.
- **A list that can grow gets a search from 8 rows** (`SearchInput`, `@/components/SearchInput`; Waypoint's `LIST_SEARCH_THRESHOLD`): members, checklist items and the like, filtering by title, name and note, with one muted line when nothing matches.
- **Alignment is not optional.** Everything in a column shares one left edge, and a tappable row's text and trailing chevron sit on the same left and right edges as the section header above it (a row `Button` that sets `px-0` needs `px-0!` where a theme pads full-width buttons; measure `row title x == header x` and `chevron right == container right` in the browser): a line that starts with an emoji or icon gets a fixed-width icon column (`w-5 shrink-0 text-center`) so its text lines up with its siblings, never an inline emoji that shifts the first word. Counts and dates in a row are a `whitespace-nowrap` badge or their own cell, never a trailing `· ×3` that wraps onto a line alone. Containers pad consistently, and a row with nothing to say is omitted rather than filled with a placeholder like "No format preference". Check every new screen at narrow phone width before calling it done. A label that comes from data (a theater name) truncates or wraps inside its container and never sets the container's width. An inline link inside a sentence keeps the sentence's line box (no vertical padding or min-height) so its text sits on the same baseline as the words beside it. Touch targets are at least 40px tall (star rows, icon-only buttons, help icons, inline links), adjacent icon buttons get a gap, and only the destructive one turns red. A badge or button inside a tile that sits three across is the emoji plus one word on a phone ("🎯 Set", "🏆 Met") and the full phrase from `sm` up ("🎯 Set a goal", "🏆 Goal met"), with the full phrase in an `aria-label`: a badge that wraps to two lines is the bug. Keep such a control compact and give it a 40px hit area with a pseudo-element, not padding. A help icon on a tile sits in its top-right corner on a phone, never trailing a label that can wrap away from it. Icon-only buttons (a footer's trash, an invite icon, a back chevron, a floating pill's swap button) are 40×40, and a color class on a `variant` can be silently beaten by it, so set a destructive color with `!` (or the `tertiary` variant) and check the computed color.
- **Text and controls sit inside their shape.** The rounder a field, select, button or pill, the more its text needs inset from the curve: a theme that raises the radius raises the horizontal padding of every field with it (Waypoint's `waypoint.css` does it for inputs and select triggers), and any label, hint or row that belongs to a field lines up with the field's text edge, not its border. Leading icons get their own padding so they never overlap the text. Check a new radius on an input, a select, a textarea and a pill before calling it done.
- **Colors are checked where they land, in light and dark.** For every themed color, look at it on a filled button, a selected pill, a badge, a highlighted card, a tinted banner and the outline button beside them. Content on a strong fill has to stay readable: emoji don't recolor and dark text on a dark fill disappears, so a selected pill among emoji options is a soft tint with a primary outline, not a solid primary fill. Parts of one control (icon, label, border) come from one color. A color that is fine on a button but overwhelming across a whole screen (every card button the same strong fill) is too loud for the app's primary: pick quieter and let the accent do the shouting. An app's accent surfaces (a highlighted card, a banner) use its `accent` tokens, never raw palette utilities, so a re-theme is a CSS edit.
- **A separator only separates items on the same line.** A "·" between two facts is hidden (`max-sm:hidden`) or replaced by the line break wherever they stack, so it never dangles at the end of a line.
- **Content that grows doesn't push its actions to the bottom.** If a list can get long (members, requests, items), the action that adds to it lives in the header beside the title, never after the list. Then ask what the screen looks like with 5 and with 50 of everything.
- **A name promises only what happens.** "Invite" says a message goes out; when someone is only set up ahead of time and nothing is sent, the action is "Add" and the copy says no email is sent.
- **Waypoint's tone is business casual:** utility with a little style, soft blues and a warm accent, corners between formal and playful. Keep cute emoji (💌, 🎉) off utility surfaces such as invitations and confirmations; use them where they carry meaning (event types, roles).
- **Layout switches.** Swap components with `useMediaQuery().isBelow('sm')`; pure reflow uses `sm:` classes.
- **Phone shell.** A trip's bottom nav is only Overview / Timeline / Expenses (`TripBottomNav`). Every other section (`TRIP_SUBVIEW_LABELS`: Members, Stays, Rentals, Before the Road, Ideas) is a `Subview` reached *from Overview* by an entry point (a count pill in `TripEntryPoints`, or a chevron row like `StaysEntry`) — never a new bottom-nav slot. Its title is the section's own `SectionHeader` title, its back closes to Overview, and the id goes in `TRIP_SECTION_TABS` so `?tab=` works. Desktop shows the same section as a `TabsList` tab.
- **Overview is the phase-aware hub.** Show what needs action *now* (pre-trip: ideas, checklist, album; live: today's check-ins and pickups, weather, the day's agenda). Things that change minute to minute (what is happening now, what is next) don't take a place in the page: they float as a pill over every main screen (`NowPill`), with one button to swap Now and Up next and a tap for the details, so the static hub stays short and the rest of the trip stays in reach. One emphasized surface at a time; everything else is a quiet row. A floating pill resets any peek ("Up next") when the live event changes, keeps a visible affordance on its tap target, and the entries a live trip needs at a glance (members, checklist, stays, rentals) share one row at the top.
- **Pick the container by the content, phone first.** Judge every form on a phone (390×844), where it is mostly used. **Modal:** a handful of simple inputs that fit the screen without scrolling in every state the form can reach (a title and two or three fields, a code, a quick confirm) and that don't grow as they're filled in. **Drawer:** the default for anything bigger that is a form or a quick action: create/edit with several sections, a form whose fields reveal, a row's actions and read-only detail of unpredictable length (notes, a breakdown). It rises over the screen it came from, so the person keeps their place, and it swipes away. Forms use `@/components/FormSheet` (a tall drawer on phones, a modal from `sm` up, footer pinned). **Subview:** a search, a sequence the user leaves through its own back control, or a page-sized task where even a tall drawer would feel cramped (decide case by case; Waypoint's event form is the one that does). A full-screen takeover loses the context a drawer keeps, so don't reach for it just because a form is long. **Never a long form in one modal.** A modal taller than ~70% of the phone viewport (about 590px), or that scrolls, in any state it can reach, is a bug: move it to a drawer rather than making it more compact, and measure it (see Validation). The question to ask: would this scroll on a phone, and does the person need to see what is behind it?
- **Never stack an overlay on an overlay:** whatever continues inside an open drawer swaps its content in place with a "‹ Back" link, and a drawer whose action opens a form or another container closes first (Modify on an item's details drawer closes the drawer, then opens the editor). A destructive confirm is the only thing allowed on top. A help icon's explanation is a `Tooltip` with its arrow on a computer (`HelpTip`), never a `Popover` (its `--color-tooltip` tokens in `src/dreamer-ui.css` are the popover's surface, so it matches a `Popover`), and a modal on a phone, or a `Tooltip` there too (`noModal`) when the icon sits inside a drawer, modal or subview. A short, plain note (a sentence or two) is always the tooltip at every size, opening above the icon (`placement='top'`, `noModal`) and sitting to the right of the label it explains, never a paragraph under the field; the modal is for text long enough to need a title and "Got it". A text link that explains something ("How premium savings work") opens a modal at every size; `HelpTip` captures Escape so the modal closes alone. An auto-opening prompt (an invitation, a welcome) yields to the prompt the current route asks for (`?inviteCode=`, `?trip=`), and two auto-opening overlays are never mounted at once. A form sheet's footer sits flush with the bottom edge in the sheet's own surface color, the sheet is capped near 92% of the screen so the page behind shows, and nothing scrolls into view beneath the footer (check at the end of a scroll, in both themes).
- **On a phone the primary action is the widest control in the footer.** `ModalFooterActions` gives the right group the row's leftover width, so Cancel and a trash icon stay compact; a secondary submit ("Add another flight") moves above the footer on phones instead of becoming a fourth control. A details drawer has one primary button (plus at most one secondary) in its footer; the other actions go in one `bg-muted/50` block in its body. An add-a-note prompt in a drawer is a visible row, not a link, and its Save and Cancel are full-size.
- **Chrome gets out of the way while scrolling, but back navigation never does.** The site header slides away on phones while scrolling down and returns on the first scroll up (`useHideOnScroll`, which sets `data-site-header` on `<html>`). A mini-app's own header with a back control sticks on phones: use `@/components/StickyAppBar` (back control, quick actions, and a one-line title that slides in beside the back control once it has stuck) or, for any other row, the `sticky-app-bar` class (`src/index.css`), which sticks below the site header while it shows and takes the top of the screen when it is gone. Never hand-roll a sticky header, and tweak this behaviour only in those two places. Subview headers use the class; an overlay subview's title row is pinned inside its own scroller. The `<body>` must never be a scroll container (`overflow-x: clip !important` in `index.css`, because Dreamer UI modals leave `overflow: auto` on it), or `sticky` silently stops working.
- **Time-triggered helpers are quiet, not pop-ups.** When the clock makes a shortcut relevant (A-List's "add from trailers" bubble around a showing), show a small nudge where the user already is, anchored to existing chrome, that folds into a chip so it can be reopened; never open a drawer, modal or screen on its own. An auto-opening overlay is for something that needs an answer now (the Seen prompt).
- **Subviews: a full-page screen that takes over the mini-app, built on the central `@/components/Subview` (A-List's `AddSubview` and `MembershipSettingsSubview`, Waypoint's nested sections and its long forms).** Use one when the task is a search, when its results change height as the user works so a drawer or modal would jump, when it is a sequence the user should leave only through its own back control, or when it is a page-sized form no drawer fits (see "Pick the container by the content"). `Subview` is a generic container: `<Subview title onClose>` draws the header (round back button, large `text-2xl` noun title, which sets it apart from the smaller section subheaders; no rule beneath it), scrolls to the top, and gives the screen its own history entry, so the phone's back gesture or the browser's back closes the subview instead of leaving the page beneath it (`useSubviewHistory`). Pass an `onClose` that just unmounts it; never navigate on its behalf. A `SectionHeader` whose title equals the subview's drops its own title and keeps a subtitle-and-action row beneath the header (use the subtitle, not a badge, for a count like "2 members"), so keep the two titles identical or the screen shows a double header. The header holds only the back button and the title: keep CTAs out of it and in the content, where the section puts them. It hides the app's tab bar and brings its own way out, so the app shell's navigation is never involved. The screens underneath stay mounted (hidden) so filters, scroll-independent state and the selected day survive the trip. A step inside it changes the back button's label ("Back to results") instead of adding a second control. **A subview opened from deep inside a screen** whose parent can't swap its own content out (the event form from a card's Modify) is an `overlay` subview (`<Subview overlay>`, or `FormScreen`): the same header and history entry on a full-screen layer over screens that stay mounted, with the form's `ModalFooterActions` pinned to the bottom so Save is always in reach. Don't use one for a quick detail view, a short list or a confirm (drawer/modal), and never open a modal or drawer on top of one except a destructive confirm.
- **Overlays.** Phone → `Drawer`, desktop → `Popover`/`DropdownMenu`, confirmations → `useActionModal` at every size, forms → the container that fits them ("Pick the container by the content"); a form that is a drawer on phones is a modal from `sm` up. Build the content once and render it in both. In a drawer's action list, group related actions in one `bg-muted/50` block, keep other actions standalone, and put destructive ones last in red. An auto-opening question that needs a typed answer follows the same split: a drawer on phones, a `Modal` from `sm` up, with its primary and escape actions kept on screen.
- **Screens and cards.** Every section opens with `SectionHeader` (title + at most one primary CTA, hidden when not permitted). Overview rows use the small uppercase eyebrow `h3`. One border per card — tint to group, never nest — with flat `divide-y` rows inside. An empty list is one muted line with the CTA in the header; an Overview entry with nothing yet is a tappable prompt row.
- **Indicators.** Leading round icon chip with a soft tint; counts only when `> 0`, via `IconBadge` or the `bg-primary` pill.
- **Create and edit ask little up front.** Required essentials only (usually a title plus the one field that makes it real), then the journey details as visible questions, then truly optional extras behind a "+ Add X" reveal (or a chip row) with a "Remove X" undo. Two-up fields use `grid gap-3 sm:grid-cols-2`. The footer stays on one row, with Cancel on the left edge (`ModalFooterActions` `cancelAction`) and the primary action alone on the right, so labels stay short (Cancel / Save / Add / Post). An action takes its name from its context: a section already titled Stays has "Add", not "Add stay". Go multi-step only when step two is truly secondary. A form that outgrows a phone modal becomes a drawer, never a taller modal.
- **A journey detail is asked, not tucked away: in forms and everywhere else.** When the app's answer, another screen or the next step depends on a detail the user usually has in hand at that moment (what a ticket cost, who's coming, when they land, whether it's booked, where the car goes back), don't bury it behind a "+ Add X" link, a chip or a collapsed section. Ask it as a visible question with `Pill` answers ("🎟️ Already bought your ticket?" → "Yes, I paid" / "Not yet"), reveal its fields in place on yes, default to the quick answer so fast adds stay fast, and keep a later way to fill it in. The test: if skipping it leaves something else wrong or empty (an Overview filtered to "my events", a savings total), it is a journey detail. Outside forms the same holds: a step the user's path needs (their own arrival and trip home) is a visible, skippable card, not a menu item. "+ Add X" and chips are only for truly optional extras.
- **Copy** reads like a friend: notification sentences ("Alex added Lunch at Salt Creek"), warm one-line prompts, concrete placeholders ("Dinner at Ichiran").
- **Never offer an action the user can't complete.** Gate every button, reveal and submit with the same predicate as the rule behind it (`canAddIdea`, with `now` from `useNow()`), hide it rather than show-then-fail, and when state can flip while a form is open, disable its submit and say why. A menu with nothing in it for this person (a Commenter's trip actions) is not rendered at all.
- **Trip-phase gating has two clocks.** Display uses the viewer's local day (`getTripStatus`); write gating uses UTC to match `firestore.rules` (`roleGuards.ts`: `hasTripStarted`). A UI gate and the rule that backs it use the same one — never mix them.

## Product

How a feature should serve the person using it; the review agents and your own iteration add lasting rules here (fold them in, don't append).

- **A document fills the form; it doesn't create records.** Reading a confirmation lives inside the form of the thing it describes (a flight, a stay, a rental), only for structured logistics, and never as a general "upload" button. It fills the real fields, says what it couldn't read, and the person reviews and edits them before saving; a checklist of proposed entries is no review. It touches only the fields it read: it never wipes what the person already typed or chose, a field it couldn't read stays empty so the "couldn't read" note is true, a date far outside the trip counts as unread, and it says an AI reads the file and that it isn't saved. Errors from the service never reach the screen verbatim; one warm sentence does, and the detail is logged.
- **Ask once, then keep it one tap away.** An invitation opens as a modal when the person lands (Join, Not for me, Close), and after Close it waits behind an icon button beside the entry point; it is never a banner that pushes the page down. "Once" is per person, not per tab: remember what was shown in `localStorage` keyed by uid. A standing invitation is hidden once the person is on the trip by any path (approve, join code, join by invitation), and an offered Join is never one the rules would refuse.
- **Ask for a permission on a tap, with the reason beside it.** Location, notifications and the like are never requested on load; the button says what it is for ("Use my current location") and the feature works without it (a zip code, skipping the step).
- **A hand-off to a third party is a hand-off, not a checkout.** The app shows what it can, opens the other site in a new tab straight from the tap, says before leaving what to look for there, and welcomes the person back with one question that has everything it already knows filled in. It never takes payment. Every state of the step before it has a way forward (a failed or empty lookup still offers the other site, and never says "you can still do X" in a view where X is impossible), and every route into the same record (Mark paid, Edit, the welcome-back question) is seeded from the same known data.
- **A prompt asks for exactly what it says.** If it says it needs two things, it shows two inputs and the rest as one summary line with a "Change" link; a disabled primary action says why. A feature that depends on an earlier choice (theater, then showtimes) explains the dependency where the choice is made and preselects when only one option is valid.
- **Copy about someone else's screen is hedged until checked.** What a third party's checkout shows (a fee line, a $0) is verified against the real thing or worded so it holds either way.
- **A lookup that fills a form never holds it up.** It has a short timeout, a failure is never cached as an empty answer, and the fallback is the person's own wording. An offer after saving (an expense, a task) is limited to things that usually cost something and never opens for free time.
- **A stopgap says so quietly.** When a simpler version ships before the real one (a typed theater name until AMC's search is ready), say it once in the field's hint line ("Soon you'll be able to search…"), never a banner or badge, and store the data in the shape the real version will fill in so nothing is migrated later.
- **Optional setup is skippable and quiet afterwards.** A last-step "Skip", then one muted line where it matters, never a repeating prompt or an auto-opened overlay.
- **Say what the app can't know.** When a source only covers part of the story (prices for upcoming days only, a fee it never exposes), the screen says so plainly and falls back to a form, instead of showing a blank or a guess.
- **Lay numbers out; don't let them wrap.** A worked example or equation ("$22 − $16 = $6") is a few short rows, one operand per line with its label, never a sentence the browser breaks mid-equation. Check it at 390px. Group related figures on a line deliberately and keep each group `whitespace-nowrap`.
- **A control never hides an action in a repeated gesture.** Tapping the current value to clear it, a long-press that deletes, a double-click that resets: none of these can be discovered, so give the action its own visible control (a rating's "Clear" link). A hover preview looks different from the committed state (lighter, not the same fill) and shows nothing when it equals the current value; a hovered control still answers the keyboard (arrow keys), so focus it on mouse enter.
- **Explain any number the person can't derive.** A stat that isn't self-evident (savings, a weekly count that resets on a day) carries a help icon that opens the explanation (`HelpTip`), and a field that asks for something unexpected says why beneath it.

## Designing a mini-app's look

Each mini-app may have its own personality on top of the shared playful base; A-List (`src/apps/a-list`) is the reference.

- **Theme through tokens, in one stylesheet.** The app owns `<app>.css` that overrides Dreamer UI's semantic color tokens (`--color-primary`, `secondary`, `accent`, `muted`, `border`, light and dark) on a class (`html.a-list-theme`) that a `useXTheme()` hook adds to `<html>` only while the app is mounted, so portaled modals and drawers pick it up and other apps are untouched. Components then use semantic classes (`bg-primary`, `bg-accent`), never raw palette colors, so a later re-theme is a CSS edit.
- **Pick the metaphor first and let it name everything.** A-List is "AMC and the theater": red primary, marquee-gold accent, ticket/popcorn/film emoji, copy like "Did you catch it?". Write the metaphor, palette roles and shape language (what is round, what is a pill) in the app's rules file.
- **Shared pieces stay general; app flavor lives in the app.** Pills, badges (`PriorityBadge`, `ViewingStatusBadge`), tiles (`StatTile`) and subviews are built in the app's `components/shared` or `components/shell` against the app's tokens. Anything a second app needs moves to `src/components` in that PR.
- **Write the app's rules down.** Add `.github/instructions/<app>.instructions.md` and the identical `.claude/rules/<app>.md` (see `a-list.instructions.md` for the shape: theme, shape language, emoji meaning, subview use, anything app-specific like a money input). Update them whenever the app's design vocabulary changes, in the same PR.
- **Where a visual rule lives: the narrowest place that covers everyone who needs it.** Behaviour every app should get lives once in `src/index.css` (the `sticky-app-bar` utility, the `body` overflow clip that keeps `sticky` working, the 92dvh cap on every drawer so the page shows through at the top, `color-scheme` for native widgets); a rule that is the app's look (palette, radii, field padding, selected-pill tint, how tappable text reads) lives in `<app>.css` on the theme class; a one-off stays on the component. Never patch a cross-app problem in one app's stylesheet, and never push one app's taste into the global one. Before adding a central rule, grep `index.css` and `dreamer-ui.css` for the one that already exists; after changing one, re-drive another app's drawer, header and form and add a row to the PR's regression table, because a global change reaches every mini-app.
- **Text color is part of the theme, not per component.** Body and row text is `text-foreground`; blue (the primary) is for real links (a URL, a place) and for filled-button labels. A tertiary or ghost button is a quiet action or a tappable row, so the app's stylesheet sets its text to the normal color (Waypoint's `button.text-primary:not([class*='bg-'])` rule in `waypoint.css` is the one to copy), instead of every call site adding `text-foreground`. A new mini-app starts its `<app>.css` with the tokens, the radius/padding inset, the selected-pill tint and this rule, then checks a screen of rows in light and dark for blue that isn't a link. A button inside a drawer is never transparent or borderless against the sheet: give an action row a visible edge (`border-border`) or a `bg-muted/50` block.
- **Badge contrast: status badges are soft tints (`secondary`, `accent`, `muted`) or outlines.** A solid fill (`primary`, `warning`, `destructive`) is for the one thing on the screen that needs action, never for a status that repeats down a list. Check a badge's text against its fill and neighbors; if it jumps out more than the title beside it, soften it.
- **Colors must not fight their emoji.** Don't put an emoji on a background of its own hue (🔥 on red); give it a neutral or complementary chip. Solid red/primary fills are for the one primary action on a screen, not for status chips. A selected pill is solid, so it carries no emoji of a matching hue (a 📍 on red); the section's label carries the icon instead.

## State, data, and performance

- **Firestore `onSnapshot` lives in `store/listeners/`** as `startXListener(key, onChange)`, started once from a `useXSync` hook at the mini-app's top-level page (reference: `useNineLivesSync.ts`, `useWaypointSync.ts`). Never inside a leaf/tab/panel component's `useEffect`. The exception is a genuinely modal-local, ephemeral subscription that no other component reads (e.g. a single invite-code lookup); keep it a small hook and mount it via a conditionally-rendered, keyed component so it subscribes once per key. A listener for an optional enhancement (theaters) never feeds the fatal load-error screen: its failure degrades only its own UI, because a rules-deploy lag or one denied collection must not lock features that work.
- **Request/response calls go through TanStack Query** (`queryOptions` factory in `src/lib/<feature>/<feature>Queries.ts` or `src/apps/<app>/queries/<resource>Queries.ts`). Key includes every param that changes the result and nothing that doesn't; `staleTime` fits how often the data changes. Writes and non-idempotent calls stay uncached.
- **`meta: { persist: true }` must earn its place.** Remove it from any query whose `queryFn` reads Firestore (Firestore's own cache already persists it) or returns secrets, tokens, or key material. Keep it on safe third-party/worker results so they work offline.
- **Performance is a design check for every mini-app, judged at scale.** Every app keeps an oversized seed fixture (Waypoint's "Big Group Reunion (scale test)" is the reference) and a feature that adds a list or per-row work is opened on it, on a phone-width page, with the dev build throttled to 4× CPU (Playwright + CDP `Emulation.setCPUThrottlingRate`), switching between the app's main tabs. A tab switch that takes over a second at 4× on the fixture, or any "Maximum update depth" or render storm in the console, is a bug. Profile before optimizing (`Profiler.start` through CDP, sort by self time): the hot spot is rarely where it looks.
- **The patterns that fixed Waypoint, to reuse:**
  - *Build once, reuse.* An `Intl.DateTimeFormat`/`NumberFormat` is built once (module-level or a `Map` keyed by its options), never per call or per row. A pure conversion called per row on every render (a time-zone offset, a trip-relative time) is cached by its inputs, or per item in a `WeakMap` when items are replaced rather than mutated (`memoizeByItem`).
  - *One pass, not per row or per pair.* Compute totals, settlements and groupings in a single walk that buckets into a `Map`, then look up; never filter the whole list inside a per-row or per-pair loop. Keep the old and new outputs identical on random data before replacing an algorithm.
  - *Memoize on stable inputs.* Derive heavy values with `useMemo` or a `createSelector` keyed on the data they read; ids derived from an object (`Object.keys(trip.members)`) are memoized on that object so downstream memos hold.
  - *One listener per key, one render per burst.* An external store that many components watch (`useUserInfo`) shares one Firestore listener per key, bumps a per-key revision so only the components showing that key re-render, and batches a burst of snapshots into one notification; `useSyncExternalStore` snapshots are O(1) and cached (`useMediaQuery` stores the breakpoint instead of calling `matchMedia` per read), and any module cache of user data is cleared on sign-out.
  - *Cap what you draw.* A list that can reach 100+ rows caps or collapses (a "Show N more", a search, a Disclosure) rather than rendering all of it. A long list grouped by day or section mounts a group only when it nears the screen (`@/components/LazyMount`, with an estimated height and the first screenful eager) and gives the group's wrapper the `defer-offscreen` utility (`content-visibility: auto`, so the browser skips style, layout and paint offscreen) with `--defer-size` set to the same estimate. `content-visibility` alone is not enough: React still builds every element, and that was the cost. Calibrate the estimate against the real height so the scrollbar barely moves.
  - *Don't tear down what the next screen needs.* A tab switch unmounts and remounts a screen's components; a shared store's listener lingers a few minutes after its last watcher leaves (`useUserInfo`), because starting 120 Firestore listeners again cost more than the render. Never start a listener per tab or per row.
  - A listener kept alive after its last watcher leaves is stopped, and its handle cleared, by the same code that clears the cached data on sign-out (and restarted for components still watching), and a failed `onSnapshot` clears its handle, so a later watcher resubscribes. `LazyMount`'s `eager` is read once: content that has mounted stays mounted when the list reorders.
  - *Keep the tap instant.* Render the new tab in a transition (`useTransition`) and move the nav at once, and wrap each big tab in `memo` so the urgent update (the nav moving) does not re-render the tab that is leaving.
  - *Closed means unmounted.* A drawer or modal's heavy body (a filter sheet with a pill per member) renders only while open.
- **A PR that touches performance says how in its body**: a `## Performance` section with the fixture, the throttle, before/after numbers for the screens switched, and what changed.
- **`useAppSelector` that builds a new array/object** (`.filter`, `.map`, spread, object literal, `[]` fallback) must pass `shallowEqual` from `react-redux` or use a `createSelector` selector. A selector that returns an existing slice or `.find(...) ?? null` is fine.
- **Pick the atomic write that fits — never write a cached document back whole.** Anything another user can change while a modal is open (`seenBy`/`dismissedBy` maps, vote or history arrays, `members`, a paid-status map, `isArchived`) is a concurrency hazard. Full rules in `copilot-instructions.md` ("Atomic writes"); the short form:
  - **Append/remove on an array** (`changeHistory`, `upvotedBy`) → `arrayUnion`/`arrayRemove`.
  - **One member's own key in a map** → `runTransaction` (read via `transaction.get`) or a dotted-path `updateDoc`.
  - **Derived from the prior value, or must hold across several documents** (role changes, approving a suggestion, a counter) → one `runTransaction` that re-reads everything it depends on and aborts with a readable message if the world changed. Network side effects (reminders, uploads) stay outside it, with cleanup if it fails.
  - **An edit form's save** → `updateDoc` with only the fields the form owns, never `setDoc` of the cached object: that silently overwrites a concurrent vote, seen-mark, or archive. Reference: `updateEvent`, `updateStay`, `markExpensePaid`.
  - **A pointer to another document** (`favoriteTheatreId`) → a transaction that confirms the target still exists, and removing the target re-points it (to another candidate, or none) in the same transaction on every surface that removes it; a dangling pointer reads as none.
  - **A prompt driven by a timestamp field** (`purchase.startedAt`) is cleared in the same write that answers it, and bounded by the item's status, so it can't re-ask after the answer or for something already over.
  - **A side effect keyed by a stored id** (a scheduled push's `trailerReminderId`) is rescheduled only when the field it derives from changed in that edit (compare with the document the transaction read), cancelled only while still ahead, and never awaited after the write: a slow or offline network must not hold the save UI.
  - A `writeBatch` is for independent writes with no reads. Thunks that only assign caller-supplied values to disjoint scalar fields need none of this. Reference: Waypoint `membershipActions.ts`.

## Firestore and Storage rules

- The rule's identity check matches the collection's real path. Shape validation covers every field on the type using the `T | null` convention. Immutable-field checks cover only truly immutable fields (id, owner/parent id, `createdBy`, `createdAt`, file metadata) — don't lock a field the UI edits.
- `storage.rules` paths mirror wherever the Firestore doc lives. `firestore.indexes.json` drops indexes for queries that no longer exist and adds any composite index a new query needs.
- Never add a global `match /{path=**}/X` rule for something scoped under an app path; prefer a body check (`resource.data.householdId == householdId`).
- Repeated assertions go in helper functions. Never put a self-referential `get()`/`exists()` in a collection's own `allow read`; use `resource.data`. Split OR-ed read predicates into separate `allow read` statements.
- Denials and atomicity are verified against the emulator (e.g. a raw REST or client-SDK write), not just by the absence of a UI button.
- **Every PR that adds/renames a field, changes who may write one, moves a path, or adds a collection updates `firestore.rules` (and `storage.rules`, indexes) in the same PR, and says so in the PR body.** Before finishing, grep the diff for each touched field and permission and confirm a rule covers it; a rule you didn't need to change is a conclusion to state, not assume.
- **Verify rules directly against the emulator before the PR is done** — sign in as each role through the auth emulator and hit Firestore's REST API (`Bearer owner` seeds fixtures): one allowed write and one denied write per role-sensitive rule you touched, including the "editor/non-member must be denied" side. Rule changes also re-run every pre-existing rule on the same collection.
- **Rules must tolerate documents written before a field existed.** On update paths read new fields with `resource.data.get('field', default)`, never `resource.data.field`; a legacy document may be backfilled only with the field's empty value (`{}`/`[]`/`null`), never arbitrary content.

## Cloud Functions

- **Third-party results are cached carefully.** Never cache an empty or null answer for the full TTL (a parsing gap would stick for weeks), round any privacy-reduced input (coordinates) on the server before the upstream call so a shared entry never depends on who populated it, and list every contract detail taken from docs alone (date formats, parameter names, paging) in the PR body as unverified: a fake server you wrote yourself doesn't verify it.
- A third-party key that can't be domain-restricted is a Functions secret behind an `onCall` (never in the browser, a response or a log); a free-tier API shared by all users gets a server-side cache and a daily budget guard. Full rule in `copilot-instructions.md`.
- **`functions/README.md` is the functions reference — keep it current in the same PR.** Adding, renaming or removing a function updates its row in the Functions table (trigger, app, purpose). A new secret or env var gets a "Secrets and config" row, and a function that caches, budgets or fetches for a user gets a per-function note. A new secret is created in production before the PR merges (CI deploys every function on merge, and a missing secret fails the whole deploy), and the PR body says so.
- **Local setup lives in scripts, not memory.** A step every developer must repeat (like building `functions/lib/` before the emulators load it, handled by the `preemulators*` hooks) becomes a `package.json` script or `pre*` hook, and the README documents the command rather than the manual step.
- A newly-added `onCall` function can deploy without its public-invoker IAM grant (symptom: browser CORS error; GCP Cloud Run request logs show a 403 on the `OPTIONS` preflight). See README's [Deployment](README.md#new-cloud-functions--cloud-run-invoker-access) section for the `gcloud run services update --no-invoker-iam-check` fix.

## Nine Lives placement

Nine Lives features are one of two shapes — check which the request actually asks for:

- **Household-level sections** rendered directly in `NineLives.tsx`, each wrapped in `DetailsDisclosure` (see `ClinicsSection.tsx`, `ExpensesSection.tsx`), stored at `apps/nine-lives/households/{householdId}/{collection}/{id}`, synced via `useNineLivesSync.ts`.
- **Cat-scoped tabs** in `CatDetailsModal.tsx`, stored at `households/{householdId}/cats/{catId}/{collection}`, synced via `useCatDetailSync.ts`.

Migrating between them means moving the collection path and updating every action/listener/selector, the rule, the Storage path, and the tab/section wiring in `CatDetailsModal.tsx`/`NineLives.tsx` at the position the request specifies (Visits, Expenses, Vet Clinics are the anchors for "under"/"at the bottom"). An entity that attaches to several cats uses `catIds: string[]` (create dedupes with `Array.from(new Set(...))`, form uses a first-position `FormFactories.checkboxGroup`, list resolves cat names, rule checks `catIds is list && catIds.size() > 0`).

## Validation

- **Typecheck with `npx tsc -b --force` (or `npm run build`)** — `tsc --noEmit -p .` checks nothing in this solution-style repo. Also run `npx eslint .`.
- **Measure every modal and form on a phone (390×844) before calling it done.** In a Playwright script, open each one in every state it can reach (a new item, an edit, each reveal switched on) and read the container's height: a modal over ~70% of the viewport (about 590px) or that scrolls moves to a drawer (or a subview when it is a search or a sequence) ("Pick the container by the content"). A form is not done because it fits on desktop.
- **Look at every new or recolored surface at full size in light and dark.** Read each screenshot for text or emoji lost on a fill, a control whose icon, label and border disagree, text pressed against a rounded edge, a label that doesn't line up with its field, and a separator left dangling after a wrap. A change to a theme token is checked on a filled button, a selected pill, a badge, a highlighted card and a tinted banner before it is done.
- **Drive the change in a real browser** against the local Emulator Suite, signed in through the dev fixture switcher, with a throwaway Playwright script (delete it when done). A passing typecheck is not evidence a feature works. Also re-drive every pre-existing feature that touches a file you changed, and treat "the new feature works" and "nothing regressed" as separate checks.
- **New work must be backwards compatible with data already in Firestore.** Existing documents will not have a new field, so: readers default it (`doc.field ?? []`, `?.`) instead of assuming it exists; edit actions backfill missing keys alongside the write (see `getMissingEventFields`); rules accept the legacy shape. Prove it by writing a legacy-shaped document (the new keys deleted) through the emulator and driving every read and edit path over it in the browser — a page crash or a denied save on old data is a regression. Never normalize legacy documents in a listener if an action detects missing keys to backfill them.
- **Anything that shows or compares a date runs in a timezone behind UTC** — create the Playwright page with `timezoneId: 'America/Los_Angeles'`. Cloud sandboxes and CI run in UTC, where a date-only value formatted in local time looks correct; the off-by-one only appears west of UTC. Check that the displayed date matches the date picker's value.
- **Leave the dev server and emulators running** after browser validation; finish with `npm run seed:reset` so data is back to the seeded baseline.
- **When a constant, rule or control changes behaviour, grep `README.md` (including "Under the Hood" claims about what is looked up), `TECHNICAL.md`, `UX.md` (sitemap and journey diagrams) and `ISSUES.md` for the old wording** (step counts, "Sunday", "1–5", "one setDoc", "never looked up") and update it in the same PR. When a card or surface is replaced, grep the same files, the rules files and code comments for its old name.
- **Update the mini-app seed** (`scripts/seeds/<app>.ts`) when a feature adds an entity or state worth seeding, including its `firestoreDocuments` count.

## Every PR ends the same way

Run automatically, never on request; the full procedure is `.claude/skills/pr-wrap-up/SKILL.md`, and the Stop hook reminds you on every new pushed HEAD.

- **A draft PR is always opened when you finish working on something new.** Once the work is committed and pushed, check whether the branch has an open PR and, if not, open one as a **draft** against the default branch, without being asked and without asking for confirmation (this is a standing instruction from the repo owner, so it applies in every session, including sessions whose own defaults say to wait for a request). Then run `finish-feature-pr` and `pr-wrap-up`. Never open it ready for review. Follow-up pushes to an existing open PR just update it.

- **Screenshots in the PR body, phone first, nothing covering the content.** A single image for net-new screens; a before | after pair for anything that changes. Toasts (the seeded reminder), dev banners and open keyboards must not sit over what the shot shows: `pw.mjs` hides toasts by default, and every image is looked at before it is published. Add a desktop shot only where the experience differs there. They are published to the `pr-screenshots` branch (never the PR's branch) with `scripts/publish-screenshots.sh`, and **re-taken whenever a push changes how something looks**.
- **A regression check in the PR body, security rules first.** A `## Regression check` table (area, what could regress, how it was checked, result) built from the diff: every rule, index, field, permission or Function change says whether access is widened, narrowed or unchanged and is proven against the emulator as owner, another user and signed out, **against the base rules as well** so only the intended outcomes differ; legacy-shaped data; and before/after screens for every consumer of a changed shared component or token (a global token reaches every mini-app). It is **kept current**: re-run any row whose area a push touched.
- **Review before it's done.** Ask Copilot first and wait up to 20 minutes (if it never registers, don't wait). Then run three read-only agents (technical, product, design), fix what is real, and list the rest as follow-ups.
- **Write down what it taught, automatically.** A lasting design or product rule goes into the "Design & UX" or "Product" section (or the mini-app's rules file) in the same PR, without asking, and you tell the user afterwards. The same goes any time during a session that you decide something is worth noting there.

## Release hygiene

Bump once per PR, in its first code-changing commit, and re-check against `origin/main` first — main may already have taken the number.
- Keep the root `README.md` and the mini-app docs current, concise, and in their existing tone.
- **The root `README.md` "Current apps" list mirrors `APP_REGISTRY`:** every app has one line (an emoji, its name, its registry description), added in the same PR that registers the app and updated whenever an app is renamed or its description changes.
- Commits and PRs end with the attribution lines the session's system reminder specifies.
