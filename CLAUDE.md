# CLAUDE.md

Coding practices, styles, and norms for this repo. Every rule here and in the files it points to applies to new code and to any PR you review or finish.

**Large or multi-issue work runs through the `orchestrate` skill, without being asked:** a task that spans more than one issue, will likely change about 1,000 lines or more, or was planned in plan mode. You (the session model) plan, brief, integrate and verify; cheaper agents in `.claude/agents/` build, check and review. The whole pipeline, from planning to merge, is `docs/conventions/pipeline.md`, and it **improves itself**: when a correction, a miss, noise or a wasted step shows a skill, hook, agent, convention or script should change, change it when you are confident and propose it to the owner when you are not (`pipeline.md` "The pipeline improves itself").

**A plan keeps the owner's mental load low.** It is a short page the owner can read in under a minute: what the person will see or be able to do, which items count (the criteria) when that matters, and only the decisions that are uncertain or risky, each a 🚩 question with your recommendation. Files, selectors, checks, verification steps and docs are yours to get right and stay out of it (owner, A-List release days: "the plan is so dense"). A plan for a follow-up covers only the follow-up: each answer and what it changes and the questions they asked, never the earlier plan or what is already built (owner, Runway cards round 3). A session that comes back in plan mode with nothing new writes a one-line plan. These rules replace plan mode's default template (no Context, Files or Verification sections), and `plan-check.sh` sends back a plan that names files or code, nests bullets or runs past 350 words. All of them are in `orchestrate` "Writing a plan".

Per-app rules live in `.claude/rules/<app>.md` (loaded by `paths` when you touch that app; `.github/instructions/<app>.instructions.md` only points there). Read the one for the app you are touching. `.github/copilot-instructions.md` is a pointer to this file and `docs/conventions/`, and keeps no rules of its own.

## Code style

- **Functions over loose variables.** No `let` assigned across `if`/`else` branches — wrap the branching in a small function with early returns and use its result. Build values with `.reduce`/`.map`/`.filter`/`Object.fromEntries` instead of `for` loops and manual `push`/insertion. Default to `const`. Keep code compact and colocated: a helper lives next to its use, not in a new file. Don't extract a small snippet just because two or three places repeat it — keep a copy where each is used, so changing one never means untangling shared callers, and so a one-off helper doesn't become the precedent. A general behaviour other apps are likely to want (a gesture, sheet, picker, formatter, storage helper) is the exception: see "Build it shared from the first use". Share only what is genuinely general and stable (a real `src/utils` function, a component with its own reason to exist). One exception: a figure one screen shows in two places (a summary line and its sheet's tile) is formatted by one function both call, so a title never disagrees with its tile.
- **Comments: default zero.** Only write one when the process doesn't make sense on its own — a hidden constraint, a workaround for a specific bug, a non-obvious invariant, or why the obvious approach isn't used. Never describe what code does, restate a name in prose, or reference a task/PR/caller. Max 3 lines, no app/file/function names. One exception: a one-line `/** */` on an exported helper that says what it provides and its hard scope limit (reference: `grantEmulatorDevAccess` in `src/lib/dev/devAccess.ts`, "…Emulators only.") is welcome. Re-audit every touched file before wrapping up.
- **`line-clamp-N` never shares an element with `block`, `flex`, `grid` or `inline`.** Each replaces the `display` the clamp needs, so the class stays and nothing clips (round 8: a collection row with two long recipe names grew to 220px). Measure it with long text, not the seeded names: the line count of the element is N.
- **No IIFEs.** Arrow callbacks passed to `.map()`, `onClick=`, `setState()` are fine.
- **Never `setState` synchronously in a `useEffect` body** (or during render to mirror props). Derive during render, or set state only inside async/subscription callbacks. A parent that needs a child's unsaved state holds the draft itself (per-thing drafts passed down), never an effect in the child that calls the parent's `setState`.
- **Generate ids with `generateUuid` (`@/utils`), never `crypto.randomUUID()` directly:** it doesn't exist on the plain-HTTP LAN and share links, so a bare call crashes there. A secret or unguessable token (a share link, a PIN) is `generateToken`, not a UUID.
- **Firestore fields are `T | null`**, required keys, explicit `null` — never optional `?:` or `undefined`.
- **Date-only vs. instant.** A date picked with no time (`fromDateInputValue`) is UTC midnight: display it with `formatDateUTC`/`getDayLabel`, never `formatDate`/`formatDateTime`/local getters, and treat a date-only end date as covering its whole day (`endDate + 1 day`) when comparing an instant against it. An instant (`startAt`, `createdAt`) displays in local time. Full rule in `docs/conventions/data-contracts.md` ("Know which of the two kinds of time value a field is"). A date-only value never reaches copy as an ISO string: summaries built at write time (a change-log line sealed into a document) format it with `formatDateUTC` before sealing.
- **Trip-relative time** (Waypoint events and stays: a day offset + floating `"HH:mm"`, zone = the item's override or the trip's default) is a third kind of time value: never store it as a timestamp, and convert it to an instant only through `zonedDateTimeToEpoch` for reminders and "now" checks. Full rule in `docs/conventions/data-contracts.md`.
- **A range input preserves its range:** moving a start moves an already-chosen end by the same amount (`DateRangeField`, `shiftRangeEnd`).
- **When the date range is what the person is acting on, show a calendar, not two date boxes.** A range that is its own question (what dates to share, which days to look at) is Dreamer UI's `Calendar mode='range'` in the flow, with a line under it that says what the range covers and "Tap the first and last day" until it has both; two `DateRangeField` inputs stay right when the range is one field among many in a form (a trip's dates). Consider the calendar wherever a screen's main job is picking days, and check it at 320px, in dark, and that a second tap on one day is a single day. Dreamer UI's `Calendar` can't start with a range selected, so a sheet that presets one keeps it in its own state, clears the calendar's selection styles and draws the range in `renderCell` (`onRangeSelect` runs inside the calendar's state update, so apply it in a microtask). (A-List's "Pick dates" share range is the reference.)
- **Deprecate, don't delete, superseded Firestore fields** — keep them in the type with `@deprecated` and write `null` going forward.
- **Shared utils are general** (name and parameters free of app entities, in `src/utils`); app-specific ones live in that app's `utils/`. A component or hook a second app needs moves to central `src/components`/`src/ui`/`src/hooks` in that PR; never import across `src/apps/*`. **A shared util, hook, component, callable or endpoint never carries one app's words:** its name, parameters, return keys, defaults, docs and error messages say nothing about a recipe, trip, cat or movie (`fetchPageContent` returns the kinds of content a caller asks for, and Pinch's own `lib/` turns them into a recipe draft). Before adding one to `src/` or `functions/`, grep the file for the app's entity names; an app-specific reading, prompt or mapping stays in that app. **Turning a typed or read value into one of a list's known options (an ingredient, a cat, a clinic, a breed, an airline), or into a custom option written like the rest, is `@/utils/optionMatchUtils` (`createOptionMatcher`, `toDisplayCase`)**: an app supplies its names, ignored words and casing and never writes its own normalizer, similarity threshold or title-casing. Before writing any `normalize*`, `match*` or casing helper, grep `src/utils` and the other apps' `utils/` for the same job; a second copy is a finding, and the copies move onto the shared one in the same PR.
- **Money is integer minor units** (`priceCents`), formatted at the edge. Per-member private data nests under `apps/{appId}/<root>/{uid}/…` with a one-line uid rule (full rules in `docs/conventions/data-contracts.md`).
- **Copy names a relationship as a relationship.** An expense is *linked to* an event, stay or rental; it does not "pay for" it, and a toast or sheet never says it does ("Linked Dinner to Pike Place Market"). Before shipping copy about two things that are connected, say out loud which one acts on the other.
- **Copy is product-forward**: warm, friendly user-facing text (subtext, empty states, descriptions), not spec-literal. A label written for the default stays true in every state it can reach (a split among some people is not "the whole group"), and an example uses a real day from this trip.
- **Labeled hairline dividers use `@/components/SectionDivider`** (label centered, optional `trailing`), never a hand-rolled `flex-1 border-t` pair. A list that splits into named groups (Waypoint's timeline days, A-List's "Opening this week" / "Everything else") separates them with it. Groups the person makes (a recipe's "For the sauce") are ordered by one pure helper every surface uses (Pinch's `groupIngredientLines`), ungrouped items first with no heading, since below a group they read as part of it; every edit the recipe's form can make is recorded in the recipe's history, moving an item between groups and renaming or removing a heading included, and an item shown away from its heading names its group only where it would be ambiguous (its ingredient sits in more than one group).
- **Hover and floating UI uses Dreamer UI's `Popover`/`DropdownMenu`/`Drawer`, not a hand-rolled `group-hover` panel.** Check the library before building a floating surface; if a quirk of the component truly blocks it, say why in the PR (A-List's day peek is a `hoverable` `Popover` whose inline-block wrapper is stretched over the calendar cell).
- **Build it shared from the first use when other apps are likely to need it, not only once a second one does.** Before writing a component, hook, util or behaviour, ask whether another app, existing or future, plausibly needs it; on a site of apps used mostly on phones, touch gestures (press and hold is `useLongPress`), sheets, pickers, formatters and storage helpers almost always do. When the chance is high, it goes in `src/components`, `src/hooks`, `src/utils` or `src/lib` with no app's words in it (`SearchInput`, `SectionDivider`, `Subview`, `MoneyInput`, `AppLogo`); when it is low, it stays in the app and nobody builds speculative helpers. A component whose props mention a movie, trip, cat or household stays in the app (a `ViewingRow`, a `PriorityBadge`) (owner: a long press was built inside Home's tile).
- **When a UI primitive is promoted to `src/components`, the app's identical copies move onto it in the same PR.** `ActionRow` is the shared tinted drawer row, and Pinch's `StartCookingRow` and `AddToShoppingRow` are thin wrappers that only supply an icon and their words, so one markup is never kept in two places to drift apart.
- **Voice for any app is `@/lib/speech`, `useSpeechCommands` and `useNaturalVoice`, never a copy of Pinch's.** `listeningMode` (the closed / waiting for a phrase / command window / kept open machine and its clocks), `readWakePhrase` (a wake phrase at the start of what was heard), `useSpeechCommands` (the recognizer with its windows, restarts, `say` and `cue`), `readAloud` (one reading function: the natural voice when ready, the browser's otherwise; every text goes through `toSpokenText` first, which writes out units, fractions, temperatures and ranges: "1/2 tsp salt" is "half a teaspoon of salt", "350°F" is "350 degrees Fahrenheit") and `NaturalVoiceOption` (the opt-in row). An app supplies its command grammar, its phrases and its words; nothing under `src/lib/speech` or those hooks names an app's entities, and `check:pinch-voice` (`speechShared.ts`) fails if it does.
- **A library component that hard-codes colours is replaced centrally, never patched per use.** Dreamer UI's `Callout` draws dark-mode palette text (`text-blue-200`) on any theme, so a light theme lost its words; the fix is one shared `InlineNotice` in the theme's tokens and an ESLint `no-restricted-imports` entry that refuses `Callout` (owner, Runway round 4; Worth the Wait had patched its own copy with `text-blue-700`). When a call site has to override a library component's colours to make it readable, that is the signal: fix it once and forbid the raw component.
- **Shared components first, then Dreamer UI.** Before hand-building any UI behavior, check `src/components`/`src/ui` and then Dreamer UI's components for one that already does it (copy-with-feedback is `@/components/CopyTextButton`, which also copies on plain-HTTP pages and says "Copied" on itself, not a `Button` + state + timeout; Dreamer UI's `CopyButton` needs the Clipboard API and hands its `Button` a Fragment). No raw `<button>`/`<input>`/`<select>`/`<textarea>`. Use `AppToggle` (`@/components/AppToggle`), never Dreamer UI's raw `Toggle`. Use a toggle for anything that takes effect immediately (live filter, "show archived"); use `Checkbox` only for form-staged values and to-do-style completion marks.
- **A pasted link's preview is `@/hooks/useLinkPreview` with `@/components/LinkPreviewCard`, in every app.** The hook settles the text (`toWebLink`, a real-looking host, typing paused), reads the page through the request the caller passes (the one the link's later reading makes, so the preview and that reading are one fetch) and returns the sanitised title, site, description and https picture only once the page is read, or `null`: a card never shows a looking-up or failed state, a skeleton or a stale page. A form whose Save waits on the read or that asks for a title when it fails uses `useLinkLookup` (the same flow, also reporting `isLooking`, `hasFailed` and `settledText`) and draws those states as form copy, not on a card. An app adds its own page request and `isEnabled`, never its own debounce, link parser or clipping. Pair it with a Clear control on the field.
- **A Dreamer UI `Button` never receives a Fragment child.** `Button` clones each element child to give it a `className`, so a Fragment (`<Button><>icon text</></Button>`, or one kept in a variable) makes React log "Invalid prop `className` supplied to `React.Fragment`" on every update, though not on the first mount, so a census taken at load misses it. Pass the pieces as separate children (`{logo}{name}`, as Pinch's `StoreHeading` and `GroupRow` do); Dreamer UI's `CopyButton` builds a Fragment child too, so Waypoint's `TripCard` and Worth the Wait's layout log it. Read the console after an update, not only at load.
- **A control never flashes a border when focus or selection leaves it.** Two causes, both fixed centrally: a pointer-focused control keeps its focus outline/ring and fades it out when focus moves on (a pill you tapped, a card the drawer handed focus back to on close), and a deselected pill fades its old selected fill and border while the next one fades in. `src/index.css` removes the outline/ring for `:focus:not(:focus-visible)` at every width (keyboard focus keeps its cue), and `Pill` carries `!transition-none`. Never reintroduce a focus cue that shows for the pointer, never re-enable the transition in a theme, and give any hand-styled toggled chip used as an option `transition-none`. Dreamer UI's `Button` ships `transition-all`, which flashed a row or card whenever focus or hover left it (the "Catch any good moments" banner, expense and agenda rows); `index.css` now sets `transition: none` on every `button[class*='transition-all']`, so a `Button` row needs no per-site `transition-none`, and a Dreamer UI `Clickable` is not needed for this. It bit Waypoint, then A-List's filters and watchlist cards.
- **A quick action doesn't lock the whole surface.** Ticking a checkbox or flipping a switch writes in the background and touches only its own control: a sheet-wide `isBusy`/`disabled` for the length of the write fades every other button and reads as a flicker. Lock the surface only for a slow, consequential action (add, link, delete). A choice that writes at once (a held line's Top up) says what it took and puts its own Undo on the line where it was made, never only a reset chip elsewhere on the screen.
- **A remote-search `Select` shows its own status and keeps what the API matched.** Dreamer UI's `Select` filters options by substring against its search box, so an accent-insensitive or fuzzy match (Montreal finds Montréal) vanishes unless it carries the typed text in its `description`; show Searching…, No city found and a failure line (which says the field is optional) as a disabled option, and reserve right padding on a clearable trigger so a long label never runs under the clear icon (`CitySelect`).
- **Text that leaves the app is safe to paste.** A profile's `displayName` can hold the person's email (the sign-in fallback), so a name containing `@` is treated as unnamed in a copy or export, user text is escaped for the format, and an action that copies says what it includes (codes, notes). Every copy goes through `copyToClipboard`, which falls back on plain-HTTP pages, and a failure never says "try again" when retrying cannot help.
- **A tap-time action reads the store through `getState()` and checks `tripId`.** Page-level subscriptions are for what the page renders; names or slices only an occasional action needs come from a small child that subscribes, or from `getState()` with each slice's `tripId` compared to the open trip, so a copy never mixes two trips.
- **A control added to a header row is checked at 320, 340, 360 and 390px, as production renders it (no dev account switcher).** Its label drops to an icon or loses its chevron on the narrowest phones, the row stays one line, its centre is measured against the viewport's, and every button in it gets a 40px hit area from a pseudo-element, not padding (`Button` `variant='base'` `size='sm'` is 28px tall; check with `elementFromPoint` above and below it; `SubviewHeader`'s back button and `SectionHeader`'s action slot give it centrally). A header add button names what it makes in every view of its screen ("New recipe", "New saved meal", "New idea": one shape and icon, the label keyed on the view shown and kept in `constants.ts`), never a bare "New".
- **A prompt that answers an action reports its failure inside itself and stays open.** The sheet that asks for a payment (or any answer) shows an abort such as "someone already marked this as paid" in itself, derives its record from the live store by id rather than holding a snapshot, and closes itself when the record has already reached the target state. When a field leaves a form, grep `TECHNICAL.md`, `UX.md` and `ISSUES.md` for its `show*Field` name.
- **A button that acts on a record from inside its editor is honest about unsaved edits.** A status flip in an editor (Mark paid) is disabled with "Save your changes first" while the form is dirty, never closes the sheet over typed edits, and shows its failure; a summary that stands for a linked thing always shows the linked thing's own name, whatever the person typed below it; and a reserved height meant for a phone's floating dropdown is scoped to the phone breakpoint (`max-sm:`).
- **An action is named by its outcome, with a one-line subtitle.** "Mark paid" that opens a form says nothing; "Add what you paid" does. A drawer's rows say what changes ("Change day, time or theater", not "Edit"), the same record never has two edits side by side, and the manual route is one tap from the guided one (A-List's Buy tickets panel ends with "Already bought it somewhere else? Add what you paid"). A button that dismisses a question says whether it comes back ("Ask me later" vs "I changed my mind"). A drawer's one primary button is the next step in the person's loop (a recipe's is "Plan it", or "Start cooking" when it is on today's plan), with Modify beside it in the footer, not in a block lower in the body.
- **A page-sized screen doesn't leave dead space under its last control on a phone.** `Subview` trims its bottom padding below `sm` (16px instead of 72px), so a form's footer sits near the bottom of the screen; larger screens keep the roomy padding. Measure the gap under the last control at 390px.
- **A repeated row action is quiet.** "Copy link" or "Open" on every row of a list that can reach ten rows is `secondary` or `tertiary`; the solid primary is the screen's one CTA. A destructive confirm over near-identical rows names what tells the target apart (dates, PIN, when it was made), not only what the rows share. A list row carries no chips at all: its actions live in what the row opens, and so do its inputs: a list whose items each have settings (a feature switch's rollout and people) is one row per item with a one-line summary of its state that opens a sheet holding them, judged as if the list held five items (owner, feature switches) (Runway's rows open the item's sheet, `ItemSheet`); the one exception is a card of something waiting on the person, which carries its next step as a button (`docs/conventions/app-look.md` "The site's own screens"). A history or log row with an action (Undo a move, Take back a payment) opens a small sheet that holds it, with a chevron on the row; never a chip or button drawn on the row (owner, Runway: an inline "Take back" read as text, and an "Undo this move" chip was "disgustingly" large on a phone).
- **A toggled icon-button state (liked, upvoted, saved, bookmarked) is shown by filling the icon, not by switching the button's `variant`** (a mode switch that is also a status, cooking mode's mic while it listens, adds a tinted edge and a pulse to the filled icon)**.** Keep the button on one neutral `variant` (usually `tertiary`) and conditionally add `fill-current` plus a matching `text-*` color class to the icon itself, e.g. `className={join('h-3.5 w-3.5', isUpvoted && 'fill-current text-primary')}`. Reference: the upvote button in `EventSuggestionsList.tsx`.

## Pattern index

One line each: the need, the pattern, where it lives. A pattern from here or a new one is described in full in `docs/conventions/design-ux.md`.

- **Look the pattern up before designing anything; the index is the first stop.** Scan it, then `grep` `src/components`, `src/ui` and the app's rules file for anything it misses. If a pattern exists, use it; if you build or find a second use of something new, add it (see "Record the pattern you establish"). One line each: the need, the pattern, where it lives.
  - **Structure and navigation:** a section title with at most one CTA is `SectionHeader`, a labeled hairline between groups `SectionDivider`; a full-page screen (search, sequence, page-sized task) is a `Subview` (`overlay` from deep in a screen), a form too long for a phone modal `FormScreen`, a phone header that keeps Back on screen `StickyAppBar`; several views of one thing are tabs, one bar per screen (`Tabs variant='pills'` in an app, `UnderlineTabs` and `TabPanel` on a utility screen), many things to pick from is a list that opens its detail on a phone and a left panel beside it from `lg` (`AdminDashboard`), never stacked tab bars; an app's landing, signed-out and loading states are `AppEntryFallback`, `AuthRequiredState` and `Loading`; an app's logo anywhere on the site is `AppLogo`, and Home's phone grid of apps (press and hold for details and a star) is `design-ux.md` "Home is a phone home screen".
  - **Forms and input:** money entry is `AmountHero` (or `AmountField isHero`) and a create form is a `QuestionFlow` ("Don't make me think"); a form is a `FormSheet` (drawer on phones, modal from `sm`) with its `ModalFooterActions`, and a delete is `DeleteIconButton` plus `useActionModal().confirm`; optional extras are `AddFieldChips` (once added, rows under a heading with Remove in each row's sheet: `OptionalDetailRows`), a collapsible group of fields `FormSection`, starting points under a field `SuggestionChips`; pick one of a few is `PillGroup` (`isThin` for filters), a setting's two to four choices in one track (the menu's Theme) `SegmentedControl`, several `MultiPillGroup`, an existing name or a new one `PickOrCreate`, a day that is nearly always today `FoldedDateField`; Keep editing / Discard on every way out of typed work `useDiscardGuard`; a form's unsaved work survives the phone closing the app with `useFormDraft` + `useKeepFormDraft` and `DraftRestoredNotice`; a row's short money and dates `formatCentsShort` and `formatDateShortUTC`; an immediate on/off is `AppToggle`; money is `MoneyInput`, a date `DateInput`, a date range `DateRangeField`, a city `CitySelect`, a place `PlaceAutocompleteInput`, a time zone `TimezoneSelect`, a guided way in vs starting fresh `MethodPicker` (emoji or icon), a link with a preview `LinkAttachField`, a photo `PhotoPicker`, a rating `StarRating`, the way out of a search or picker that lacks what the person means ("Can't find it? Add your own") `CantFindItButton`, a centered accent pill under the results and never a text link.
  - **Reading a receipt:** `@/lib/receipts` is the one reader for every app: `extractReceiptFromFile` turns a photo, screenshot or PDF into a `ReceiptReading` (merchant, kind of purchase, address, date and time, currency, line items with quantity and unit price, subtotal, tax, fees, discount, the tip charged, the tips the bill suggests, total; integer cents, caps in the prompt, `normalizeReceiptReading` settles the answer). It draws nothing: each app shows and uses the reading in its own screens (Waypoint's `ReceiptSplitScreen` splits it between people). A failed AI reading's sentence is `getAiReadFailureMessage` (`@/lib/firebase/aiFailure`). A new field every expense tool would want is added to the reader, never parsed again in an app.
  - **Lists and detail:** search a list with `SearchInput` (from 8 rows), a door to a related list a thin full-width row under that search (Runway Spend's Groups), sort it with `SortControl`, build a very long one under `LazyMount`; read-only detail of unknown length is a `DetailSheet`, and a row that would carry a sub-list shows a count and opens one; a trend over time is `TrendLineChart` (one line, an optional dotted comparison line and a guide line; `isSoft` is the quiet look a rounded app uses: no grid or axis lines, three ticks, a soft fill, an end dot; `yDomain`/`yTicks` pin the axis so a control that drives the chart visibly moves it, `marker` is a small dot with an always-visible callout and arrow, such as where the line crosses the guide; `dividers` and `band` mark a moment or a stretch of the x-axis, such as today or where something ends), a number is a `StatTile` (with a `HelpTip` when it isn't self-evident), shares of a whole (always a full circle) or progress toward a limit (a ring that may stop short) is `@/components/Doughnut` with the fixed categorical slots in `doughnutPalette.ts` (at most 6 segments, a legend list beside it carries the values), a count on an icon `IconBadge`, a calendar day `DateChip`, a person `UserAvatar` and several `AvatarStack`; a row's overflow menu is `EllipsisDropdown`, an outbound link `ExternalLinkText`, an image from a URL `FallbackImage`, copy-to-clipboard Dreamer UI's `CopyButton`, a toggled icon state a filled icon.
  - **Features per person:** a feature some people don't want is a switch in `FEATURE_GATES`, set in the admin's Features tab and read with `useIsGateOpen`, with `GatesClosedNote` at the bottom of the app's settings (`product.md` "A feature some people don't want is a switch").
  - **One app's own patterns** (a trip's phone shell, A-List's calendar and theater rows) live in its rules file: `.claude/rules/waypoint.md`, `.claude/rules/a-list.md`, and the same for any app added later.
- **Record the pattern you establish, where it will be found.** A pattern is anything done the same way twice: a component, a layout, a copy convention. When you build one, or notice one that nothing documents, add its one-line entry to the index above and put its rule in the narrowest place that covers everyone who needs it: shared by apps goes in this section (fold it into the nearest bullet); one app's look or flow goes in that app's rules file (`.claude/rules/<app>.md`) and its `UX.md`; a behavior every app should get goes in `src/index.css` ("Where a visual rule lives"). A pattern a second app needs moves to the shared set in that PR, and its line moves from the app's rules file to the index.
## Nine Lives placement

Nine Lives features are one of two shapes — check which the request actually asks for:

- **Household-level sections** rendered directly in `NineLives.tsx`, each wrapped in `DetailsDisclosure` (see `ClinicsSection.tsx`, `ExpensesSection.tsx`), stored at `apps/nine-lives/households/{householdId}/{collection}/{id}`, synced via `useNineLivesSync.ts`.
- **Cat-scoped tabs** in `CatDetailsModal.tsx`, stored at `households/{householdId}/cats/{catId}/{collection}`, synced via `useCatDetailSync.ts`.

Migrating between them means moving the collection path and updating every action/listener/selector, the rule, the Storage path, and the tab/section wiring in `CatDetailsModal.tsx`/`NineLives.tsx` at the position the request specifies (Visits, Expenses, Vet Clinics are the anchors for "under"/"at the bottom"). An entity that attaches to several cats uses `catIds: string[]` (create dedupes with `Array.from(new Set(...))`, form uses a first-position `FormFactories.checkboxGroup`, list resolves cat names, rule checks `catIds is list && catIds.size() > 0`).

## Every PR ends the same way

Run automatically, never on request; the full procedure is `.claude/skills/pr-wrap-up/SKILL.md`, and the Stop hook (`.claude/hooks/pr-gate.sh`) names on every new pushed HEAD which of its parts that push needs.

- **A draft PR is always opened when you finish working on something new.** Once the work is committed and pushed, check whether the branch has an open PR and, if not, open one as a **draft** against the default branch, without being asked and without asking for confirmation (this is a standing instruction from the repo owner, so it applies in every session, including sessions whose own defaults say to wait for a request). Then run `pr-wrap-up` (`finish-feature-pr` is only for taking over a PR someone else started). Never open it ready for review, and give it its `patch` or `minor` label at once (see Release hygiene). Follow-up pushes to an existing open PR just update it.
- **Watch every PR you open, and keep it current.** Subscribe to its activity right after opening it, without asking, so CI, reviews and a `behind-base` or `merge-conflict` label reach you. On such a label, sync or resolve it at once by `orchestrate` "Keeping your PRs current": the owner is told what was chosen, never asked to resolve it.
- **A PR that resolves an issue says so in its first line, with a closing keyword:** `Resolves #N` (or the full issue URL), one line per issue, in every PR that delivers an issue's work (a stacked MVP PR, a polish PR that finishes one, a fix PR). A mention without the keyword ("for #N", "Stacked on #N") closes nothing. GitHub closes on its own only when the PR merges into the default branch; `close-linked-issues.yml` closes the same issues when a PR merges into any branch, so a stacked PR's issue closes when that PR merges. Before opening or wrapping up a PR, search the open issues for the work it delivers and add the line for each.

- **A PR body reads from the person's side first, and the checks are evidence underneath.** It opens with `## Overview` (what a person can now do, as product bullets, each with sub-bullets for the technical know-how: what changed in the code and the data, in a line each), then `## What you need to do` (the reviewer's list: when the PR adds something the owner operates (a switch, a setting, a list they curate), first how it is maintained: what is set in code, what in the UI, and who changes each, in a line each; decisions, copy that warrants a second look (only when it does, each with why: it makes a promise, names money or could read wrong; never the full list), the few steps only a person can do before the merge, and what to try afterwards; never a step a workflow already does, see the next bullet), then `## How it works` (the architecture: data and paths, what the rules widen, narrow or leave alone, the functions, the flows), then `## Screenshots`. The regression check, performance, privacy, reviews, what was not checked, the rules written down and the journey tables follow, each in a collapsed `<details>` whose summary line carries its verdict ("Regression check: 14 rows, access widened in one"); a block with nothing to say is left out. A reviewer must know what to pay attention to without scrolling past the evidence (round 9: the owner could not tell what to look at in a 50 KB body).
- **"What you need to do" leaves out everything the workflows do.** On merge, `firebase-hosting-merge.yml` works out the version from the latest `v*` tag and the PR's `patch`/`minor` label, runs `npm ci` and the build, tags the release, then runs `fb:deploy:smart` (functions, Realtime Database rules, Firestore rules and indexes, Storage rules, and the invoker grant for new callables) **before** it deploys Hosting, then publishes the app version and deploys the Cloudflare worker when `cloudflare-worker.js` or `wrangler.toml` changed; pull requests run `check:indexes`, the Pinch and option-match checks and the version-label check, and `pr-sync-check.yml` labels every open PR `behind-base` or `merge-conflict` on each push to main and every six hours. So a PR never lists "deploy the rules first", "deploy with the client", "run `npm ci`", "deploy the functions", "deploy indexes", "open the callable", "bump the version" or "deploy the worker": say in How it works what the rules widen or narrow, and nothing else. **Every step the owner must do is something to run, not something to figure out:** a numbered list where each command sits in its own copy-paste block for the tools the owner has (the `gh` and `firebase` CLIs and Claude Code; `gcloud` only as an option with a browser fallback), or better one repo script that does every part a command can (`npm run pipeline:secrets`), and the few clicks no command can do spelled out click by click with the exact text to paste; never a bare "create the secret" (owner: "I'd like it to be as simple as possible"). What does stay is only what a person must do because no workflow can: a decision, copy that warrants a second look, a secret or env var the workflows don't have (a new Functions secret created in production before the merge, since the deploy fails without it; a new `VITE_` variable added to the merge workflow's build env and as a GitHub secret), a console setting or one-off upload, and what to try on a device afterwards. When the list would be empty, the section is just the decisions. It ends with **Decisions I made for you**: every light call the session made on the owner's behalf, each with the other option (`automerge`), left out when there were none; the "copy that warrants a second look" above is about wording to re-read, not these. Before writing it, read `.github/workflows/` and `scripts/fbDeploySmart.ts` again: if a workflow changes, this bullet changes with it.
- **Screenshots in the PR body, phone first, nothing covering the content.** A single image for net-new screens; a before | after pair for anything that changes. Toasts (the seeded reminder), dev banners and open keyboards must not sit over what the shot shows: `pw.mjs` hides toasts by default, and every image is looked at before it is published. Add a desktop shot only where the experience differs there. They are published to the `pr-screenshots` branch (never the PR's branch) with `.claude/skills/pr-wrap-up/scripts/publish-screenshots.sh`, and **re-taken whenever a push changes how something looks**.
- **A regression check in the PR body, security rules first.** A `## Regression check` table (area, what could regress, how it was checked, result) built from the diff: every rule, index, field, permission or Function change says whether access is widened, narrowed or unchanged and is proven against the emulator as owner, another user and signed out, **against the base rules as well** so only the intended outcomes differ; legacy-shaped data; and before/after screens for every consumer of a changed shared component or token (a global token reaches every app). It is **kept current**: re-run any row whose area a push touched.
- **Screenshots and the review agents run whenever the diff meets a trigger** (a visible change, a new callable, rule, write path or third-party contract, non-obvious logic), and a failing environment (emulators won't start) is solved with a throwaway harness page, never skipped: see `.claude/skills/pr-wrap-up/SKILL.md` ("What triggers each part").
- **Review before it's done, sized to the PR.** S, M or L by changed lines and the areas touched (`orchestrate` "Sizing the review"): the `validator` agent always, Copilot's 20-minute window from M up, the technical, product and design reviewers as the change needs, and for an L PR one reviewer per shard plus `lead-reviewer`. Fix what is real and list the rest as follow-ups.
- **Every PR has a status comment.** One `📋 Status` comment, rewritten in place after each push and review, says what must be done before merge, what should be, the next moves and where the PR sits among the app's planned issues (`orchestrate` "The PR status comment"), so the owner reads one comment to know where the PR stands.
- **Every work round ends with the same card.** The last reply of a round (work done, not a plan) closes with, in this order: every 🚩 still open, restated even if an earlier message said it, a decision phrased as a question with its options and a link to each option's screenshot, then every ⚠️ still true, then the light calls made on the owner's behalf this round under **Decisions I made for you** (each with the other option, `automerge`; left out when there were none), then each PR touched as one line in stack order (bottom first: number, one-line state, CI), then this round's screenshots as links, then a link to the admin dashboard's Pipeline (`https://apps.moondreams.dev/admin?view=pipeline`, live, answerable from a phone) with the pinned "📥 Owner inbox" issue after it as the fallback, both holding the same across every session. Nothing the owner must act on lives only higher up in the chat (owner, "what now" between sessions). Read the inbox issue before writing the card: a 🚩 it still shows for this session is either restated or closed in its PR's status comment, never reported as "nothing waiting". A 🚩 line is a question with a `?` when the owner answers it and a plain statement when it is a step they do (the dashboard ticks a statement off and asks for a reply only to a question); a merge clears the dashboard's 🚩s for that session, so after a merge restate only what still needs the owner, never what the merge settled. **A session works on its own PRs and questions only.** Another session's PRs, questions and findings (seen in the inbox or the PR list) are never pulled into this session's work, summaries or cards, and are mentioned only when they bear on this work (a file both change, a PR this one builds on, a merge or deploy this one waits behind in the merge line); when the owner answers another session's question here, say once which session and PR it belongs to and offer to pass it on, without acting on it (owner: "we don't mention or pull in context from another session"). **Every PR or issue named in a reply, a status comment or a PR body is a clickable link** (`[#564](https://github.com/<owner>/<repo>/pull/564)`), never a bare number (owner: "560 is not hyperlinked").
- **Write down what it taught, automatically.** A lasting design or product rule, or a pattern worth reusing (add it to the Pattern index), goes into the narrowest `docs/conventions/` file (or the app's rules file) in the same PR, without asking, and you tell the user afterwards. **The review agents (`.claude/agents/`, procedure in `docs/conventions/agents.md`) are revised without being asked, whenever you are confident a change makes reviews catch more or flag less noise**: every moment of feedback is the signal to re-evaluate them (the owner reports a problem a review passed, corrects a choice, rejects a finding, or you find a bug after a review), and each revision is an audit of the whole section (sharpen, merge, replace, delete), never an append, by the procedure at the top of that file, in the same turn as the work that showed it.

## Release hygiene

- **Never edit `SITE_VERSION`; label the PR instead.** The site version is worked out at merge: the deploy workflow takes the latest `v*` git tag, adds a patch (or a minor when the merged PR carries the `minor` label), bakes it into the build and tags the commit after the deploy succeeds. Every PR carries exactly one label, `patch` (fix or small tweak) or `minor` (feature; finishing an in-progress feature PR is `minor`), and the `PR version label` check fails without it. Set it when you open the PR (`issue_write` update with `labels`) and change it if the PR's scope changes. Local builds read `dev`.
- Keep the root `README.md` and the app docs current, concise, and in their existing tone.
- **A vendored third-party asset (an icon set, a font, a dataset) keeps its licence beside it** and says where it came from: a `NOTICE`/`LICENSE` file in the same folder, the licence outcome stated in the PR that adds it, and an attribution row in the app where the licence requires one. Confirm the licence before committing the asset, and say plainly in the PR what could not be checked from the sandbox. A third-party binary a feature sends to browsers (a WebAssembly build) is the same: name any copyleft inside it (eSpeak NG is GPL-3.0 inside the natural voice's phonemizer), say it where the person turns the feature on, and leave the decision to ship it to the owner in the PR.
- **A production problem that took real digging is written into the root README's "Troubleshooting" section** in the same PR that fixes it (symptom, cause, fix, how to tell it apart), including what is only a hypothesis and what the person did on their device beforehand. Temporary diagnostics (a debug panel, extra logging) are removed in that PR or the next.
- **A new app follows the New app checklist (`docs/conventions/new-app.md`)** (registry, route, the `useTrackAppUsage` hook and its Cloud Function finder, state, rules, seed, docs). Adding an app means walking that list, not only the registry.
- **The root `README.md` "Current apps" list mirrors `APP_REGISTRY`:** every app has one line (an emoji, its name, its registry description), added in the same PR that registers the app and updated whenever an app is renamed or its description changes.
- Commits and PRs end with the attribution lines the session's system reminder specifies.
