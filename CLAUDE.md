# CLAUDE.md

Coding practices, styles, and norms for this repo. Every rule here applies to new code and to any PR you review or finish.

The shared rules (imports/aliases, Firestore data contracts, listeners, TanStack Query, invite/join pattern, React state, class names, Dreamer UI usage) live in `.github/copilot-instructions.md` and apply in full:

@.github/copilot-instructions.md

Per-mini-app rules live in `.github/instructions/<app>.instructions.md` (Copilot, `applyTo`) with an identical `.claude/rules/<app>.md` (Claude, `paths`); read the one for the app you are touching. This file adds the norms specific to how Claude works in this repo, plus the review checklist that `.claude/skills/finish-feature-pr` runs. When a rule appears in both places, `copilot-instructions.md` is the source of truth and this file only points at it.

## Code style

- **Functions over loose variables.** No `let` assigned across `if`/`else` branches — wrap the branching in a small function with early returns and use its result. Build values with `.reduce`/`.map`/`.filter`/`Object.fromEntries` instead of `for` loops and manual `push`/insertion. Default to `const`. Keep code compact and colocated: a helper lives next to its use, not in a new file. Don't extract a small snippet just because two or three places repeat it — keep a copy where each is used, so changing one never means untangling shared callers, and so a one-off helper doesn't become the precedent. Share only what is genuinely general and stable (a real `src/utils` function, a component with its own reason to exist). One exception: a figure one screen shows in two places (a summary line and its sheet's tile) is formatted by one function both call, so a title never disagrees with its tile.
- **Comments: default zero.** Only write one when the process doesn't make sense on its own — a hidden constraint, a workaround for a specific bug, a non-obvious invariant, or why the obvious approach isn't used. Never describe what code does, restate a name in prose, or reference a task/PR/caller. Max 3 lines, no app/file/function names. One exception: a one-line `/** */` on an exported helper that says what it provides and its hard scope limit (reference: `grantEmulatorDevAccess` in `src/lib/dev/devAccess.ts`, "…Emulators only.") is welcome. Re-audit every touched file before wrapping up.
- **`line-clamp-N` never shares an element with `block`, `flex`, `grid` or `inline`.** Each replaces the `display` the clamp needs, so the class stays and nothing clips (round 8: a collection row with two long recipe names grew to 220px). Measure it with long text, not the seeded names: the line count of the element is N.
- **No IIFEs.** Arrow callbacks passed to `.map()`, `onClick=`, `setState()` are fine.
- **Never `setState` synchronously in a `useEffect` body** (or during render to mirror props). Derive during render, or set state only inside async/subscription callbacks. A parent that needs a child's unsaved state holds the draft itself (per-thing drafts passed down), never an effect in the child that calls the parent's `setState`.
- **Generate ids with `generateUuid` (`@/utils`), never `crypto.randomUUID()` directly:** it doesn't exist on the plain-HTTP LAN and share links, so a bare call crashes there. A secret or unguessable token (a share link, a PIN) is `generateToken`, not a UUID.
- **Firestore fields are `T | null`**, required keys, explicit `null` — never optional `?:` or `undefined`.
- **Date-only vs. instant.** A date picked with no time (`fromDateInputValue`) is UTC midnight: display it with `formatDateUTC`/`getDayLabel`, never `formatDate`/`formatDateTime`/local getters, and treat a date-only end date as covering its whole day (`endDate + 1 day`) when comparing an instant against it. An instant (`startAt`, `createdAt`) displays in local time. Full rule in `copilot-instructions.md` ("Know which of the two kinds of time value a field is").
- **Trip-relative time** (Waypoint events and stays: a day offset + floating `"HH:mm"`, zone = the item's override or the trip's default) is a third kind of time value: never store it as a timestamp, and convert it to an instant only through `zonedDateTimeToEpoch` for reminders and "now" checks. Full rule in `copilot-instructions.md`.
- **A range input preserves its range:** moving a start moves an already-chosen end by the same amount (`DateRangeField`, `shiftRangeEnd`).
- **When the date range is what the person is acting on, show a calendar, not two date boxes.** A range that is its own question (what dates to share, which days to look at) is Dreamer UI's `Calendar mode='range'` in the flow, with a line under it that says what the range covers and "Tap the first and last day" until it has both; two `DateRangeField` inputs stay right when the range is one field among many in a form (a trip's dates). Consider the calendar wherever a screen's main job is picking days, and check it at 320px, in dark, and that a second tap on one day is a single day. Dreamer UI's `Calendar` can't start with a range selected, so a sheet that presets one keeps it in its own state, clears the calendar's selection styles and draws the range in `renderCell` (`onRangeSelect` runs inside the calendar's state update, so apply it in a microtask). (A-List's "Pick dates" share range is the reference.)
- **Deprecate, don't delete, superseded Firestore fields** — keep them in the type with `@deprecated` and write `null` going forward.
- **Shared utils are general** (name and parameters free of app entities, in `src/utils`); app-specific ones live in that mini-app's `utils/`. A component or hook a second mini-app needs moves to central `src/components`/`src/ui`/`src/hooks` in that PR; never import across `src/apps/*`. **A shared util, hook, component, callable or endpoint never carries one app's words:** its name, parameters, return keys, defaults, docs and error messages say nothing about a recipe, trip, cat or movie (`fetchPageContent` returns the kinds of content a caller asks for, and Pinch's own `lib/` turns them into a recipe draft). Before adding one to `src/` or `functions/`, grep the file for the app's entity names; an app-specific reading, prompt or mapping stays in that app. **Turning a typed or read value into one of a list's known options (an ingredient, a cat, a clinic, a breed, an airline), or into a custom option written like the rest, is `@/utils/optionMatchUtils` (`createOptionMatcher`, `toDisplayCase`)**: an app supplies its names, ignored words and casing and never writes its own normalizer, similarity threshold or title-casing. Before writing any `normalize*`, `match*` or casing helper, grep `src/utils` and the other apps' `utils/` for the same job; a second copy is a finding, and the copies move onto the shared one in the same PR.
- **Money is integer minor units** (`priceCents`), formatted at the edge. Per-member private data nests under `apps/{appId}/<root>/{uid}/…` with a one-line uid rule (full rules in `copilot-instructions.md`).
- **Copy names a relationship as a relationship.** An expense is *linked to* an event, stay or rental; it does not "pay for" it, and a toast or sheet never says it does ("Linked Dinner to Pike Place Market"). Before shipping copy about two things that are connected, say out loud which one acts on the other.
- **Copy is product-forward**: warm, friendly user-facing text (subtext, empty states, descriptions), not spec-literal. A label written for the default stays true in every state it can reach (a split among some people is not "the whole group"), and an example uses a real day from this trip.
- **Labeled hairline dividers use `@/components/SectionDivider`** (label centered, optional `trailing`), never a hand-rolled `flex-1 border-t` pair. A list that splits into named groups (Waypoint's timeline days, A-List's "Opening this week" / "Everything else") separates them with it. Groups the person makes (a recipe's "For the sauce") are ordered by one pure helper every surface uses (Pinch's `groupIngredientLines`), ungrouped items first with no heading, since below a group they read as part of it; every edit the recipe's form can make is recorded in the recipe's history, moving an item between groups and renaming or removing a heading included, and an item shown away from its heading names its group only where it would be ambiguous (its ingredient sits in more than one group).
- **Hover and floating UI uses Dreamer UI's `Popover`/`DropdownMenu`/`Drawer`, not a hand-rolled `group-hover` panel.** Check the library before building a floating surface; if a quirk of the component truly blocks it, say why in the PR (A-List's day peek is a `hoverable` `Popover` whose inline-block wrapper is stretched over the calendar cell).
- **A UI primitive with no app entities in its props lives in `src/components` from the first use, not only once a second app wants it** (`SearchInput`, `SectionDivider`, `Subview`, `MoneyInput`). Before writing a component, ask whether its props mention a movie, trip, cat or household; if not, it is shared. Keep only entity-aware pieces (a `ViewingRow`, a `PriorityBadge`) in the app.
- **When a UI primitive is promoted to `src/components`, the app's identical copies move onto it in the same PR.** `ActionRow` is the shared tinted drawer row, and Pinch's `StartCookingRow` and `AddToShoppingRow` are thin wrappers that only supply an icon and their words, so one markup is never kept in two places to drift apart.
- **Voice for any mini-app is `@/lib/speech`, `useSpeechCommands` and `useNaturalVoice`, never a copy of Pinch's.** `listeningMode` (the closed / waiting for a phrase / command window / kept open machine and its clocks), `readWakePhrase` (a wake phrase at the start of what was heard), `useSpeechCommands` (the recognizer with its windows, restarts, `say` and `cue`), `readAloud` (one reading function: the natural voice when ready, the browser's otherwise; every text goes through `toSpokenText` first, which writes out units, fractions, temperatures and ranges: "1/2 tsp salt" is "half a teaspoon of salt", "350°F" is "350 degrees Fahrenheit") and `NaturalVoiceOption` (the opt-in row). An app supplies its command grammar, its phrases and its words; nothing under `src/lib/speech` or those hooks names an app's entities, and `check:pinch-voice` (`speechShared.ts`) fails if it does.
- **Shared components first, then Dreamer UI.** Before hand-building any UI behavior, check `src/components`/`src/ui` and then Dreamer UI's components for one that already does it (copy-with-feedback is `@/components/CopyTextButton`, which also copies on plain-HTTP pages and says "Copied" on itself, not a `Button` + state + timeout; Dreamer UI's `CopyButton` needs the Clipboard API and hands its `Button` a Fragment). No raw `<button>`/`<input>`/`<select>`/`<textarea>`. Use `AppToggle` (`@/components/AppToggle`), never Dreamer UI's raw `Toggle`. Use a toggle for anything that takes effect immediately (live filter, "show archived"); use `Checkbox` only for form-staged values and to-do-style completion marks.
- **A pasted link's preview is `@/hooks/useLinkPreview` with `@/components/LinkPreviewCard`, in every app.** The hook settles the text (`toWebLink`, a real-looking host, typing paused), reads the page through the request the caller passes (the one the link's later reading makes, so the preview and that reading are one fetch) and returns the sanitised title, site, description and https picture only once the page is read, or `null`: a card never shows a looking-up or failed state, a skeleton or a stale page. A form whose Save waits on the read or that asks for a title when it fails uses `useLinkLookup` (the same flow, also reporting `isLooking`, `hasFailed` and `settledText`) and draws those states as form copy, not on a card. An app adds its own page request and `isEnabled`, never its own debounce, link parser or clipping. Pair it with a Clear control on the field.
- **A Dreamer UI `Button` never receives a Fragment child.** `Button` clones each element child to give it a `className`, so a Fragment (`<Button><>icon text</></Button>`, or one kept in a variable) makes React log "Invalid prop `className` supplied to `React.Fragment`" on every update, though not on the first mount, so a census taken at load misses it. Pass the pieces as separate children (`{logo}{name}`, as Pinch's `StoreHeading` and `GroupRow` do); Dreamer UI's `CopyButton` builds a Fragment child too, so Waypoint's `TripCard` and Worth the Wait's layout log it. Read the console after an update, not only at load.
- **A control never flashes a border when focus or selection leaves it.** Two causes, both fixed centrally: a pointer-focused control keeps its focus outline/ring and fades it out when focus moves on (a pill you tapped, a card the drawer handed focus back to on close), and a deselected pill fades its old selected fill and border while the next one fades in. `src/index.css` removes the outline/ring for `:focus:not(:focus-visible)` at every width (keyboard focus keeps its cue), and `Pill` carries `!transition-none`. Never reintroduce a focus cue that shows for the pointer, never re-enable the transition in a theme, and give any hand-styled toggled chip used as an option `transition-none`. Dreamer UI's `Button` ships `transition-all`, which flashed a row or card whenever focus or hover left it (the "Catch any good moments" banner, expense and agenda rows); `index.css` now sets `transition: none` on every `button[class*='transition-all']`, so a `Button` row needs no per-site `transition-none`, and a Dreamer UI `Clickable` is not needed for this. It bit Waypoint, then A-List's filters and watchlist cards.
- **A quick action doesn't lock the whole surface.** Ticking a checkbox or flipping a switch writes in the background and touches only its own control: a sheet-wide `isBusy`/`disabled` for the length of the write fades every other button and reads as a flicker. Lock the surface only for a slow, consequential action (add, link, delete).
- **A remote-search `Select` shows its own status and keeps what the API matched.** Dreamer UI's `Select` filters options by substring against its search box, so an accent-insensitive or fuzzy match (Montreal finds Montréal) vanishes unless it carries the typed text in its `description`; show Searching…, No city found and a failure line (which says the field is optional) as a disabled option, and reserve right padding on a clearable trigger so a long label never runs under the clear icon (`CitySelect`).
- **Text that leaves the app is safe to paste.** A profile's `displayName` can hold the person's email (the sign-in fallback), so a name containing `@` is treated as unnamed in a copy or export, user text is escaped for the format, and an action that copies says what it includes (codes, notes). Every copy goes through `copyToClipboard`, which falls back on plain-HTTP pages, and a failure never says "try again" when retrying cannot help.
- **A tap-time action reads the store through `getState()` and checks `tripId`.** Page-level subscriptions are for what the page renders; names or slices only an occasional action needs come from a small child that subscribes, or from `getState()` with each slice's `tripId` compared to the open trip, so a copy never mixes two trips.
- **A control added to a header row is checked at 320, 340, 360 and 390px, as production renders it (no dev account switcher).** Its label drops to an icon or loses its chevron on the narrowest phones, the row stays one line, its centre is measured against the viewport's, and every button in it gets a 40px hit area from a pseudo-element, not padding (`Button` `variant='base'` `size='sm'` is 28px tall; check with `elementFromPoint` above and below it; `SubviewHeader`'s back button and `SectionHeader`'s action slot give it centrally). A header add button names what it makes in every view of its screen ("New recipe", "New saved meal", "New idea": one shape and icon, the label keyed on the view shown and kept in `constants.ts`), never a bare "New".
- **A prompt that answers an action reports its failure inside itself and stays open.** The sheet that asks for a payment (or any answer) shows an abort such as "someone already marked this as paid" in itself, derives its record from the live store by id rather than holding a snapshot, and closes itself when the record has already reached the target state. When a field leaves a form, grep `TECHNICAL.md`, `UX.md` and `ISSUES.md` for its `show*Field` name.
- **A button that acts on a record from inside its editor is honest about unsaved edits.** A status flip in an editor (Mark paid) is disabled with "Save your changes first" while the form is dirty, never closes the sheet over typed edits, and shows its failure; a summary that stands for a linked thing always shows the linked thing's own name, whatever the person typed below it; and a reserved height meant for a phone's floating dropdown is scoped to the phone breakpoint (`max-sm:`).
- **An action is named by its outcome, with a one-line subtitle.** "Mark paid" that opens a form says nothing; "Add what you paid" does. A drawer's rows say what changes ("Change day, time or theater", not "Edit"), the same record never has two edits side by side, and the manual route is one tap from the guided one (A-List's Buy tickets panel ends with "Already bought it somewhere else? Add what you paid"). A button that dismisses a question says whether it comes back ("Ask me later" vs "I changed my mind"). A drawer's one primary button is the next step in the person's loop (a recipe's is "Plan it", or "Start cooking" when it is on today's plan), with Modify beside it in the footer, not in a block lower in the body.
- **A page-sized screen doesn't leave dead space under its last control on a phone.** `Subview` trims its bottom padding below `sm` (16px instead of 72px), so a form's footer sits near the bottom of the screen; larger screens keep the roomy padding. Measure the gap under the last control at 390px.
- **A repeated row action is quiet.** "Copy link" or "Open" on every row of a list that can reach ten rows is `secondary` or `tertiary`; the solid primary is the screen's one CTA. A destructive confirm over near-identical rows names what tells the target apart (dates, PIN, when it was made), not only what the rows share.
- **A toggled icon-button state (liked, upvoted, saved, bookmarked) is shown by filling the icon, not by switching the button's `variant`** (a mode switch that is also a status, cooking mode's mic while it listens, adds a tinted edge and a pulse to the filled icon)**.** Keep the button on one neutral `variant` (usually `tertiary`) and conditionally add `fill-current` plus a matching `text-*` color class to the icon itself, e.g. `className={join('h-3.5 w-3.5', isUpvoted && 'fill-current text-primary')}`. Reference: the upvote button in `EventSuggestionsList.tsx`.

## Forms and CRUD conventions

- **Form and section titles are plain nouns**, whatever the container (modal, drawer or subview): "Expense", "Visit", "New cat", never CRUD verbs ("Add Expense", "Edit Visit"). The same title serves create and edit. The verb belongs on the primary action button and on a destructive confirm dialog's title.
- **Submit buttons disable until required fields are valid** (`onDataChange` + `isValid`); no required-field asterisks. When a row is what blocks the submit, the pinned footer says what to fix as a link to that row, which scrolls to it and focuses it.
- **Truly optional extras use a "+ Add X" reveal link** (or a chip, see `AddFieldChips`), not "(optional)" in the label. Keep the "+" for short labels (a verb and a noun or two); a sentence-like label ("Can't find it? Add it by title") gets no plus. A detail the user's path depends on is not an optional extra: it is asked ("A journey detail is asked, not tucked away", under Design & UX). An action beside a section title is vertically centered on the title line (`SectionHeader` does this). **Fields a record normally has are not extras:** a recipe's servings, times, photo, description and steps are visible sections of its form, never chips at the bottom.
- **An always-mounted form container (a modal, drawer or subview shown via `isOpen`) needs `key={editingX?.id ?? 'new'}`** at its call site, or its internal state goes stale across edit targets. One that's conditionally rendered should be keyed on whatever identity it depends on.
- **Deletes go through `useActionModal().confirm(...)` with `destructive: true`** — never a bare `window.confirm` or no confirmation. **An act that is undone for a few seconds asks no confirm:** taking one line off a shopping list, clearing what you've bought or tossing a box raises an Undo toast instead (guarded against a double tap); a whole record keeps its confirm, and a confirm names everything that goes with it (a recipe's cooks and notes), offering to hide instead when hiding keeps something the person made.
- **A form's delete is an icon-only trash button, bottom-left of the footer**, in a modal or in a subview's pinned footer alike. Use the shared `DeleteIconButton` as `leftActions` of `ModalFooterActions` (`rightActions` holds Cancel then the primary submit). Never a "Delete" text button in the Cancel/Save row. References: `ChecklistItemFormModal.tsx`, `ExpenseFormModal.tsx`.
- **Dreamer UI's `Form` reads `initialData` once.** To change its values from code, remount it with a key that changes on every change (a counter, so re-picking the same item still remounts).
- **`SummaryEditor` focuses its field when it opens, and a date or number field has no text selection to set:** focus it, never call `setSelectionRange` on it (it throws on those input types).
- **An add step confirms itself and never loses typing.** A form clears its field only after the write succeeds (a failed save keeps what was typed), and a successful add either returns to the list, where the new row is the confirmation, or says what was added; never clear the field and stay silent. A cap or uniqueness check that lives only in the UI is stated as such in `TECHNICAL.md`.
- **A form or add opened on behalf of another record says so.** Show "For {event}" while it applies a link, prefill what the context knows, never let a field (private) silently detach it, and toast what was added and to what when the sheet it came from closes. A form opened from a drawer returns to it, showing the result (the drawer is the hub), and a new record's add lands on its own drawer, whose primary is the next step. A row of corner tabs is checked at 320px at 100% and with slightly larger text: on a phone each tab is the emoji plus one short word (full phrase in `aria-label`), and an emphasized state is a soft tint plus a visible border, never quieter than its neutral sibling.
- **A settings form that fills a page (not a sheet) pins its status and Save row to the bottom of the screen** (`sticky bottom-0` at the end of the form, `bg-background/90` with `backdrop-blur`), because its fields can run past a phone screen and "unsaved changes" must stay in sight.
- **A form's footer must be able to pin.** `ModalFooterActions` is a direct child of the form grid (a wrapper around it is `contents`), or its `sticky` has no room to move; check that Cancel and the primary action are on screen the moment a sheet opens at 390×844. A Dreamer UI `Select` filters its own list: never mirror its search into state to filter or cap the options yourself (`onSearch` doesn't fire when it resets).
- **Fields inside a `Modal` use `variant='outline'`:** `solid` is the card's own color in dark mode and the field disappears. A modal step whose list grows puts its input above the list and caps the list's height, so the field and footer never fall below the fold at 390×844.
- **One scroll area per surface: a fixed header, and only the list scrolls beneath it** (a column cap never sits below its own header plus the list's floor, or the sheet stops short and the list ends up under the footer; under about 500px of height the sheet body is the one scroller, and a filter chip with its own ✕ gets no Clear beside it: from two chips a quiet "Clear all" chip, never a link). The text above a list and its search field sit in a `shrink-0` header, never overlaid on the list (no `sticky` over rows: a drawer body's own padding lets rows slide through the gap above it); the list is the one scroller below. In a `DetailSheet`/`Drawer` that means a column `flex max-h-[max(12rem,calc(92dvh-22rem))] flex-col` (the `22rem` leaves room for the drawer's title and footer) with a `min-h-0 flex-1 overflow-y-auto` list, so the drawer's own body never scrolls. Content shared between a drawer (phones) and a popover (desktop) applies its cap on the popover side only. Check it with the sheet open: the drawer body's `scrollHeight` equals its `clientHeight`, exactly one descendant scrolls, and scrolling the list never moves the header. **A capped list keeps a floor of about three rows** (`[@media(max-height:800px)]:min-h-36`) and its cap counts every line of the header above it: measure the list's `clientHeight` at 375×667 and 320×568, where it is never 0 (the drawer body may scroll a little there, the accepted fallback, rather than a list nobody can see).
- **A search's results inside a `Modal` are capped (a `max-h` with scroll, about four rows) and measured at 320px with the most the API can return,** so the field and footer never move or fall off the screen as results arrive; Enter in such a field never submits the form around it. A picker hosted in a sheet takes its cap from the shared picker (`ItemSearch` `isCapped`), never one of its own per host (round 8: two hosts missed it, and their whole drawer scrolled after typing at 667px). A range's two boxes keep a visible caption after they are filled in (a placeholder is not a label).
- **Pending-request/invite features ship both sides together**: owner approve/decline *and* requester cancel/withdraw (delete their own doc, destructive confirm).
- **A row action that creates or removes a record has an in-flight guard.** Its row is disabled until the write settles (a planned meal's "Mark as cooked", the same row in the recipe drawer's ⋯ More), so a second tap during the acknowledgement lag can't make a second record and a second Undo toast. A second deliberate action after the toast is fine. A row removed from a list the person is tapping through stays in place, struck through and saying what happened ("Taken off your list"), until the sheet closes, so the next tap never lands on the row that slid up.
- **Static option lists** (dropdown options, role/status allowlists) are declared once in the mini-app's `constants.ts` (never `types.ts`, which is types only) and imported everywhere. Reference: `src/apps/waypoint/constants.ts`.

## Design & UX

How Waypoint's phone-first redesign works; new features follow it. Design the phone screen first, then widen.

- **A form opens with the one question that fills in the rest, and reveals in stages.** If an answer can pre-fill the form (what an expense pays for), ask it first and show nothing else until it is answered; a picked answer shows as a short summary with "Change" instead of the fields it filled. Then show only the essentials (who it is for, how much) put only truly optional extras behind "Add to this X" chips (day, group, note). A state with its own consequences (paid or unpaid) is never a field of the details form, add or edit: adding offers a second submit above the footer ("Add and mark paid") for the common case, and later changes are their own action with their own small modal. A two-way switch on a field (total or per person) is a quiet link beside its label, not a pair of pills. Two steps and a long form are both worse than this: never show every field at once. A choice that reshapes the form (shared or private) does it in place and carries over what was typed; never tell the person to close the form and start another, and keep a private option inside the same form with one line saying only they see it. A private section sits where it is found without scrolling past a long shared one (above the dues, not below).
- **A drawer's one text box is focused once the drawer has settled** (a ref and a short timer: `autoFocus` loses to the drawer container taking focus); print `document.activeElement` after opening. It takes focus on open only when it is the screen's question: a screen opened with its subject already chosen (planning a recipe from its drawer) keeps the keyboard down so the real question, the day, stays visible. A sheet whose first button is a consequential row action (Remove) gets a harmless first focus from `sm` up, a Done carrying `data-modal-action`: Dreamer UI's `Modal` focuses the first button, so Enter on open would act.
- **A phone form shows a few inputs at a time.** Many fields on screen at once reads as overwhelming and disorganized on a phone, so everything stays editable but only what is being edited is open. A growing list of rows (ingredients, steps, items) is a column of one-line summaries ("Chicken thigh · 2 lb"); tapping a row opens its inputs one row at a time: in a drawer on a phone for any row with more than one input or free text (an ingredient, a step, nutrition values), in place from `sm` up, and tapping it again or another row closes it. An editor that opens in the list it edits must be told apart from the rows around it at a glance, and a tint is not the answer: a row editor with several fields and a search (an ingredient) is a modal from `sm` instead, the phone's drawer widened (`DetailSheet`). A collapsed row says what is wrong with it ("Add an amount") instead of hiding a bad value, and a freshly added row opens itself. A sheet that fills in many records (twelve missing prices) steps through one at a time with "2 of 12", "Skip for now" and "Save and next", never a scroll of twelve sets of fields. A stepping sheet takes its defaults from context (the order from what matters most, the unit from how the recipe measures it, the store from the row before): the person's own earlier answer is not a guess, an exception to nothing-preselected scoped to a step-through. Optional extras stay behind chips. A form's basics (title, description, times) are summary rows too (`@/components/SummaryEditor`: a caption, the value, a chevron, a drawer on a phone and a popover from `sm`, each ending in Done, Enter closing it without saving the form), except that a blank new record's title editor opens by itself once so typing starts at once. Before calling a form done, count the inputs visible at 390×844 when it opens: a title, a count and the rows as one-liners, not a page of boxes, and a row's drawer shows only that row's fields. References: Pinch's `RecipeForm` and `FillInSheet`.
- **Removing a row from a form shows an undo with a visible countdown, never a silent removal.** The row goes at once and `@/components/UndoSnackbar` (over `useUndoRemoval`) floats "Removed Salt · Undo · 6" above the pinned footer, counting down, with Undo putting the row back in its place; one removal is pending at a time and the removal stands when the count ends. One act wears one glyph: an ingredient's and a step's remove are the same ✕ (a trash is for a form's whole-record delete and a drawer's red Remove row). A whole-record delete keeps its confirm dialog.

## Product

How a feature should serve the person using it; the review agents and your own iteration add lasting rules here (fold them in, don't append).

- **A document fills the form; it doesn't create records.** Reading a confirmation lives inside the form of the thing it describes (a flight, a stay, a rental), only for structured logistics, and never as a general "upload" button. It fills the real fields, says what it couldn't read, and the person reviews and edits them before saving; a checklist of proposed entries is no review. It touches only the fields it read: it never wipes what the person already typed or chose, a field it couldn't read stays empty so the "couldn't read" note is true, a date far outside the trip counts as unread, and it says an AI reads the file and that it isn't saved. Errors from the service never reach the screen verbatim; one warm sentence does, and the detail is logged. A value the source doesn't give ("to taste", "a handful") is kept as its words with no number, never invented: every total leaves it out without calling it a gap, and the form never makes the person type a number to save. A heuristic that rewrites read text (splitting "salt and pepper") fires on a signal in the text (a to-taste tail) or when every resulting part resolves to a known thing, never on shape alone, so "macaroni and cheese" stays whole.
- **Ask once, then keep it one tap away.** An invitation opens as a modal when the person lands (Join, Not for me, Close), and after Close it waits behind an icon button beside the entry point; it is never a banner that pushes the page down. "Once" is per person, not per tab: remember what was shown in `localStorage` keyed by uid. A standing invitation is hidden once the person is on the trip by any path (approve, join code, join by invitation), and an offered Join is never one the rules would refuse.

A period's total takes its qualifier from one helper (Pinch's `getGapQualifier`, behind `getPeriodCostText` and `getPeriodCostTile`): "so far" only while a gap can still be priced, "+" once every gap is on a fixed day, so a passed week's total reads "$1,805+"; its averages are over fully priced meals and need none.
- **A basis switch converts stored numbers and reinterprets only what the person typed.** Switching "per serving / per 100 g / per oz" on numbers that came from the saved ingredient shows the same nutrition in the new unit; after the person types a number it relabels what they typed and says what it saves. Two controls with the same labels never behave in opposite ways, a detail view opens on the list's basis, and a message never names a unit the person didn't type.
- **A filter that narrows beyond what its pills say states it on its active chip** ("Needs a price · in Yours"), so a scope pill it overrides never looks broken.
- **Language is plain and modest.** Copy says what a thing is or does in everyday words and never glamorizes: no "everything in one place", "all-in-one", "home base", "where X lives", "seamless", "effortless", "powerful", "unlock", "magic" or "the ultimate". A subtitle names the contents ("Your ingredients, products and stores."), an empty state says what to do next, a README opens with the problem in plain terms. This covers screens, empty states, link previews, READMEs, PR bodies and seed data; re-read every string you add for a phrase that sounds like an ad. **The account is the site's, never an app's:** one sign-in works across every mini-app, so copy about signing in says "an account" ("With an account"), never "a Pinch account" or "your Pinch login", and never promises something one app's account can't give another.
- **A label's nutrition is entered on the label's basis and viewed on the person's.** Packages state values per 100 g, per serving or per 28 g, so the form asks which ("per 100 g", "per serving", "per 28 g") and converts to the stored per-100 g value; it never forces one basis. A drawer or summary can show per serving or per 100 g with a switch, says which it is showing, and remembers the choice.
- **Rows that carry numbers let the person hide them.** A recipe, meal or ingredient list with prices or macros has one View options control (`@/components/ViewOptions`) beside its search, remembered on the device per person; hiding changes only what is shown, never what a total counts. **Lists show the least by default:** prices on, calories and macros off, with View options one tap away, and a choice already stored is kept. **Quiet is the default and depth is opt-in:** a new kind of row line starts off unless it is a decision for that row, and a View option exists for preference, never to tame a loud default. **A display choice that reaches several tabs is a switch in the app's Settings tab, and each screen it changes points there with one row:** which numbers exist (calories, protein, carbs, fat) change more than one tab, so they live once in Settings, never as a section repeated in every tab's View options and never in one tab's header. A choice about one screen's own feature (whether the Calendar draws its stat tiles) is that screen's View options, not Settings, even when it started as "a setting"; and a switch that turns a feature on or off, which a person would be surprised to find reset on another device, is saved with the account (`PinchSettings`), while the sheet's row choices (show prices) stay on the device. A choice that changes one screen's rows (show prices, show what's in stock) stays in that screen's View options. A screen the Settings choice changes has a tinted door row in its View options ("Calories and macros · Switch them on in Settings", drawn in place of the switch while the choice isn't made, and still there in another wording once it is, so the way to change it never disappears), the door closes its sheet the way a back gesture does and then switches tabs as a tap on the tab would (back from Settings goes to the Calendar, like from any tab) and puts focus on the new screen. The first number switched on in Settings also turns the lists' macros line on, so the switch shows something; later switches touch no list. A display choice kept in a saved setting changes the screen only once the save succeeds, never ahead of a write that can fail.
- **Every list that piles up has its bulk end.** After a power cut, a clean-out or a holiday, finishing a hundred rows one by one is the bug: stock, ticked items and finished history each get one action with the list's own header (not under the rows), shown only for the whole list (never while a scope chip or a search narrows it, so "all" is unambiguous), whose confirm says what it takes off and what it keeps ("keeps them in What you finished as cleared out"), that re-reads every record inside a transaction per chunk and reports the number it really changed, and whose Undo reverses only what is still as the action left it. A ticked shopping list's clear is the exception: no confirm, only its Undo, since what it takes off is what the person already bought.
- **A date is a prompt with its action, and a list a person acts on in numbers has a select mode.** A badge that says a box or package is past its date or due soon has its action in reach: one quiet tinted row above the list ("3 are past their date" with "Toss them", a confirm that names them, an Undo toast) and a **Select** mode (rows tick, a count says how many, a pinned footer offers only what applies, `Escape`/back/Cancel end it one layer at a time). Every bulk act is one planner over a re-read per chunk inside a transaction, counts what it left alone by reason ("Tossed 3 of 4 boxes · One was already finished."), and its Undo reverses only what is still as the act left it. The shared pieces are `useSelection`, `SelectionBar` and `PromptRow`.
- **The phone is not a desk: a doing screen survives the device's life.** Screen off, tab hidden, app switched, tab discarded, offline, no wake lock (plain HTTP): a countdown is a wall-clock deadline that a view re-reads on `useOnTabReturn` (a `now` kept in state by a tick is stale after the screen was off), the screen is held awake while the task runs and the line says so quietly where it can't be, an unfinished activity may keep a small per-viewer copy under `<app>:<uid>:<name>-session` in `localStorage` (written on change, expiring, cleared on completion, on leaving by choice and on sign-out through `clearViewerSessions`, offered back as a quiet row, never an overlay), and what a web page can't do (ring while the screen is off) has the nearest honest substitute the person chose, a push they turned on, cancelled when the thing is done.
- **A lookup or send the person didn't ask for each time names what it sends, and can be turned off.** An automatic web search for photos says "Searches the web with your recipe's title. Nothing else is sent." on its surface, has a switch in Settings and a quiet in-context off with an Undo when the form can't open Settings. A device permission is its own row with the reason beside its switch; per-account kind switches under it stay dimmed until it is on. A control that changes a default says where that default shows ("Your usual 4 days") and that records already made keep their values.
- **A named set of records is a record per person plus an id on the member (Sources' shape), and its word is one constant pair.** Collections ("Bulk", "High-protein") are made only where they are used, managed behind the filter's own question (never a destination tile), and a pick-one filter over a many-to-many label never claims an intersection. A suggestion is derived from the record's own numbers (never added silently, never from a partial sum; a label the data can't support is left out) and a favorite is a flag on the record with a star.
- **An opt-in is offered where the need starts, once, and asked on its own tap.** Something timed or sent later (a timer's push, a reminder) is offered as one quiet capsule at the moment it starts ("Buzz me if the screen is off · Turn on") whose small modal asks the browser on that tap and sets the device and the switch together; nothing is drawn once it is on, a refused or unsupported browser says why, and Settings stays the one place to turn it off. A page never asks for a permission on load.
- **A quantity is asked as bought, never prefilled from a plan.** The amount of something the person brought home starts empty ("How much did you buy?") and Save says why it is off; only a product's own size may prefill it, and what the plan said is a hint beside the field. A bulk or many-to-many act is a pinned footer under a Select: the label picker (Recipes' "Add to a collection") writes in chunks, reports the real count and the ones it could not change, and its Undo takes off only what the act added.
- **A flag about what is missing leaves out what the person never tracks.** "Not in your pantry" and its share skip the shop staples (salt, water, oil) while nothing of them is tracked, so a partly tracked store never makes every recipe look short.
- **What the app records about a member's behaviour (last visit, which apps they open) is stored where only that member and the admin can read it,** never on a profile document other members can read, and never described as "admin-only" without checking the collection's read rule.

## Security and privacy

What may leave a person's account, and how. Applies to anything that goes outside the signed-in member's own screen: a share link, an export, a copy to the clipboard, a push or email, a link preview.

- **Decide field by field what leaves, and write the list down.** Before building anything that shows a member's data to someone else, list every field it could carry and mark each *include* or *exclude* with a reason, and put that list in the PR body under `## Privacy`. Personally identifying data (name, email, uid, photo, anything that says whose it is), money (prices, fees, totals), opinions (ratings, notes) and precise location are excluded unless the feature is only useful with them. A calendar share carries a movie's title, poster, time, runtime, rating, format and theater, and nothing else.
- **Allowlist, never spread.** Copy fields out by name into a new object, in the client that builds it and again in whatever serves it. Never send a stored document, `{ ...doc }` or "everything except" a few keys: the next field someone adds to the type would leave with it. The serving function runs the stored copy through the allowlist again, so an old or hand-edited document can't carry more, and a copy that fails it is `null`, never a partial object (half a meal says something else).
- **A public link is unguessable and read through a function.** The id has at least 128 bits from a CSPRNG and is never a counter, a timestamp or `generateUuid`: `generateToken` (`@/utils/idUtils`) when the client creates the record, and **minted by the function with `crypto.randomInt` whenever a function writes it** (Pinch's recipe and meal links), so a client can never choose a weak one. Firestore rules give a visitor nothing; a Cloud Function reads with the admin SDK, returns only the allowlisted shape, and answers a malformed, unknown and deleted id identically so ids can't be probed. A picture that goes with a link is copied by the function into a folder named by the id, which a Storage rule lets anyone `get` but nobody `list` or write, each copy under its own download token (a plain copy carries the private original's token into a public link), and deleting the link deletes the folder. A link opens without sign-in only when that is the point of the feature.
- **A public page never says who shared it.** The record keeps the owner's uid so the owner can manage it, and the function that serves the page answers `isOwner` by comparing the caller's uid (a signed-out call works: auth is optional there) and sends the owner's own record id to the owner alone: never the uid, name, email or photo. The owner sees the same page marked as theirs with a way back into the app; nobody else can tell whose it is.
- **A secret in a URL goes nowhere else.** The site shell writes every signed-in person's current path to Realtime Database presence, which anyone can read, so a route that carries a token (`/a-list/shared/<id>`) is shortened before it is written (`Layout`). Also keep it out of error reports, analytics and any stored redirect, and out of logs: a Function logs a short code and at most the first four characters of an id, never a path (a Storage error's message holds it), a title or a body.
- **Optional locks are checked on the server.** A PIN or password is never sent to a visitor's browser or stored where a visitor can read it, is compared in constant time, and is shown back only to the owner, hidden until they reveal it and copyable while hidden. A field that takes a secret is masked with its own show/hide button (`type='button'`: Dreamer UI's built-in password eye submits the surrounding form, so keep `type='text'` and show a `*` per typed character yourself, leaving any placeholder as is) and accepts a paste, including one with stray spaces or a label. Say plainly in `TECHNICAL.md` what the lock does not protect against (no attempt limit, a plain-text PIN the owner can read).
- **A share is a snapshot unless it says otherwise, and ending it is one tap.** The owner can take the copy again (**update**, the address stays), **get a new address** (the old one stops working at once) or **stop sharing** (deletion cuts access at once, and its confirm says everyone with the link loses access and that it can't be undone); deleting the record a link was made from stops the link too, and that confirm says so. A delete removes the files first and the documents after, so a failure leaves a link that can be stopped again rather than pictures nobody can reach, and it answers a missing, a malformed and someone else's id alike. Copy says what the person is giving away before they create it, in words about their data and naming every kind of thing the page shows (seen status, free text they typed, which "rating" is meant: say "star ratings" when a content rating like PG-13 is also visible).
- **Previews say less than the page.** A link preview (the Cloudflare worker's Open Graph tags) is public even when the page is locked, so its text is generic and never names a person, a title or a date range from the shared content. A page that shows someone's data behind a link calls `useNoIndex` (`@/hooks/useNoIndex`) and gets a `pages` entry in `cloudflare-worker.js`, which sends `X-Robots-Tag: noindex, nofollow` (the standard for every page that works without sign-in: not listed, its links not followed) and `Referrer-Policy: no-referrer` for crawlers and browsers that don't run JS. `useNoIndex` also sets `<meta name='referrer' content='no-referrer'>`, so the address never travels to another site through a link or picture on the page, and the page's links are `https` only with `rel='noopener noreferrer nofollow ugc'`.
- **Free text and URLs on a public page are allowlisted by shape or host.** A first-party page never loads an arbitrary image URL or renders more than the allowlisted fields, and a public page loads nothing from a third party at all (no video thumbnail, no hotlinked cover, no embed: each is a request that tells another server someone opened a private link); typed titles and names are shown as written, and the form says so.
- **Cap what one person can publish** (A-List: 10 links) and say where the cap is enforced in `TECHNICAL.md`, per "A cap or uniqueness check that lives only in the UI". A cap message that points to another screen for the fix carries the door to it as a chip (it closes a drawer first and opens the screen), never only the words.
- **Verify the denial, not just the success.** For anything public, test as the owner, another signed-in user and a signed-out visitor, against the emulator with the base rules beside the branch's so only the intended outcomes differ, and read the response body for fields that shouldn't be there (the owner's uid, the PIN, a price). Then follow the secret itself: open the link signed in and grep every store the shell writes to (presence, storage, logs) for the token.

## Designing a mini-app's look

Each mini-app may have its own personality on top of the shared playful base; A-List (`src/apps/a-list`) is the reference.

- **Theme through tokens, in one stylesheet.** The app owns `<app>.css` that overrides Dreamer UI's semantic color tokens (`--color-primary`, `secondary`, `accent`, `muted`, `border`, and the floating surfaces `--color-popover`, `--color-popover-foreground`, `--color-tooltip` and `--color-tooltip-foreground`, light and dark, plus `--subview-backdrop` for the subview card's backdrop; `npm run check:apps` fails a theme that omits any of them, since a popover, dropdown or tooltip would otherwise keep the site's white and zinc and clash with the app's paper) on a class (`html.a-list-theme`) that a `useXTheme()` hook adds to `<html>` only while the app is mounted, so portaled modals and drawers pick it up and other apps are untouched. Components then use semantic classes (`bg-primary`, `bg-accent`), never raw palette colors, so a later re-theme is a CSS edit.
- **A theme's paired tokens are readable in light and dark, and `npm run check:apps` measures it.** Each `--color-X` / `--color-X-foreground` pair a theme sets (primary, secondary, accent, popover, tooltip, and destructive, success and warning if overridden) is at least 4.5:1, and a dark block is read on top of the light one. The site-wide top strip (`OfflineBanner`: offline, slow, "New version ready · Restart") is the `primary` pair and its button is that pair swapped (`bg-primary-foreground! text-primary!`), never a `secondary`/`tertiary` variant, which an app's theme restyles (Pinch's makes `bg-secondary` buttons see-through, which left Restart unreadable). A new theme, or a change to its colors, is looked at on that strip too.
- **Pick the metaphor first and let it name everything.** A-List is "AMC and the theater": red primary, marquee-gold accent, ticket/popcorn/film emoji, copy like "Did you catch it?". Write the metaphor, palette roles and shape language (what is round, what is a pill) in the app's rules file.
- **Shared pieces stay general; app flavor lives in the app.** Pills, badges (`PriorityBadge`, `ViewingStatusBadge`), tiles (`StatTile`) and subviews are built in the app's `components/shared` or `components/shell` against the app's tokens. Anything a second app needs moves to `src/components` in that PR.
- **Write the app's rules down.** Add `.github/instructions/<app>.instructions.md` and the identical `.claude/rules/<app>.md` (see `a-list.instructions.md` for the shape: theme, shape language, emoji meaning, subview use, anything app-specific like a money input, and its recurring layouts as patterns). Update them whenever the app's design vocabulary changes, in the same PR.
- **Where a visual rule lives: the narrowest place that covers everyone who needs it.** Behaviour every app should get lives once in `src/index.css` (the `sticky-app-bar` utility, the `body` overflow clip that keeps `sticky` working, the 92dvh cap on every drawer so the page shows through at the top, `color-scheme` for native widgets); a rule that is the app's look (palette, radii, field padding, selected-pill tint, how tappable text reads) lives in `<app>.css` on the theme class; a one-off stays on the component. Never patch a cross-app problem in one app's stylesheet, and never push one app's taste into the global one. Before adding a central rule, grep `index.css` and `dreamer-ui.css` for the one that already exists; after changing one, re-drive another app's drawer, header and form and add a row to the PR's regression table, because a global change reaches every mini-app.
- **Text color is part of the theme, not per component.** Body and row text is `text-foreground`; blue (the primary) is for real links (a URL, a place) and for filled-button labels. A tertiary or ghost button is a quiet action or a tappable row, so the app's stylesheet sets its text to the normal color (Waypoint's `button.text-primary:not([class*='bg-'])` rule in `waypoint.css` is the one to copy), instead of every call site adding `text-foreground`. A new mini-app starts its `<app>.css` with the tokens, the radius/padding inset, the selected-pill tint and this rule, then checks a screen of rows in light and dark for blue that isn't a link. A link-style button is only for a link inside a sentence of three or more other words ("Add prices" in a line about prices), and stays underlined where there is no hover to reveal it (a phone). "Show N more" under a list is `@/components/ShowMoreButton` (a left-aligned 40px tertiary row with a chevron, never underlined), and a reveal or a two-way switch on a field ("Add a note", "Put it in a group", "No amount") is `@/components/RevealChip` (a dashed chip, with its "Remove" as the same chip); a control that changes what the screen asks (a summary's "Change", "Done"), opens another view or acts in bulk is a row with a chevron, a chip or a pill, never a link (owner, round 7: "Change day or meal" under a title). A quiet state action (Reset, Tick all, Clear what you got) is an `ActionChips` chip with an icon and a bulk removal is its red hairline one (`isDestructive`); a value changed inside a drawer or sheet is a `SummaryRow` (framed with the same hairline as the builders' row) that swaps the sheet's own content in place, since `SummaryEditor` opens its own drawer or popover and a drawer never opens a second drawer. A button inside a drawer is never transparent or borderless against the sheet, a red one included: give an action row a visible edge (`border-border`) or a `bg-muted/50` block (a destructive one is `ActionRow isDestructive`).
- **Every control takes the app's shape language, ticks included.** An app whose shapes are round (Pinch) makes its checkbox a circle in its own stylesheet (one rule on the theme class for Dreamer UI's `button[role='checkbox']`: a ring unticked, the ink fill ticked, the focus ring and a 40px target kept), never per call site and never in `index.css`; a property the component sets inline (the checkbox's fill) needs `!important` in the theme rule, with a comment saying why. Read the computed `border-radius` (at least half the width), fill and tick color in light and dark, checked, unchecked and disabled: the ticked fill has at least 3:1 contrast with the surface and the tick at least 3:1 with the fill, `:focus-visible` shows an outline, and the hit area with any pseudo-element is at least 40×40. A mark that looks like a control follows it too: in a round app a done or status tick is the round `@/components/TickMark` (`variant='soft'` for a mark that repeats down a list, the ink one for a single done row), never ✅ or ☑️ (an emoji draws a square box), and a request to make every X round is answered by a census of everything that draws the shape (controls, emoji, icons, shared components) on every screen, not by the control alone (owner, round 7: the square ones were ✅ emoji).
- **Badge contrast: status badges are soft tints (`secondary`, `accent`, `muted`) or outlines.** A solid fill (`primary`, `warning`, `destructive`) is for the one thing on the screen that needs action, never for a status that repeats down a list. Check a badge's text against its fill and neighbors; if it jumps out more than the title beside it, soften it. An attention tint covers only the last stretch (a date that is today or tomorrow): a state that lasts most of an item's life is not a warning, and a count's words say the window ("2 to eat by tomorrow").
- **Colors must not fight their emoji.** Don't put an emoji on a background of its own hue (🔥 on red); give it a neutral or complementary chip. Solid red/primary fills are for the one primary action on a screen, not for status chips. A selected pill is solid, so it carries no emoji of a matching hue (a 📍 on red); the section's label carries the icon instead.

## State, data, and performance

- **Firestore `onSnapshot` lives in `store/listeners/`** as `startXListener(key, onChange)`, started once from a `useXSync` hook at the mini-app's top-level page (reference: `useNineLivesSync.ts`, `useWaypointSync.ts`). Never inside a leaf/tab/panel component's `useEffect`. The exception is a genuinely modal-local, ephemeral subscription that no other component reads (e.g. a single invite-code lookup); keep it a small hook and mount it via a conditionally-rendered, keyed component so it subscribes once per key. A listener for an optional enhancement (theaters) never feeds the fatal load-error screen: its failure degrades only its own UI, because a rules-deploy lag or one denied collection must not lock features that work. It also logs its error (`console.error`) and clears what it had loaded, so a rules lag or a typo never removes the feature without a trace or leaves stale rows on screen.
- **A continuation after the `await` of a write that can sit queued offline never closes or navigates shared screen state unless the screen that started it is still the one showing.** Use a functional setter that checks what is open (`closeSubviewIf`, a token compared inside `setView`) or a mounted check, never a bare `closeSubview()`: offline the write resolves much later, and a bare close shuts whatever is open by then, such as a half-typed form. A save that can sit queued offline closes its sheet once the same pure checks the write makes have passed, without waiting for the server, and marks the row ("Saves when you're back online") after a moment; only an upload holds the sheet, and then Cancel becomes Close. The same goes for a read: a reading that lands after the person left is dropped, and a confirm answered after the screen moved on leaves the new screen alone.
- **A picker never writes.** A search or pick control's "New X" stages a draft that the form saving the record writes in the same batch (see "A record created only because another record names it" below), so an abandoned plan, recipe or list leaves nothing behind. What a person does where the signal drops (ticks, adds, eating, planning) closes its form as soon as Firestore has the write locally and never holds Cancel hostage to the server; a transaction is used only where losing a rare race is worse than failing offline, and TECHNICAL.md states the race.
- **Request/response calls go through TanStack Query** (`queryOptions` factory in `src/lib/<feature>/<feature>Queries.ts` or `src/apps/<app>/queries/<resource>Queries.ts`). Key includes every param that changes the result and nothing that doesn't; `staleTime` fits how often the data changes. Writes and non-idempotent calls stay uncached. A read whose empty answer came only from the device's cache (`metadata.fromCache`) is "couldn't load", never "nothing".
- **Coming back to the tab is `useOnTabReturn` (`@/hooks/useOnTabReturn`), never a hand-rolled `visibilitychange` listener.** It fires when the page turns visible again or the window regains focus after losing it, so a dismissed "ask me later" question, a refresh of time-sensitive data or a re-check after a hand-off to another site can all hang off one place.
- **A countdown runs to a wall-clock deadline and is settled from three places:** the nearest timeout, `useOnTabReturn` and the display's own tick. A timeout that wakes before the deadline (the clock stepped back, or the tab was throttled) re-arms for what is left instead of returning, so a timer never sits at 0:00 without alerting; a deadline passed by a forward step finishes on the next tick.
- **A hook that mirrors a browser handle (a wake-lock sentinel) updates its status only for the handle it currently holds,** and treats a handle the browser already released as absent. A late `release` event from an old handle must not flip a newer one's status, a released handle is requested again instead of trusted, and a rejected release after the person left is logged, never shown as a failure (`useWakeLock`).
- **A toast for a change is keyed on a transition this page watched, not on a state.** A listener's first snapshot arrives after mount, from an empty store, so "is `sent` and wasn't `sent` before" fires for every old record on each reload. Toast only an item first seen in an earlier state and now in the target one; an item that first appears already there never toasts.
- **Screen state a person could share, reload or go back to lives in the URL through `nuqs`, not `useState`.** `NuqsAdapter` (`nuqs/adapters/react-router/v7`) wraps the router's root element. Its writes are shallow: they change the URL without telling react-router, so `useSearchParams`, `useLocation` and `history.state.idx` lag behind; give each param one reader and never use `idx` to decide what Back does. Declare the parsers next to the feature (`parseAsStringLiteral([...] as const)` for a fixed set, `parseAsString` for an id) in one `use<Feature>UrlState` hook that returns named actions (`showApp`, `goBack`), never raw setters. A step deeper (list → detail on a phone) is `history: 'push'`, and the hook marks that entry (`history.replaceState` with its own flag once the push settles) so Back pops it (`navigate(-1)`) and a deep link's Back clears the params with a replace instead. Peers, tabs and an overlay mirrored to the URL (a member sheet) are `replace`, so opening and closing never changes `history.length`. Check with `history.length` and two system Backs, not only the visible screen. Keep drafts out of the URL. Reference: `src/screens/admin/useDashboardUrlState.ts`.
- **Admin and reporting screens read once, with a refresh button; only what the admin edits is live.** Usage, visits and member lists are one-shot TanStack queries (`staleTime` a minute, all under `ADMIN_QUERY_KEY` so one refresh covers them), not listeners, because nobody watches them change. The app catalog stays a listener since its settings are edited there.
- **`meta: { persist: true }` must earn its place.** Remove it from any query whose `queryFn` reads Firestore (Firestore's own cache already persists it) or returns secrets, tokens, or key material. Keep it on safe third-party/worker results so they work offline.
- **Performance is a design check for every mini-app, judged at scale.** Every app keeps an oversized seed fixture (Waypoint's "Big Group Reunion (scale test)" is the reference) and a feature that adds a list or per-row work is opened on it, on a phone-width page, with the dev build throttled to 4× CPU (Playwright + CDP `Emulation.setCPUThrottlingRate`), switching between the app's main tabs. A tab switch that takes over a second at 4× on the fixture, or any "Maximum update depth" or render storm in the console, is a bug. Profile before optimizing (`Profiler.start` through CDP, sort by self time): the hot spot is rarely where it looks. A fixture is evidence only for the data it holds: when a change adds per-row work on a field the scale fixture lacks, extend the fixture before quoting a number.
- **The patterns that fixed Waypoint, to reuse:**
  - *Build once, reuse.* An `Intl.DateTimeFormat`/`NumberFormat` is built once (module-level or a `Map` keyed by its options), never per call or per row. A pure conversion called per row on every render (a time-zone offset, a trip-relative time) is cached by its inputs, or per item in a `WeakMap` when items are replaced rather than mutated (`memoizeByItem`).
  - *One pass, not per row or per pair.* Compute totals, settlements and groupings in a single walk that buckets into a `Map`, then look up; never filter the whole list inside a per-row or per-pair loop. Keep the old and new outputs identical on random data before replacing an algorithm. Text a list derives per row from data that rarely changes (the names behind each shopping row) is worked out once per change of that data, keyed by its inputs, and shared by the row and its height estimate.
  - *Memoize on stable inputs.* Derive heavy values with `useMemo` or a `createSelector` keyed on the data they read; ids derived from an object (`Object.keys(trip.members)`) are memoized on that object so downstream memos hold.
  - *One listener per key, one render per burst.* An external store that many components watch (`useUserInfo`) shares one Firestore listener per key, bumps a per-key revision so only the components showing that key re-render, and batches a burst of snapshots into one notification; `useSyncExternalStore` snapshots are O(1) and cached (`useMediaQuery` stores the breakpoint instead of calling `matchMedia` per read), and any module cache of user data is cleared on sign-out.
  - *Cap what you draw.* A list that can reach 100+ rows caps or collapses (a "Show N more", a search, a Disclosure) rather than rendering all of it. A long list grouped by day or section mounts a group only when it nears the screen (`@/components/LazyMount`, with an estimated height and the first screenful eager) and gives the group's wrapper the `defer-offscreen` utility (`content-visibility: auto`, so the browser skips style, layout and paint offscreen) with `--defer-size` set to the same estimate. `content-visibility` alone is not enough: React still builds every element, and that was the cost. Calibrate the estimate against the real height so the scrollbar barely moves. A section that can hold 60+ rows mounts them in chunks of 12 and puts `defer-offscreen` on the chunk, not the whole section (a monolithic section can't flow across CSS columns).
  - *Don't tear down what the next screen needs.* A tab switch unmounts and remounts a screen's components; a shared store's listener lingers a few minutes after its last watcher leaves (`useUserInfo`), because starting 120 Firestore listeners again cost more than the render. Never start a listener per tab or per row.
  - A listener kept alive after its last watcher leaves is stopped, and its handle cleared, by the same code that clears the cached data on sign-out (and restarted for components still watching), and a failed `onSnapshot` clears its handle, so a later watcher resubscribes. `LazyMount`'s `eager` is read once: content that has mounted stays mounted when the list reorders.
  - *Keep the tap instant.* Render the new tab in a transition (`useTransition`) and move the nav at once, and wrap each big tab in `memo` so the urgent update (the nav moving) does not re-render the tab that is leaving.
  - *Detail sheets mounted by a big list don't live in its parent.* The open state of a sheet that rows open sits in a small child the rows reach through a ref or store, so a tap doesn't re-render every day of the list; measure click-to-visible at 4× for every row type, not only tab switches (a stay row's sheet took 1.2 s while its sibling travel row took 0.1 s).
  - *Closed means unmounted.* A drawer or modal's heavy body (a filter sheet with a pill per member) renders only while open.
- **A PR that touches performance says how in its body**: a `## Performance` section with the fixture, the throttle, before/after numbers for the screens switched, and what changed.
- **`useAppSelector` that builds a new array/object** (`.filter`, `.map`, spread, object literal, `[]` fallback) must pass `shallowEqual` from `react-redux` or use a `createSelector` selector. A selector that returns an existing slice or `.find(...) ?? null` is fine.
- **Pick the atomic write that fits — never write a cached document back whole.** Anything another user can change while a modal is open (`seenBy`/`dismissedBy` maps, vote or history arrays, `members`, a paid-status map, `isArchived`) is a concurrency hazard. Full rules in `copilot-instructions.md` ("Atomic writes"); the short form:
  - **A bulk delete or change chosen from a cached flag** (Clear what's ticked, archive all) re-reads the flag inside a `runTransaction` per chunk and touches only the documents that still match, returning the real count; or its TECHNICAL note states the window. A second device may have flipped one a second ago.
  - **A back-link written for another record** (an idea's `recipeId` when a recipe is made from it) never rides in the batch of the record the person cares about: a queued offline batch can be refused whole when the linked document vanished on another device. Commit the record first, write the link as a field-scoped update after it, never throw if the link fails, and report whether it landed (the toast claims no link it didn't make).
  - **Append/remove on an array** (`changeHistory`, `upvotedBy`) → `arrayUnion`/`arrayRemove`. A list the rules cap is merged from the transaction's own read instead: `arrayUnion` can't respect a cap, and the next add would be denied.
  - **One member's own key in a map** → `runTransaction` (read via `transaction.get`) or a dotted-path `updateDoc`.
  - **Derived from the prior value, or must hold across several documents** (role changes, approving a suggestion, a counter) → one `runTransaction` that re-reads everything it depends on and aborts with a readable message if the world changed. Network side effects (reminders, uploads) stay outside it, with cleanup if it fails.
  - **An edit form's save** → `updateDoc` with only the fields the form owns, never `setDoc` of the cached object: that silently overwrites a concurrent vote, seen-mark, or archive. Reference: `updateEvent`, `updateStay`, `markExpensePaid`.
  - **A pointer to another document** (`favoriteTheatreId`) → a transaction that confirms the target still exists, and removing the target re-points it (to another candidate, or none) in the same transaction on every surface that removes it; a dangling pointer reads as none.
  - **A prompt driven by a timestamp field** (`purchase.startedAt`) is cleared in the same write that answers it, and bounded by the item's status, so it can't re-ask after the answer or for something already over.
  - **A side effect keyed by a stored id** (a scheduled push's `trailerReminderId`) is rescheduled only when the field it derives from changed in that edit (compare with the document the transaction read), cancelled only while still ahead, and never awaited after the write: a slow or offline network must not hold the save UI.
  - **A form's save thunk accepts only the fields its form shows.** If the form doesn't show paid state, `updateX` doesn't take it, and passing the cached value back "unchanged" is the same stale overwrite. An action that reverses another (mark unpaid, un-archive) is a transaction that aborts if the state already changed and also resets the per-member flags the forward action's readers use (`paidMemberStatus`). Reference: `updateExpense` vs `markExpensePaid`/`markExpenseUnpaid`.
  - **A record created only because another record names it** (a new source typed in a recipe form, a proposed ingredient) is written in the same `writeBatch` as that record, never as a separate awaited write before it: a failed save leaves no orphan, and an offline save is queued whole instead of hanging on the first write.
  - A `writeBatch` is for independent writes with no reads. Thunks that only assign caller-supplied values to disjoint scalar fields need none of this. Reference: Waypoint `membershipActions.ts`.
- **A delete across records re-reads each record per chunk inside a transaction, removes the parent last, and reports the real count,** so an interrupted run can be rerun and leaves nothing half-removed; it leaves `updatedAt` alone where that versions a cover.
- **A reminder tells the person through one surface.** A reminder the scheduling page rings for itself carries `inAppToast: false`, and a new push path says which one surface tells the person. A saved copy that names something scheduled on a server (a timer's push) carries its id, and every way the copy is dropped cancels it; a guard on "does this exist" that reads a windowed store checks the window first; a first write that creates a shared document is a transaction, never trusting "not in the cache". Finished reminders are pruned by the scheduled sender, and a device token leaves on sign-out and when the push service reports it gone.
- **A client that starts writing a new key on create is run against the base rules first (only a rule that names the key can refuse it; the beta tier names few).** Before it ships, run the client's exact create and edit shapes against the base rules (`git show <base>:firestore.rules`) and put the consequence in the Regression check as evidence (base rules refuse a create carrying the new key). It is never a step for the reviewer: the merge workflow deploys rules, indexes and functions before it deploys the client, so the order is already right (only the preview, which builds against production rules, can't save what the new rules allow until the merge). A number written with `increment` is rounded wherever it is read back into a field or compared, and every `await` before a bounded step (sign-out's presence write) is driven offline.

## Firestore and Storage rules

- **Every app here is a beta app, so `firestore.rules` is the beta tier (about 54,000 estimated bytes against the 256,000 limit).** It keeps what protects people from each other: sign-in, ownership, membership and role gates, trip phase rules, invite, pending-request and approval flows, immutable ownership fields (`createdBy`, `tripId`, `householdId`, `ownerUid`), own-key-only writes to shared maps (`seenBy`, paid status), the unguessable share-id format, the reminder link check, and the few shape checks that protect one member from another: Waypoint early payments (in the split, capped at the expense, only the returned flag once paid), the shared album, web-address links other members open (a case-insensitive `http(s):` scheme, or no script scheme for a field saved as typed), membership writes that touch only `members`, Worth the Wait's key, reveal lock and each partner's own reveal request, and reminders that reach only yourself or people sharing the trip (Admins and Editors) or household. Before calling a rules change done, replay every client read and write per app, as each role and phase the UI allows, against the old and the new rules in the emulator (separate project ids keep runs apart), and probe what a modified client could do to another person. It does not validate a field's type, length or enum, the `hasOnly`/`hasAll` key lists, list caps or timestamp bounds: a caller who can write a document may write any shape, and the client's types and caps are the only guard. Do not add those checks back to a beta app; the full rules for an app come back when it graduates (`GRADUATING.md`, phase 2; the strict file is in git history at c784e89), and the strict one is not needed to merge. A rule's identity check still matches the collection's real path, and a state-changing rule (who may approve, archive or delete) is verified against the emulator for the allowed and denied side as before.
- `storage.rules` paths mirror wherever the Firestore doc lives.
- **Every query that needs a composite index ships it in `firestore.indexes.json` in the same PR.** The emulator never enforces indexes, so a missing one passes every local check and fails in production with `FAILED_PRECONDITION: The query requires an index`, which for a scheduled Function means silently doing nothing every run. A composite index is needed when a query has an equality filter (`==`, `in`, `array-contains`) plus a range filter (`<`, `<=`, `>`, `>=`, `!=`, `not-in`) or an `orderBy` on a different field, or range/`orderBy` on two or more fields; a lone equality, a lone range or a lone `orderBy` is not. List equality fields first, then the range/`orderBy` fields in query order, with `queryScope` `COLLECTION_GROUP` for `collectionGroup()` queries. Run `npm run check:indexes` (CI runs it on every PR touching `src`, `functions/src` or the index file); it fails on a missing index and warns on one no query uses, so delete indexes for queries that no longer exist. The index file deploys with everything else (`fb:deploy:smart` includes `firestore:indexes`), but a new index takes a few minutes to build after deploy, so a Function that depends on it fails until it reports READY. The script reads queries statically: one built from a variable collection path it can't resolve is matched by field set alone, so state in the PR body which index a dynamic query relies on.
- **`firestore.rules` has a size limit the emulator never enforces: compiled executables under 256,000 bytes, and the size is the rules' own text.** It came out as 1.73775 bytes per character of code (comments removed, whitespace collapsed to single spaces) on two real answers from the Rules API, and a function's body counts once however many rules call it (merging seven create/update pairs saved only 247 characters). Past the limit the merge deploy fails at the very last step, releasing the rules, with only `HTTP Error: 409, Release … already exists` (the CLI hides the real `400 Total size of compiled executables must be smaller than 256000 bytes`), after the Storage and Database rules have already gone out, and a re-run fails the same way. #395 hit it at 258,960. `npm run check:rules-size` (CI runs it on every PR touching the rules) estimates the size, warns from 240,000 and fails from 250,000, and lists the clauses repeated most. A clause that repeats (`request.resource.data.createdAt == resource.data.createdAt`) is a helper function at the top of the rules, not a copy per rule; a PR that adds rules says the estimate in its Regression check. Prove that a shrink leaves behaviour unchanged by running the same writes against the old and new rules in the emulator (`PUT /emulator/v1/projects/<id>:securityRules` swaps them) for every document of the seed, as every seeded user and signed out, and diffing the results. README "Troubleshooting" has the symptom.
- Never add a global `match /{path=**}/X` rule for something scoped under an app path; prefer a body check (`resource.data.householdId == householdId`).
- Repeated assertions go in helper functions. Never put a self-referential `get()`/`exists()` in a collection's own `allow read`; use `resource.data`. Split OR-ed read predicates into separate `allow read` statements.
- Denials and atomicity are verified against the emulator (e.g. a raw REST or client-SDK write), not just by the absence of a UI button. A client that writes a new field needs no rule change in the beta tier, but a client that stops sending a field its reader needs is a client bug the rules will not catch.
- **Every PR that adds/renames a field, changes who may write one, moves a path, or adds a collection updates `firestore.rules` (and `storage.rules`, indexes) in the same PR, and says so in the PR body.** Before finishing, grep the diff for each touched field and permission and confirm a rule covers it; a rule you didn't need to change is a conclusion to state, not assume.
- **Verify rules directly against the emulator before the PR is done** — sign in as each role through the auth emulator and hit Firestore's REST API (`Bearer owner` seeds fixtures): one allowed write and one denied write per role-sensitive rule you touched, including the "editor/non-member must be denied" side. Rule changes also re-run every pre-existing rule on the same collection.
- **A PR whose client needs new rules says in its Not checked block that its preview channel can't exercise it until the merge** (the preview is run by hand, builds against the production backend, and rules deploy only on merge); it is a limit of the preview, not a to-do.

## Cloud Functions

- **A function that parses a person's link reads it in one linear pass.** Never a lazy `[\s\S]*?` or an unbounded `[^>]*` over a page: a hostile 1.5 MB body turns those quadratic and blocks the instance for minutes (the 6 s timeout only aborts the fetch). `fetchPageContent`'s `readPage` is the reference, and the public-address check allows only global-unicast IPv6. Any input cap is benchmarked raised too (see Validation).
- **A handler that dispatches on a client-supplied key checks `Object.hasOwn` (or uses a `Map`),** never a bare object lookup that resolves names like `toString`.
- **Third-party results are cached carefully.** Never cache an empty or null answer for the full TTL (a parsing gap would stick for weeks), round any privacy-reduced input (coordinates) on the server before the upstream call so a shared entry never depends on who populated it, and list every contract detail taken from docs alone (date formats, parameter names, paging) in the PR body as unverified: a fake server you wrote yourself doesn't verify it.
- A third-party key that can't be domain-restricted is a Functions secret behind an `onCall` (never in the browser, a response or a log); a free-tier API shared by all users gets a server-side cache and a daily budget guard. Full rule in `copilot-instructions.md`.
- **A scheduled sender never flushes a backlog.** Anything that sends on a timer drops what is long overdue (reminders: 30 minutes, then `expired`, a yearly one rolls forward) instead of sending it late, because an outage or a missing index would otherwise deliver every missed message at once the moment it is fixed.
- **`functions/README.md` is the functions reference — keep it current in the same PR.** Adding, renaming or removing a function updates its row in the Functions table (trigger, app, purpose). A new secret or env var gets a "Secrets and config" row, and a function that caches, budgets or fetches for a user gets a per-function note. A new secret is created in production before the PR merges (CI deploys every function on merge, and a missing secret fails the whole deploy), and the PR body says so.
- **A function that fetches a person's link uses the guarded fetch.** `functions/src/linkMetadata/safeFetch.ts` (public-address check, redirect cap, byte cap, timeout) is the one way a function opens a user-supplied URL, as `fetchLinkMetadata` and `fetchPageContent` do; never a bare `fetch` of a typed link.
- **A page-reading function returns what the caller asks for.** `fetchPageContent` takes `include` (`text`, `structuredData`, `meta`, `headings`, `images`), optional `schemaTypes` and a text cap, returns only those kinds, and knows nothing about what the app does with them; a new kind is a new extractor in that file, never a flag for one app. The app's own `lib/` turns the content into its entity (Pinch hands the page text and any Recipe data to the AI reader, which reads partial or odd pages a hand-written parser misses). Image addresses it returns are third-party: load them through `FallbackImage`. A parser of a person's link caps every collection it builds (images, headings, nodes) before any step that is quadratic in its size, and starts every sticky pattern on a token, never on `\s*`; benchmark it against a 1.5 MB body of 100,000 `<img>` tags and of 780 `<meta>` tags padded with 1,900 spaces each.
- **Local setup lives in scripts, not memory.** A step every developer must repeat (like building `functions/lib/` before the emulators load it, handled by the `preemulators*` hooks) becomes a `package.json` script or `pre*` hook, and the README documents the command rather than the manual step.
- **A new `onCall` function needs nothing run by hand to reach the browser.** The organization policy refuses the CLI's public IAM grant, so `fb:deploy:smart` (what the merge workflow runs; `fb:functions` and `fb:deploy` skip this) sees `Unable to set the invoker`, opens every callable with `npm run fb:invoker -- --all` (`--no-invoker-iam-check`) and deploys once more. A callable that skipped that path (symptom: browser CORS error; Cloud Run request logs show a 403 on the `OPTIONS` preflight) is fixed with `npm run fb:invoker -- <function>`; it refuses a function that is not an `onCall`, whose IAM check must stay on. Because a callable is then open to anyone with its address, it checks `request.auth` itself unless it exists for signed-out visitors, and `functions/README.md` says which. See README's [invoker section](README.md#new-cloud-functions--cloud-run-invoker-access).
- **A once-a-day sender claims its day in a transaction before it sends,** so a failed send skips a day and never doubles one, and its window is shorter than its cadence; a feature that pushes at a time the person chose polls no slower than the shortest thing it times, and re-reads a queued reminder after waiting. A new Admin-SDK query ships its index in the same PR (`check:indexes` reads a trailing `.limit()`).
- **An optional provider credential is read at run time and its absence means the provider is skipped,** because a bound secret or a `defineString` makes the whole deploy need it. A provider list has one switch (`IMAGE_SEARCH_PROVIDERS`), a free-tier quota is counted in the provider's own time zone and stopped short of the limit, results from a third party are copied by name, https only, and a picture the person picks is loaded once at the tap so an unreachable one is refused there, not after saving.

## Validation

- **Typecheck with `npx tsc -b --force` (or `npm run build`)** — `tsc --noEmit -p .` checks nothing in this solution-style repo. Also run `npx eslint .`. Run eslint again after adding a call that passes a flag derived from state: the React Compiler can refuse a nearby `useMemo` ("Existing memoization could not be preserved") and `!!flag` fixes it.
- **A figure formatted in two places is asserted in both at the format's boundaries** (99,999 cents, 100,000 and one over): one function formats it, and a check fails if either place stops calling it. The scale fixture's biggest value is not evidence for a format that changes at a bigger one.
- **Never run Prettier on Markdown, and never run a formatter over files the change does not touch.** A run over `src/apps/pinch` re-padded every table and caused conflicts, and another over a folder reformatted about 24 unrelated files (both restored); run it on the `.ts`/`.tsx` files you changed, edit Markdown as text, never reformat in a merge resolution, and revert format-only files before review.
- **Measure every modal and form on a phone (390×844) before calling it done.** In a Playwright script, open each one in every state it can reach (a new item, an edit, each reveal switched on) and read the container's height: a modal over ~70% of the viewport (about 590px) or that scrolls moves to a drawer (or a subview when it is a search or a sequence) ("Pick the container by the content"). A form is not done because it fits on desktop. A modal's overflow is measured on its dialog (`fixed inset-0 overflow-y-auto`: `scrollHeight` minus `clientHeight`), not on its card, whose `overflow` is visible, and every sheet is checked at 844×390 for it (two 48px picker rows overflowed Shopping's modal by 29px there).
- **Look at every new or recolored surface at full size in light and dark.** Read each screenshot for text or emoji lost on a fill, a control whose icon, label and border disagree, text pressed against a rounded edge, a label that doesn't line up with its field, and a separator left dangling after a wrap. A change to a theme token is checked on a filled button, a selected pill, a badge, a highlighted card and a tinted banner before it is done.
- **A parser with an input cap is benchmarked with the cap raised, and a check fails if the cap is removed.** A test run only on capped input proves the cap, not the parser: give the parser a parameter (or a hook) that lifts the cap, time it on input far over the cap (250,000 repeats of its commonest token, a hostile run of digits), and keep a pair of cases just under and just over the cap so deleting it fails a check (`scripts/checks/durations.ts`). A check's title says what its assertion proves: a name that promises a day reads as on the list needs an assertion about that day, not about a helper's output.
- **Drive the change in a real browser** against the local Emulator Suite, signed in through the dev fixture switcher, with a throwaway Playwright script (delete it when done, and close its browser in `finally`: a leaked page keeps its listeners open, and a shared emulator under several agents runs out of heap). A passing typecheck is not evidence a feature works. Also re-drive every pre-existing feature that touches a file you changed, and treat "the new feature works" and "nothing regressed" as separate checks.
- **New work must be backwards compatible with data already in Firestore.** Existing documents will not have a new field, so: readers default it (`doc.field ?? []`, `?.`) instead of assuming it exists; edit actions backfill missing keys alongside the write (see `getMissingEventFields`); rules accept the legacy shape. Prove it by writing a legacy-shaped document (the new keys deleted) through the emulator and driving every read and edit path over it in the browser — a page crash or a denied save on old data is a regression. Never normalize legacy documents in a listener if an action detects missing keys to backfill them. A missing key ("written before we tracked this") and an empty one ("we know there is nothing") are different answers: only the second may flip a default. A stored value of a replaced option whose old default was on is not read as a choice (it was mostly the default written alongside another change): ignore the old key, so everyone starts at the new default.
- **A dependency reached only from a lazy chunk or a worker is listed in `vite.config.ts` `optimizeDeps.include`.** Otherwise the dev server finds it the first time the feature runs, re-optimizes and reloads the page, which drops a person out of cooking mode the moment they turn the natural voice on; after adding such an import, clear `node_modules/.vite`, open the feature and read the Vite log for "optimized dependencies changed. reloading" (there must be none). A feature a person turns on from inside a doing screen is driven from that screen with a marker on `window` to prove the page did not reload.
- **Anything that shows or compares a date runs in a timezone behind UTC** — create the Playwright page with `timezoneId: 'America/Los_Angeles'`. Cloud sandboxes and CI run in UTC, where a date-only value formatted in local time looks correct; the off-by-one only appears west of UTC. Check that the displayed date matches the date picker's value.
- **Leave the dev server and emulators running** after browser validation; finish with `npm run seed:reset` so data is back to the seeded baseline.
- **A PR that adds, removes or moves a door, or changes what a screen volunteers, updates the sitemap in `UX.md` and the tables in `src/apps/pinch/JOURNEYS.md` (§4.1 doors, §4.2 insight counts) in the same PR,** states in its body the journey each new door serves, and records the first-view insight count at 390×844 for the seeded, empty and scale kitchens before and after, each item classified decision / status / reference / noise (a noise item is a finding). Walk the weekly loop (plan, shop, cook, leftovers) and the back gesture over every new overlay before calling it done.
- **When a feature changes what is true about the app (adds sharing, a public callable, a new outbound path), grep the READMEs, `TECHNICAL.md`, `UX.md` and rules-file comments for "no sharing", "private", "every callable requires" and "nothing else leaves".**
- **When a constant, rule or control changes behaviour, grep `README.md` (including "Under the Hood" claims about what is looked up), `TECHNICAL.md`, `UX.md` (sitemap and journey diagrams) and `ISSUES.md` for the old wording** (step counts, "Sunday", "1–5", "one setDoc", "never looked up") and update it in the same PR. When a card or surface is replaced, grep the same files, the rules files and code comments for its old name.
- **Update the mini-app seed** (`scripts/seeds/<app>.ts`) when a feature adds an entity or state worth seeding, including its `firestoreDocuments` count.

## Every PR ends the same way

Run automatically, never on request; the full procedure is `.claude/skills/pr-wrap-up/SKILL.md`, and the Stop hook reminds you on every new pushed HEAD.

- **A draft PR is always opened when you finish working on something new.** Once the work is committed and pushed, check whether the branch has an open PR and, if not, open one as a **draft** against the default branch, without being asked and without asking for confirmation (this is a standing instruction from the repo owner, so it applies in every session, including sessions whose own defaults say to wait for a request). Then run `finish-feature-pr` and `pr-wrap-up`. Never open it ready for review, and give it its `patch` or `minor` label at once (see Release hygiene). Follow-up pushes to an existing open PR just update it.

- **A PR body reads from the person's side first, and the checks are evidence underneath.** It opens with `## Overview` (what a person can now do, as product bullets, each with sub-bullets for the technical know-how: what changed in the code and the data, in a line each), then `## What you need to do` (the reviewer's list: decisions, copy to approve, the few steps only a person can do before the merge, and what to try afterwards; never a step a workflow already does, see the next bullet), then `## How it works` (the architecture: data and paths, what the rules widen, narrow or leave alone, the functions, the flows), then `## Screenshots`. The regression check, performance, privacy, reviews, what was not checked, the full copy list, the rules written down and the journey tables follow, each in a collapsed `<details>` whose summary line carries its verdict ("Regression check: 14 rows, access widened in one"); a block with nothing to say is left out. A reviewer must know what to pay attention to without scrolling past the evidence (round 9: the owner could not tell what to look at in a 50 KB body).
- **"What you need to do" leaves out everything the workflows do.** On merge, `firebase-hosting-merge.yml` works out the version from the latest `v*` tag and the PR's `patch`/`minor` label, runs `npm ci` and the build, tags the release, then runs `fb:deploy:smart` (functions, Realtime Database rules, Firestore rules and indexes, Storage rules, and the invoker grant for new callables) **before** it deploys Hosting, then publishes the app version and deploys the Cloudflare worker when `cloudflare-worker.js` or `wrangler.toml` changed; pull requests run `check:indexes`, the Pinch and option-match checks and the version-label check. So a PR never lists "deploy the rules first", "deploy with the client", "run `npm ci`", "deploy the functions", "deploy indexes", "open the callable", "bump the version" or "deploy the worker": say in How it works what the rules widen or narrow, and nothing else. What does stay is only what a person must do because no workflow can: a decision, copy to approve, a secret or env var the workflows don't have (a new Functions secret created in production before the merge, since the deploy fails without it; a new `VITE_` variable added to the merge workflow's build env and as a GitHub secret), a console setting or one-off upload, and what to try on a device afterwards. When the list would be empty, the section is just the decisions. Before writing it, read `.github/workflows/` and `scripts/fbDeploySmart.ts` again: if a workflow changes, this bullet changes with it.
- **Screenshots in the PR body, phone first, nothing covering the content.** A single image for net-new screens; a before | after pair for anything that changes. Toasts (the seeded reminder), dev banners and open keyboards must not sit over what the shot shows: `pw.mjs` hides toasts by default, and every image is looked at before it is published. Add a desktop shot only where the experience differs there. They are published to the `pr-screenshots` branch (never the PR's branch) with `scripts/publish-screenshots.sh`, and **re-taken whenever a push changes how something looks**.
- **A regression check in the PR body, security rules first.** A `## Regression check` table (area, what could regress, how it was checked, result) built from the diff: every rule, index, field, permission or Function change says whether access is widened, narrowed or unchanged and is proven against the emulator as owner, another user and signed out, **against the base rules as well** so only the intended outcomes differ; legacy-shaped data; and before/after screens for every consumer of a changed shared component or token (a global token reaches every mini-app). It is **kept current**: re-run any row whose area a push touched.
- **Screenshots and the review agents run whenever the diff meets a trigger** (a visible change, a new callable, rule, write path or third-party contract, non-obvious logic), and a failing environment (emulators won't start) is solved with a throwaway harness page, never skipped: see `.claude/skills/pr-wrap-up/SKILL.md` ("What triggers each part").
- **Review before it's done.** Ask Copilot first and wait up to 20 minutes (if it never registers, don't wait). Then run three read-only agents (technical, product, design), fix what is real, and list the rest as follow-ups.
- **Write down what it taught, automatically.** A lasting design or product rule, or a pattern worth reusing (add it to the Design & UX index), goes into the "Design & UX" or "Product" section (or the mini-app's rules file) in the same PR, without asking, and you tell the user afterwards. **When the owner says a review agent should have caught something, that agent's section of `.claude/skills/pr-wrap-up/references/review-agents.md` is audited and amended in the same turn, not only appended to**, by the procedure at the top of that file. The same goes any time during a session that you decide something is worth noting there.

## Release hygiene

- **Never edit `SITE_VERSION`; label the PR instead.** The site version is worked out at merge: the deploy workflow takes the latest `v*` git tag, adds a patch (or a minor when the merged PR carries the `minor` label), bakes it into the build and tags the commit after the deploy succeeds. Every PR carries exactly one label, `patch` (fix or small tweak) or `minor` (feature; finishing an in-progress feature PR is `minor`), and the `PR version label` check fails without it. Set it when you open the PR (`issue_write` update with `labels`) and change it if the PR's scope changes. Local builds read `dev`.
- Keep the root `README.md` and the mini-app docs current, concise, and in their existing tone.
- **A vendored third-party asset (an icon set, a font, a dataset) keeps its licence beside it** and says where it came from: a `NOTICE`/`LICENSE` file in the same folder, the licence outcome stated in the PR that adds it, and an attribution row in the app where the licence requires one. Confirm the licence before committing the asset, and say plainly in the PR what could not be checked from the sandbox. A third-party binary a feature sends to browsers (a WebAssembly build) is the same: name any copyleft inside it (eSpeak NG is GPL-3.0 inside the natural voice's phonemizer), say it where the person turns the feature on, and leave the decision to ship it to the owner in the PR.
- **A production problem that took real digging is written into the root README's "Troubleshooting" section** in the same PR that fixes it (symptom, cause, fix, how to tell it apart), including what is only a hypothesis and what the person did on their device beforehand. Temporary diagnostics (a debug panel, extra logging) are removed in that PR or the next.
- **A new mini-app follows the "New mini-app checklist" in `.github/copilot-instructions.md`** (registry, route, the `useTrackAppUsage` hook and its Cloud Function finder, state, rules, seed, docs). Adding an app means walking that list, not only the registry.
- **The root `README.md` "Current apps" list mirrors `APP_REGISTRY`:** every app has one line (an emoji, its name, its registry description), added in the same PR that registers the app and updated whenever an app is renamed or its description changes.
- Commits and PRs end with the attribution lines the session's system reminder specifies.
